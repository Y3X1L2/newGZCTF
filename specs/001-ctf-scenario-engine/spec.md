# Feature Specification: CTF 场景化实战平台

**Feature Branch**: `001-ctf-scenario-engine`

**Created**: 2026-05-16

**Status**: Draft

**Input**: User description: "基于 GZCTF 平台开发真实世界场景设计、应急响应题目模块、以及创新提交形式的 CTF 实战平台——当前阶段聚焦于上述场景的基础设施搭建与平台能力建设，而非直接出题。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多阶段真实场景挑战 (Priority: P1)

竞赛管理员创建一个真实世界场景，将多个题目环境串联为完整的攻击链（信息搜集 → 外网打点 → 内网穿透 → 横向移动 → 权限提升）。选手在场景中逐步推进，每个阶段完成后解锁下一阶段，最终完成整个攻击链。选手可以清楚看到每一步的考察目标和能力说明。

**Why this priority**: 这是本平台区别于传统 CTF 的核心价值——将孤立题目转化为有叙事逻辑的真实攻击链。是整个平台的基石功能。

**Independent Test**: 管理员可创建一个包含 3 个阶段的场景（如"外网入口→内网扫描→域控提权"），选手从阶段 1 开始逐步解锁并完成全部阶段，系统记录每阶段的完成时间和操作路径。

**Acceptance Scenarios**:

1. **Given** 管理员登录平台，**When** 创建新场景并添加多个阶段的题目环境（每个阶段包含独立容器/虚拟机），设置阶段间的前置依赖关系，**Then** 场景创建成功，选手视图展示第一阶段为可访问状态，后续阶段为锁定状态。
2. **Given** 选手在场景阶段 1 中成功获取 Flag 并提交，**When** 系统验证 Flag 正确，**Then** 阶段 1 标记为完成，阶段 2 自动解锁，选手获得阶段 2 的访问入口（如新 IP/端口/凭证）。
3. **Given** 选手完成场景全部阶段，**When** 提交最后一个阶段的 Flag，**Then** 系统展示场景完成总结，包含各阶段耗时、考察能力点及整体得分。
4. **Given** 管理员设置了阶段间的网络隔离（如阶段 2 只能从阶段 1 的容器/VM 访问），**When** 选手处于阶段 1，**Then** 选手无法从外部直接访问阶段 2 的环境，必须通过阶段 1 作为跳板自行搭建内网隧道（如代理转发、端口映射）进行渗透。平台仅提供入口节点的直接访问，内部网络靶机由选手自行探索和连接。

### User Story 2 - 应急响应挑战模块 (Priority: P1)

竞赛管理员创建应急响应（IR）类型题目，根据靶机类型提供 SSH 连接凭证（Linux）或 Web 桌面代理（Windows）访问目标环境。选手登录受损系统，执行漏洞加固、数据恢复、日志审计、攻击路径还原等应急响应任务。系统根据选手的操作完整度和结果准确性自动评分。

**Why this priority**: 应急响应是网络安全实战的关键能力，与攻击场景形成互补，是平台完整性的必要组成部分。与 US1 同为 P1 是因为两者是平行的核心模块。

**Independent Test**: 管理员创建一个 IR 题目（如"恢复被加密的数据库并找出攻击者 IP"），选手通过 SSH 登入环境执行操作，完成任务后提交答案（恢复的数据摘要、攻击者 IP、攻击路径描述），系统验证并评分。

**Acceptance Scenarios**:

1. **Given** 管理员创建 IR 题目，**When** 配置 SSH 访问凭证（用户名/密钥/密码）、设置任务目标（如"恢复数据库中的用户表"、"找出 Web 日志中的攻击者 IP"）、配置验证规则（自动检测目标状态或提供参考答案），**Then** IR 题目创建成功，选手可见题目描述和 SSH 连接信息。
2. **Given** 选手打开 IR 题目，**When** Linux IR 环境通过 SSH 凭证连接（或 Windows IR 环境通过浏览器内嵌 Web 桌面代理连接），**Then** 成功登录到受限操作环境，可以执行命令进行排查和修复。
3. **Given** 选手在 IR 环境中完成修复操作（如恢复数据库），**When** 提交答案或系统自动检测到目标状态已达成（如数据库服务恢复、特定文件被修复），**Then** 该检查点标记为完成，选手获得对应分数。
4. **Given** IR 题目要求选手还原攻击路径，**When** 选手提交包含攻击时间线、入侵方式、受影响资产的报告，**Then** 系统记录提交内容，管理员可在后台查看并进行人工评分（如已配置）。
5. **Given** 选手在 IR 环境中执行了破坏性操作（如误删关键文件），**When** 选手请求环境重置，**Then** 系统在确认后将环境恢复至初始状态。

### User Story 3 - 综合提交与多维评分 (Priority: P2)

选手在完成场景或 IR 题目后，不仅提交 Flag，还可提交解题报告（Writeup）、攻击者 IP、中间关键凭证等多元信息。系统根据管理员预设的评分规则，综合 Flag 正确性、报告质量、关键信息准确度等维度自动或半自动评分，并生成排名。

**Why this priority**: 创新的提交与评分机制是前两个用户故事的价值放大器，但可基于 US1/US2 完成后独立叠加。P2 优先级确保核心场景和 IR 能力先落地。

**Independent Test**: 管理员为场景配置评分规则（Flag 占 40%、Writeup 占 30%、关键 IP 占 30%），选手提交所有类型答案后，系统自动计算综合得分并在排行榜中展示。

**Acceptance Scenarios**:

1. **Given** 管理员编辑场景/题目的评分配置，**When** 设置多种提交类型（Flag、解题报告、攻击者 IP、中间凭证等）及各类型分值权重，**Then** 评分规则保存成功，选手界面展示各类型的提交入口和分值说明。
2. **Given** 选手在场景中完成挑战，**When** 提交 Flag（系统自动验证）、上传解题报告（PDF/Markdown）、填写攻击者 IP 等关键信息，**Then** 所有提交被系统记录，自动验证的部分立即出分，需人工评审的部分进入评审队列。
3. **Given** 选手提交的 Flag 错误，**When** 系统验证失败，**Then** 扣除对应的尝试次数（如配置了次数限制）或给予部分分（如配置了递减评分），但不影响其他提交类型的已有得分。
4. **Given** 管理员的评分配置中 Writeup 占 30% 权重且设为人工评审，**When** 管理员在后台查看选手提交的 Writeup 并进行评分（1-10 分），**Then** 该部分得分按权重计入选手总分，排行榜实时更新。
5. **Given** 多个选手提交了不同组合的答案，**When** 系统计算综合得分，**Then** 排行榜按总分降序排列，选手可查看自己的各维度得分明细。

### User Story 4 - 场景拓扑可视化与管理 (Priority: P3)

管理员通过可视化界面设计和查看场景的网络拓扑结构——包括题目节点、网络连接关系、阶段隔离边界。选手在挑战过程中可查看当前可访问的网络拓扑视图（仅展示已解锁部分），帮助理解攻击路径。

**Why this priority**: 提升场景设计和选手体验的可用性，但不影响核心功能运行。作为体验增强在 P3 实现。

**Independent Test**: 管理员通过拖拽或配置创建包含 4 个节点的网络拓扑（外网区→DMZ区→内网区→核心区），设置节点间的网络连通规则，保存后选手视图展示当前阶段的拓扑结构。

**Acceptance Scenarios**:

1. **Given** 管理员在场景编辑器中，**When** 添加题目节点、绘制网络连接线、设置网络隔离规则（如"A 可访问 B，B 不可访问 A"），**Then** 拓扑图实时更新并保存。
2. **Given** 选手在场景中处于阶段 2，**When** 查看拓扑视图，**Then** 仅展示阶段 2 及之前已解锁节点的拓扑结构和网络关系，后续阶段节点为灰色不可见状态。
3. **Given** 场景拓扑中包含不同类型的节点（攻击入口、内网主机、域控等），**When** 选手悬停在节点上，**Then** 显示节点的角色说明和提示信息（如"内网主机 - 需要从入口节点进行横向移动"）。

### Edge Cases

- 选手同时参与多个场景时，各场景的状态和计时是否独立？（假设：独立计时，互不影响）
- 场景中包含的题目环境故障（容器崩溃）时，选手是否会丢失进度？（假设：进度持久化，环境支持快速重置）
- IR 环境中选手误操作导致环境不可用时的恢复机制？（已在 US2-5 中覆盖）
- 多人同时进行同一场景时，每个选手是否拥有独立的环境实例？（假设：每个选手获得独立环境副本）
- 评分权重之和超过或不足 100% 时的处理？（假设：系统强制校验权重总和为 100%）
- 选手提交的 Writeup 文件大小和格式限制？（假设：限制 PDF/Markdown 格式，单文件不超过 50MB）
- 场景阶段间的 Flag 是否可以重复使用？（假设：每个阶段 Flag 唯一，不可跨阶段使用）
- 选手在场景中途退出后再进入时，环境状态是否保留？（假设：环境状态保留，选手可从上次中断处继续）
- 选手预约时间段结束但未完成全部阶段时，进度如何处理？（假设：进度保留，选手可预约下一个时间段继续，但环境需重新启动）
- 单机服务器资源接近饱和时，新的环境创建请求如何处理？（假设：排队等待，按预约时间优先分配，超时提示选手另选时间段）

## Requirements *(mandatory)*

### Functional Requirements

**场景管理 (Scenario Management)**:
- **FR-001**: 系统 MUST 支持在 GZCTF 现有 Game 实体下，管理员创建多阶段真实场景作为新的 Challenge 子类型，每个场景阶段可包含一个或多个题目环境
- **FR-002**: 系统 MUST 支持设置阶段间的前置依赖关系（线性解锁 / DAG 有向无环图解锁）
- **FR-003**: 系统 MUST 支持为每个阶段配置独立的网络访问规则（如阶段 B 只能从阶段 A 的容器/VM 访问）
- **FR-004**: 系统 MUST 为每个选手提供独立的场景环境副本，确保选手间操作互不干扰
- **FR-005**: 系统 MUST 记录选手在场景中的关键操作时间线（阶段解锁时间、Flag 提交时间、环境访问日志）
- **FR-019**: 系统 MUST 支持通过 libvirt API 管理 Windows 靶机 VM 的生命周期，包括：从磁盘镜像模板创建 VM、启动、暂停、快照恢复（用于环境重置）、关机、销毁
- **FR-023**: 系统 MUST 支持管理员通过 Web 后台上传 Windows VM 磁盘镜像文件（支持 .qcow2、.ova、.vmdk 格式），系统自动存入本地存储池并注册到 libvirt，单文件上传大小上限 50GB
- **FR-024**: 系统 MUST 支持管理员通过配置 Docker/OCI Registry 地址拉取 Linux 靶机的容器镜像，支持公开和私有仓库（需配置认证凭证）
- **FR-025**: 系统 MUST 在场景创建界面提供已注册的环境模板列表（区分容器镜像和 VM 镜像），管理员可搜索、预览模板信息后选择使用

**应急响应挑战 (IR Challenges)**:
- **FR-006**: 系统 MUST 支持在 GZCTF 现有 Game 实体下，管理员创建 IRChallenge 作为新的 Challenge 子类型，配置访问方式：Linux 靶机提供 SSH 连接凭证（密码或密钥），Windows 靶机提供 Web 桌面代理（Guacamole/noVNC）浏览器内访问
- **FR-007**: 系统 MUST 支持配置 IR 题目的检查点（Checkpoint），每个检查点定义目标状态和验证方式
- **FR-008**: 系统 MUST 支持 IR 环境的状态自动检测（如检测特定服务是否恢复、文件是否修复）
- **FR-009**: 系统 MUST 支持选手请求 IR 环境重置，重置后恢复至题目初始状态
- **FR-010**: 系统 MUST 记录选手在 IR 环境中的所有操作命令日志（Linux: Shell History，Windows: PowerShell 日志），用于审计和评分参考
- **FR-021**: 系统 MUST 支持 Windows IR 靶机通过浏览器内嵌 Web 桌面代理（Guacamole/noVNC）访问，选手无需安装本地客户端，所有操作在 Web 页面中完成，支持剪贴板共享和文件传输
- **FR-022**: 攻击场景（US1）中，系统 MUST 仅提供入口节点的直接访问方式（如 Web 页面或 SSH），内部网络靶机由选手通过渗透技术自行建立连接，平台不提供内部节点的直接访问入口

**提交与评分 (Submission & Scoring)**:
- **FR-011**: 系统 MUST 支持多种提交类型：Flag 文本、解题报告文件、IP 地址、关键凭证等
- **FR-012**: 系统 MUST 支持管理员为每种提交类型配置不同的验证方式（自动验证 / 人工评审）
- **FR-013**: 系统 MUST 支持管理员配置综合评分的权重体系，各类型权重之和为 100%
- **FR-014**: 系统 MUST 在 Flag 验证时支持精确匹配和正则匹配两种模式
- **FR-015**: 系统 MUST 在排行榜中展示选手的综合得分及各维度得分明细

**通用能力 (Cross-Cutting)**:
- **FR-016**: 系统 MUST 在所有场景/题目中支持倒计时和答题时间窗口限制
- **FR-017**: 系统 MUST 为管理员提供场景/题目的操作审计日志
- **FR-018**: 系统 MUST 遵循现有 RBAC 权限体系，区分管理员、出题人和选手的角色权限
- **FR-020**: 系统 MUST 支持预约分时制：选手可选择/被分配时间段，系统在预约时间自动启动环境，时间段结束后自动回收资源（停止 VM/容器），并保留选手进度数据

### Key Entities *(include if feature involves data)*

- **Scenario（场景）**: 代表一个真实世界攻击链场景。包含名称、描述、阶段列表、评分配置、时间窗口、所属赛事。一个场景包含多个 Stage。
- **Stage（场景阶段）**: 代表攻击链中的一个步骤。包含阶段序号、名称、考察能力说明、前置阶段依赖、网络隔离规则、关联的题目环境列表。
- **ScenarioInstance（场景实例）**: 选手在场景中的运行实例。包含当前所处阶段、各阶段完成状态、环境访问凭证、操作时间线、关联的选手。
- **IRChallenge（应急响应题目）**: 代表一个应急响应类型题目。包含 SSH 连接配置（主机、端口、用户名、认证方式）、任务描述、检查点列表、环境模板引用。
- **IRCheckpoint（检查点）**: 代表 IR 题目中的一个验证目标。包含检查点描述、验证方式（自动检测命令/脚本或参考答案）、分值、是否为必须完成项。
- **IRInstance（应急响应实例）**: 选手在 IR 题目中的运行实例。包含环境访问状态、已完成检查点、Shell 操作日志、环境重置历史。
- **Submission（提交）**: 选手的一次提交记录。包含提交类型（Flag/Report/IP/Credential）、提交内容、验证状态（正确/错误/待评审）、得分、提交时间戳。
- **ScoringRule（评分规则）**: 定义一种提交类型在总分中的权重和验证方式。包含类型名称、权重百分比、验证模式（自动精确匹配/自动正则/人工评审）、尝试次数限制、递减评分规则。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员可在 10 分钟内创建一个包含 3 个阶段的完整真实场景（从环境选择到发布）
- **SC-002**: 选手在场景中的阶段解锁延迟不超过 5 秒（Flag 验证通过到下一阶段可访问）
- **SC-003**: IR 环境的 SSH 连接建立时间不超过 10 秒
- **SC-004**: 系统支持至少 200 名注册选手通过预约分时制参与场景挑战，单一时段同时活跃环境数不低于 20 个，每个选手的环境副本独立运行
- **SC-005**: IR 环境的自动检查点验证在 30 秒内返回结果
- **SC-006**: 选手对综合评分各维度的得分明细理解率达到 90%（通过赛后问卷调查）
- **SC-007**: 场景拓扑可视化界面的拓扑图渲染在 2 秒内完成（100 节点以内）
- **SC-008**: 环境重置操作在 60 秒内完成

## Assumptions

- 基于现有 GZCTF 平台进行扩展开发，复用其用户体系、赛事（Game）管理、题目（Challenge）框架、Flag 验证、排行榜等基础能力
- 场景（Scenario）和应急响应题目（IRChallenge）作为 GZCTF 现有 Challenge 实体的新子类型，挂载在 Game 实体下，复用 Game 的时间窗口、权限控制和排名发布机制
- Linux 靶机环境以容器化（Docker）方式部署，每个题目拥有独立的容器或容器组
- Windows 靶机环境通过 KVM/QEMU + libvirt 虚拟化方案在 Linux 宿主机上运行，使用 libvirt API 进行 VM 生命周期管理（创建、启动、停止、快照恢复、销毁）
- IR 环境：Linux 靶机使用容器，Windows 靶机使用 KVM/QEMU VM，通过 SSH（Linux）或 WinRM/Web Terminal（Windows）暴露给选手
- 网络隔离通过 Linux 网络命名空间 + iptables/nftables 或 SDN 实现，容器与 VM 统一纳入场景网络拓扑
- 每个选手获得独立的场景/IR 环境副本（非共享），确保隔离性
- 解题报告支持 PDF 和 Markdown 两种格式，单文件大小限制 50MB
- 平台已有基础的用户认证和 RBAC 体系，本功能在此基础上扩展权限粒度
- Linux 靶机的容器镜像从 Docker/OCI Registry（如 Docker Hub、Harbor）拉取，支持公开和私有仓库
- Windows 靶机的 VM 磁盘镜像通过 Web 后台上传至服务器本地存储池，支持 .qcow2/.ova/.vmdk 格式，单文件上限 50GB
- 场景的 GZCTF 基础平台使用 .NET (C#) + 前端技术栈，本功能的技术栈与之保持一致

### Session 2026-05-16

- Q: Linux 服务器上通过什么方式启动和管理 Windows 靶机虚拟机？ → A: KVM/QEMU + libvirt：在 Linux 宿主机上通过 KVM 虚拟化运行 Windows VM，使用 libvirt API 进行生命周期管理
- Q: 单机部署场景下，如何定义系统的并发容量和资源分配策略？ → A: 预约分时制：选手预约时间段，系统在预约时间自动启动环境，时间段结束后自动回收资源，进度数据持久保留
- Q: 选手通过什么方式访问和操作 Windows 靶机？ → A: 分场景：攻击场景（US1）中选手自行搭建内网隧道访问内部 Windows 靶机（这是挑战的一部分）；应急响应场景（US2）中纯 Windows 靶机通过 Web 桌面代理（Guacamole/noVNC）在浏览器内访问
- Q: 管理员如何将准备好的 VM 磁盘镜像/容器镜像导入平台并用于场景创建？ → A: 混合方案：Linux 靶机的容器镜像从 Docker/OCI Registry 拉取（支持公开和私有仓库），Windows VM 磁盘镜像通过 Web 后台上传至本地存储池（支持 .qcow2/.ova/.vmdk 格式，上限 50GB），系统自动注册到 libvirt
- Q: 场景和 IR 题目与 GZCTF 现有 Game/Challenge 体系的集成层级？ → A: Game 下扩展新题目类型：在现有 Game 实体下增加 Scenario 和 IRChallenge 作为 Challenge 的子类型，复用 Game 的赛事框架（时间窗口、权限、排行榜），但拥有独立的创建/编辑界面
