# TeamLab 组网平台市场与实现调研

更新日期：2026-08-11（第三轮：高性能、快速生命周期与稳定性专项已补充）
状态：进行中，仅调研，不实施功能变更。

## 1. 目标与边界

本调研用于明确 TeamLab 作为可由比赛、培训及外部系统调用的组网底座，还应具备哪些成熟能力，以及这些能力应放在平台、镜像模板还是场景内容中。

调研对象：

1. 指定平台 A：仅浏览已授权账号可见页面，不创建、修改、发布、启动或删除任何资源。
2. 指定平台 B：仅浏览演示页面和 Swagger 接口说明，不调用会产生状态变化的接口。
3. 公开成熟产品与开源项目：用于比较能力模型和实现方式。

本文件不记录账号、密码、令牌、私钥或其他访问凭据。

## 2. 评估框架

每项能力均按以下四个问题记录：

| 维度 | 判断标准 |
| --- | --- |
| 用户价值 | 真实使用者是否需要它，解决哪一步工作。 |
| 平台职责 | 组网底座是否必须负责生命周期、隔离、权限、审计和可观测性。 |
| 模板/场景职责 | 是否应由镜像内软件、设备模型或场景内容承担，避免把业务软件写进底座。 |
| 可实施性 | 成熟实现路径、关键依赖、性能与稳定性风险。 |

能力分级：`已有`、`部分具备`、`缺失`、`不应由底座承担`。只有有直接证据的能力才标记为已有。

## 4. 平台职责判定原则

### 4.1 应由 TeamLab 底座承担

- 资产编排、网络隔离、地址与路由、跨节点连接、容量与调度。
- 模板制品分发、运行环境创建/暂停/恢复/销毁和资源回收。
- 权限、审计、操作幂等、进度、失败原因、日志、流量、抓包和外部 API。
- 对真实设备、仿真设备和虚拟机提供统一的连接、状态与观测模型。

### 4.2 应由镜像、设备模型或场景内容承担

- 操作系统内部账号、服务、AD 域、工业软件、协议栈、PLC/设备行为和业务数据。
- 特定工控协议的业务语义、寄存器点位、故障模型、工艺流程和数字孪生规则。
- 需要随课程或赛事变化的靶场业务内容。

### 4.3 协作边界

底座可以向资产注入有限且可审计的运行参数（如队伍隔离标识、动态 Flag、短期访问令牌），但不在运行时安装工业软件、提升 AD 域或改造未知镜像。对外系统通过版本化 OpenAPI 控制完整生命周期，不直接访问 Agent、Docker 或 libvirt。

## 5. 指定平台 A：已取得的只读证据

### 5.1 产品结构

平台 A 是统一门户下的微前端产品。静态运行时列出独立的“竞赛”“场景”“红蓝对抗”子系统；场景子系统由单独的前端资源加载。这说明它把场景编排视为一等产品能力，而不是竞赛页面中的一个表单。

场景子系统的已发现页面模块包括：

- 场景模板、场景业务配置、场景运行实例与运行监控。
- 物理拓扑、网络管理、资源池、资产、真实资产和资产关联场景。
- 镜像管理、虚拟机管理、目标管理、远程桌面。
- 工业组件目录与工业组件详情。
- 设备管理和设备同步。

其中设备管理的可见接口为 `device-manager`，具备设备同步、登记、批量删除、共享和取消共享；页面字段包含容量、类型、使用状态、分配场景/服务器、使用时间和创建时间。该能力可以借鉴为“稀缺物理资源的登记、占用与归还”，但不能直接假设其已实现完整工业设备协议或真实网络接入。

### 5.2 登录后的只读菜单取证

平台 A 启用了验证码、单会话和登录失败锁定。已按授权完成一次登录，仅读取当前用户和完整菜单树；未执行新建、发布、启动、同步、删除、共享或提交。

其“环境构建”模块的场景相关功能如下：

### 5.4 平台 A 的产品结构复核

从真实返回与静态模块交叉看，平台 A 的强项不是某一个画布控件，而是对象分层：

1. 模板负责可复用的场景定义和校验记录。
2. 资源池和设备管理负责稀缺资源的可用性、占用、共享与释放。
3. 物理拓扑负责受权的真实交换机、端口和资产关联。
4. 工业组件目录负责组件发现、分类和复用。
5. 场景运行、流量、采集和远程桌面在运行面独立呈现。

TeamLab 应吸收这种对象分层，不应复制其将大量底层资源、模板细节和运维动作散落在高权限透传接口中的做法。

### 5.5 已分析的实际对象与操作入口

这部分来自已下载的场景前端模块，而不是菜单名。它证明前端准备了哪些对象、字段和操作入口；由于未执行写操作，不把页面代码当作后端一定已经成功执行的证明。

| 域 | 已确认的对象/字段/入口 | 可借鉴的产品结论 | TeamLab 处理原则 |
| --- | --- | --- | --- |
| 稀缺设备 | 设备名称、容量、类型、创建人、使用人、使用状态、所分配的场景/服务器、使用时间、创建时间、共享标记；支持筛选、同步、登记、共享与取消共享。 | 物理设备或专用介质必须是可查询、可占用、可归还的资源，不是场景 JSON 中的一段地址。 | 增加资源池投影和独占锁；共享是授权策略，不能绕过运行时占用事实。 |
| 物理拓扑 | 物理资产、真实网络、网络配置、自动网络命名、场景编辑、场景模板内容和访问说明均为独立模块。 | 虚实场景必须把“现实连接点”显式呈现，不能隐藏在某台宿主机的网卡配置里。 | 用受管现场连接器/端口作为显式资产；场景只引用获批的连接器。 |
| 运行运维 | 运行实例中有远程桌面、设备信息、设备管理、IP 绑定、动态扩容节点、服务模拟器、策略、防火墙、快照、流量镜像、SOC 和遥测策略模块。 | 场景设计和运行期运维应分层；运行期操作要围绕资产、网络、会话、观测和资源展开。 | 保持运行时/资产/访问会话/观测记录分离，避免把运行按钮塞回设计画布。 |
| 观测与攻防 | 流量镜像、采集、攻击事件、数据统计、脚本执行、流式数据和遥测策略有独立模块。 | 网络报文、检测结果和业务事件应是不同来源，但需要能关联到同一时间线。 | 先统一现有流量、PCAP、日志与运行事件；工业协议事件后续作为设备包可选上报。 |
| 场景复用 | 场景模板、场景练习和面向竞赛/攻防/运维等上层入口均存在。 | 场景版本可以被多种业务复用，上层玩法不应反向污染网络运行模型。 | 场景发布版本只描述可运行环境；比赛、课程、评分和题目通过绑定层接入。 |

平台 A 的静态模块还明确包含网段、自动布局、域配置、服务模拟器、预定义对象、流量镜像、物理资产、路由器、交换机和防火墙相关页面。这些是能力覆盖参考，不是要求 TeamLab 把每一个名词变成独立子系统。后续只读巡检要继续确认其资源占用释放、物理连接授权和运行失败恢复是否真正闭环。

## 6. 指定平台 B：完整 Swagger 与演示前端取证

本轮通过用户更新的代理仅读取了 Swagger JSON、演示首页和前端静态资源；没有向其业务 API 发送写请求。Swagger 自称为底层靶场 API 的前端透传层，版本为 `1.0.0`，基础路径为 `/api/v1`。演示前端与 Swagger 的场景模板、分发和入口接口存在版本差异，因此以下结论分别标注为“Swagger 已证实”或“演示前端已证实”，不假定两者完全同版。

### 6.1 接口面与成熟度判断

Swagger 共列出 **173** 个操作：55 个读取、118 个会改变基础设施状态。只声明一个 `202` 异步响应（创建场景快照）和一个 `409` 冲突响应（克隆场景）；没有全局或操作级认证定义。绝大多数场景响应是未固定字段的对象，模板、虚拟网络和 PVE 集群写模型也可以携带底层节点、网络、磁盘或连接信息。

本轮重新下载的 Swagger 与演示首页均返回 `200`。按 Swagger 标签逐项统计，接口并非只覆盖“场景菜单”：场景 51 项、VM 24 项、Docker 17 项、SDN 16 项、镜像管理 9 项、场景 DHCP 7 项、PVE 集群 6 项、VM 快照 5 项、存储 5 项、容器查看 5 项、VM SFTP 5 项、Docker 执行节点 5 项，以及 VM SSH/RDP/VNC、集群、IP 地址管理、定时任务和 MAC 管理等对象。这证明其产品面覆盖了从模板、计算、网络、运维到存储的全链路，但也进一步证明它是执行基础设施的透传服务，而不是可以直接给第三方系统使用的安全控制面。

### 6.2 演示前端的真实用户流程

已下载的演示前端包含场景管理、场景模板、图形编排、场景分发、选手入口、SSH/RDP/VNC 页面、容器终端/文件管理、三维运行拓扑和流量规则管理。其界面代码体现的流程如下：

1. 场景管理按状态、来源和创建人检索；有空态、错误态、分页、克隆、场景转模板、快照和带名称确认的删除。
2. 图形编排支持 VM、容器、交换机、路由器、防火墙、蜜罐、IDS、IPS、堡垒机、区域、连线、网格、全屏、视图快照、撤销/重做、复制/粘贴、端口映射、DHCP/静态网卡和模板镜像选择。
3. 场景分发可给全班或指定学员设置有效期、说明和附件；仅允许分发创建者拥有的场景，并能查看/撤回分发记录。
4. 选手入口通过一次性票据创建仅含入口虚拟地址路由的 WireGuard 会话，再进入场景工作区。
5. 运行期可对资产进行启动、停止、更新、重克隆、远程终端、桌面或控制台；流量规则有“草稿、校验、发布版本、重载会话、回滚”的明确顺序。

可吸收的体验原则：把“设计、分发、选手入口、运行运维、流量规则”做成互相可跳转但职责清晰的页面；每个危险操作有明确对象、状态和确认。不可照搬的部分：把业务口令、底层端口和直接基础设施地址带到浏览器，或者以普通定时刷新替代控制面事件流。

## 7. 公开成熟方案：已取得的可复核证据

### 7.1 Containerlab：快速网络编排的产品分层

Containerlab 将拓扑文件、节点、连线、管理网、运行目录和生命周期命令作为独立对象。其公开文档明确包含部署、检查、保存、销毁和图形化拓扑；支持业务链路与管理网分离、主机/外部连接、链路时延/抖动/丢包、运行后的配置保存以及按节点筛选操作。

可吸收点：

- 运行环境必须有明确的检查、保存、销毁和资源清单，不只显示“正在运行”。
- 管理面与业务面要分开，运维入口不能天然暴露给选手网络。
- 链路故障和性能参数属于“网络链路能力”，应可审计、可重置，不应散落到镜像启动脚本。
- 拓扑图的布局可利用网段/角色分组，而不是把所有资产做同一维度排列。

不直接照搬：Containerlab 以容器为主，不能替代 TeamLab 的 VM、跨节点 Fabric、比赛权限和实例隔离。

### 7.2 GNS3：控制面、计算节点与模板的对象模型

GNS3 的公开 API 和文档将项目、计算节点、模板、拓扑节点、端口连线、控制台、抓包和运行状态区分开；一个控制器可以管理多个计算节点，节点可以是 Docker、QEMU、交换机、路由器或云/外部连接。API 对节点/连线创建、启动/停止、控制台和抓包分别建模。

可吸收点：

- TeamLab 应持续保持“模板、资产、运行时、节点放置、访问会话”五类对象分离。
- 路由器、交换机和外部连接不是普通业务主机的别名，应在拓扑、端口和可观测性中保留设备语义。
- 计算节点能力、容量和连接状态应是调度输入；控制面不能把单个 Agent 当作唯一执行节点。
- 控制台/运维会话应独立于资产启动，按权限创建并留下审计记录。

不直接照搬：GNS3 偏向网络工程实验，不提供多队隔离、赛事生命周期和统一 API token 授权模型。

### 7.3 Conpot：工业协议仿真应封装为可复用资产

Conpot 使用模板表达设备资料、点位和协议配置，协议实现位于独立模块。其公开代码包含 Modbus、S7comm、IEC 104、BACnet、SNMP、HTTP 等协议服务；一个模板可同时暴露多个协议，并通过共享内部状态模拟跨协议的同一设备行为。

可吸收点：

- 工业设备资产应通过“设备包 + 模板参数 + 健康检查”交付，平台只负责编排、网络、运行、观测、权限和回收。
- 同一设备的多协议状态应由设备包内部维护，不能由 TeamLab 为每种协议写业务逻辑。
- 对协议请求/响应可产生结构化事件，关联到运行时、资产、会话和抓包时间范围。

### 7.4 OpenPLC：虚实结合应通过适配层而不是改造底座

OpenPLC 提供运行时、编程环境、Modbus/DNP3 等服务和多种硬件层选择，代码中将硬件层与 PLC 运行时分开。它适合说明“同一控制逻辑可以连到模拟 I/O 或真实 I/O”，而不是说明平台应把硬件驱动编进调度服务。

可吸收点：

- 把物理设备接入抽象为受控的现场连接器/设备适配器：平台分配、授权、审计和回收连接；适配器实现协议、串口、网卡或厂商驱动。
- 真实硬件接入必须在独立资源池中登记容量、健康、占用与独占锁，不能把现场地址和驱动凭据写入场景拓扑。
- 模拟设备和真实设备应共享“资产端口、状态、日志、观测”的外部模型，但不得假设它们可用同一种启动或销毁命令。

### 7.5 Cisco Modeling Labs：模板定义、制品与外部连接的边界

Cisco Modeling Labs（CML）的公开社区资料将节点定义、基础镜像定义和场景拓扑分开存放：节点定义描述设备类型、CPU、内存和网卡等运行需求；基础镜像定义只引用磁盘制品；拓扑引用节点定义而不携带磁盘。它支持 Docker/QCOW/KVM 设备，以及通过 External Connector 把仿真网络接到受控的物理网络。其示例还把外部连接器、非受管交换机和一般业务节点分别建模。

可吸收点：

- TeamLab 已收敛的“场景只选择模板，制品摘要和镜像参数属于模板库/运行面”的边界是正确的，应保持，不应重新在高级设置中暴露这些内部事实。
- 虚实结合的连接器应是显式的、受管的拓扑节点/端口，而不是将某块宿主机网卡暗中桥接给资产。
- 场景可复用应交付“拓扑 + 节点定义要求 + 使用说明 + 依赖清单”，不能把受版权保护的镜像内容混入场景包。
- 大规模示例只说明规模可能性，不等价于生产容量承诺；容量必须按本平台节点硬件、镜像、链路和队伍并发实测。

### 7.6 Open vSwitch：网络数据面与观测能力应独立于业务资产

Open vSwitch 的官方仓库明确将它定位为可跨物理服务器分布的虚拟交换平台，支持 KVM；已列出的能力包括 VLAN、镜像、NetFlow、sFlow、QoS、VXLAN/Geneve/GRE 隧道以及事务化配置数据库。

可吸收点：

- TeamLab 的“采集所有节点间流量”应以宿主机网桥/虚拟交换路径为事实源：镜像或采集点看到的是经过该网络段的报文，而不是要求每个来宾安装代理。
- 连线故障、镜像、限速、丢包、时延和 QoS 都属于网络数据面能力，应按运行时、链路和时间范围记录操作；资产镜像不承担这类行为。
- 不应为了使用某项高级能力而立即将现有 bridge/Fabric 全部迁移到 OVS。首要任务是统一“链路/采集点/抓包任务/流量元数据”的对象模型；当现有数据面无法提供所需能力时，再以受控节点能力逐步引入 OVS。

### 7.7 远程访问和检测产品的边界

Apache Guacamole、GNS3 的控制台和平台 B 的 SSH/RDP/VNC 页面共同说明：远程访问不是资产属性，而是一个独立的短时会话。会话需要有创建者、授权来源、目标运行时/资产、协议、开始结束时间、状态和审计记录。TeamLab 已有 Guacamole 路径，后续只应补足权限投影、会话回收、错误解释和关联日志，不重造远程桌面协议。

Suricata/Zeek 类检测产品适合作为“观测解析器”，不应成为 TeamLab 场景控制器。TeamLab 保存原始抓包、连接元数据和部署事件；检测器或设备包可以上报结构化事件。事件必须带上运行时、资产/端口、网段、时间、来源和可信度，才能与 A→B→C→B→A 的网络路径可靠关联。

### 7.8 OpenStack Neutron、OpenNebula 与 NetBox：商业控制面的基本功

这三类产品不是靶场编排器，但提供了 TeamLab 作为商业底座必须具备的“对象事实”做法：

- **OpenStack Neutron** 将网络、网段、端口绑定、路由、安全组、QoS、trunk、配额和项目范围作为独立对象；其文档还专门处理迁移失败后的陈旧端口绑定清理。TeamLab 不需要复制其大规模云网络实现，但应把“资产接口、网络、放置、绑定状态和清理”明确建模，不能只凭部署日志猜测网络是否还存在。
- **OpenNebula** 的公开说明把角色权限、多租户隔离、配额和治理作为平台能力。这印证 TeamLab 的容量预留不能仅按机器空闲量展示，必须同时按比赛/队伍/资源池/正在执行的 operation 计算。
- **NetBox** 将 IP 地址分配给具体接口而不是笼统设备，并强调租户归属、前缀/IP 唯一性、变更记录、事件驱动 webhook、设备/接口/线缆关系。TeamLab 应借鉴其对象关联和变更可追溯性，而不把 NetBox 作为运行时数据库或把物理资产管理系统嵌入控制器。

共同结论：拓扑画布是编排入口，不是事实源。运行面至少要独立保存资产接口、地址、网段、连线、节点放置、资源占用、观测任务和操作审计，才能在暂停、重启、失败恢复与销毁时做到可解释。

| 工控协议与工艺 | 工业组件、真实资产、采集入口。 | 未见专门工业 API。 | Conpot/OpenPLC 体现协议/工艺与底座分离。 | 缺失 | 建立设备包目录，首批做真实协议服务与结构化事件，不把协议逻辑写入控制面。 |
| 虚实结合 | 真实资产和物理拓扑入口。 | 未证实。 | CML 外部连接器、OpenPLC 硬件适配层。 | 缺失 | 高优先级独立路线：受管现场连接器 + 资源锁 + 网络隔离 + 审计。 |
| 外部 API | 未完整取得。 | 高权限基础设施透传 API。 | GNS3/CML 有对象 API。 | 有 OpenAPI | 完整生命周期 API、scope、资源授权、operation、事件和 webhook；严禁透传 Agent。 |

### 8.1 平台 A 功能的归类结论

| 平台 A 可见能力 | TeamLab 应对策略 | 原因 |
| --- | --- | --- |
| 资产、镜像、靶标、类型目录 | 保持并规范化模板/资产目录。 | 是所有场景复用与发布的必要前提。 |
| 场景编排、运维、资源池、网络、流量 | 继续补齐用户流程和外部 API，不重造运行底座。 | TeamLab 已有相应核心事实，应解决可见性、可控性和验收深度。 |
| 设备/云盘的共享和占用 | 引入统一资源池投影，支持受控物理设备/持久化介质登记。 | 适合稀缺资源，但必须独占锁、审计和释放。 |

| 场景练习与多类竞赛 | 以 TeamLab binding 为基础分别接入 CTF、培训、渗透等上层产品。 | 玩法不应倒灌进网络底座。 |
| 工业组件、真实资产、物理拓扑 | 采用设备包和现场连接器路线。 | 需要协议/驱动能力，但这些不属于编排和调度服务本身。 |

## 9. 详细调研计划

### R1：竞品功能取证

目标是形成“每项功能都有来源和证据”的矩阵，而不是观看界面后列主观印象。

| 工作项 | 方法 | 输出 | 完成判定 |
| --- | --- | --- | --- |
| 平台 A 登录后只读巡检 | 菜单、列表、详情、帮助、浏览器网络请求；不执行写操作。 | 页面结构图、功能表、关键对象和状态截图。 | 资源、拓扑、运行、运维、观测、物理设备六个域均有证据。 |
| 平台 B Swagger 取证 | 只下载 OpenAPI JSON，按 tag 和模型生成接口矩阵。 | 全路径清单、认证/幂等/状态机/事件能力表。 | 每个接口归类为读取、创建、状态命令、运维或观测。 |
| 平台 B 演示页面巡检 | 只浏览可见功能、帮助与空态。 | 用户流程和 UI 可用性记录。 | 不发送任何写请求。 |
| 公开产品取证 | 只用官方文档、官方 API 或开源项目文档。 | 引用表和能力证据。 | 每类至少两个独立来源，关键结论不依赖营销页。 |

### R2：用户任务与功能完整性调研

按用户真实目标，而不是按菜单分类梳理能力：

1. 场景作者：选择已认证模板/设备包，建立网段、交换机、路由器和连线，配置少量对场景真正有意义的参数，校验、试运行、发布、复用和归档。
2. 比赛管理员：把发布版本绑定比赛，预先准备制品，启动多队环境，查看容量、部署进度、失败原因，暂停、恢复、重置、销毁并清理。
3. 运维人员：经授权访问某队某资产，查看会话、日志、流量、抓包、资产状态和历史操作，安全地关闭会话或发起受控重建。
4. 选手：只看到自己队伍被暴露的入口、题目和必要状态，不可得到管理面、镜像、运维凭据、其他队伍流量或物理设备控制权。
5. 外部系统：通过 OpenAPI 从创建/编辑/校验/发布/准备到运行、观测、运维、销毁全周期管理，不需调用 Agent 私有接口。

每个任务会逐项核对：前置条件、权限、接口、实时进度、失败中文提示、幂等、审计、恢复与最终清理。

### R3：工业协议与虚实结合专项调研

| 方向 | 必答问题 | 预期产物 |
| --- | --- | --- |
| 协议仿真 | 首批哪些协议对教学/攻防最有价值，采用真实协议服务还是仅生成流量，如何表达点位和状态。 | 设备包目录与首批协议优先级。 |
| 工艺仿真 | 设备状态如何与工艺规则耦合，如何在不耦合底座的前提下实现跨设备联动。 | 设备包内部事件/状态契约。 |
| 虚实结合 | 真实 PLC、传感器、串口、现场网段如何注册、占用、隔离、审计、失联和释放。 | 现场连接器、资源池与安全模型。 |
| 观测 | 如何同时保存网络流量、协议字段、资产状态和场景事件，并做时间关联。 | 分层观测模型与保留策略。 |
| 安全 | 如何禁止选手越权接触管理网、其他队伍、现场资产或平台 Agent。 | 网络隔离、访问代理和审批/审计边界。 |

### R4：实现方案评估原则

每项候选方案必须满足以下门槛，才进入开发计划：

- 不要求运行时修改未知镜像、安装软件或猜测来宾状态。
- 不在 TeamLab Application/Agent 中写 Modbus、S7、PLC、AD 或工艺业务逻辑。
- 不把真实设备 IP、串口路径、厂商密码或密钥放进发布拓扑、日志或外部 API 响应。
- 保持 Docker、Linux VM、Windows VM、虚拟网络设备和真实设备在统一资产/端口/网络/观测模型中，但允许各自使用不同执行适配器。
- 公开 API 保持版本化、scope/resource grant、幂等键、异步 operation、事件游标、Webhook 和可读错误码，不暴露 Agent 命令。
- 容量、资源锁、部署队列、销毁和故障恢复复用 Runtime/TeamLab 既有事实源，不建立第二套调度器。

## 10. 初步最优路线（待完成竞品取证后冻结）

### 10.1 底座只扩展四类稳定能力

1. **设备包目录**：登记兼容的工业协议仿真包、工艺仿真包和网络设备包。目录只描述版本、端口、资源需求、参数 schema、健康检查和可观测能力；包内容保持在 OCI/镜像制品中。
2. **现场连接器**：在具备现场网络或串口的受管节点上运行，受平台授权后把已登记的物理端口映射给一个运行时。它只能连接被分配的端口/网段，不能成为到内网的通用跳板。
3. **链路模型**：对明确的场景链路提供时延、抖动、丢包、断开和恢复等可选网络行为，使用宿主机数据面实现，并记录操作与影响范围。
4. **分层观测**：保留现有桥接抓包和流量元数据；设备包可额外提交脱敏的协议事件。两者按运行时、资产、网段和统一时间轴关联，不能伪称解析不到的协议字段。

### 10.2 明确不做的事

- 不把 PLC 编程、工艺逻辑、工业软件安装和厂商驱动变成 TeamLab 控制器的功能。
- 不提供“任意真实网络桥接”或“任意串口转发”；每个现场连接必须登记、审批、独占、可见、可撤销。
- 不为工控场景另造模板库、队列、生命周期或权限系统。
- 不为了视觉上的“数字孪生”构建与运行无关的第二套画布和状态模型。

### 10.3 可实施的最小对象模型（调研结论，不代表已开发）

为避免后续把“工业组件、现场硬件、网络故障、镜像模板”堆成互相依赖的大功能，建议只在现有 TeamLab 场景/发布版本/运行时/operation 体系外增加四类对象，并复用既有权限、队列、审计和事件机制：

| 对象 | 最小需要记录的事实 | 不应记录或执行的内容 | 形成的用户能力 |
| --- | --- | --- | --- |
| 设备包 | 名称、版本、制品引用、支持的资产类型、暴露端口、公开参数 schema、资源需求、健康检查、可上报事件类型。 | PLC 业务规则、厂商驱动实现、平台密钥、现场地址。 | 作者可以像选模板一样选择仿真设备；设备包作者不需要修改 TeamLab 控制器。 |
| 现场连接器 | 受管节点、允许接入的物理端口/网段/串口标识、健康、容量、占用者、授权范围、最后操作和回收状态。 | 现场设备密码、通用内网路由、任意端口转发。 | 管理员可以受控地把一段真实资源分配给一个运行时，并知道谁占用、何时释放。 |
| 链路策略 | 所属运行时/链路、时延、抖动、丢包、限速、断开状态、起止时间、操作来源和恢复方式。 | 来宾镜像脚本、不可解释的全局网络修改。 | 作者/管理员可以在明确链路上复现实验条件，结束后自动按运行时回收。 |
| 协议事件 | 运行时、资产、接口/端口、时间、事件类型、来源、可信度、结构化字段版本和指向原始 PCAP 的引用。 | 未经验证的协议结论、原始敏感载荷的无限制复制。 | 流量、设备状态、日志和工艺/协议事件可以在同一时间线上检索和解释。 |

四类对象都必须通过 TeamLab 的发布版本、容量预留和 operation 创建；任何耗时动作都返回统一 operation。这样可以满足设备包/现场接入的扩展需求，而不引入第二套队列、第二套生命周期或另一条越过平台的执行通道。

“竞品有”不等于“把竞品菜单逐项复制”。以下按用户任务拆分，要求是达到等价能力覆盖，并采用 TeamLab 的权限、调度和 API 架构实现。

### 12.1 必须形成闭环的能力清单

| 用户任务 | 必须具备的能力 | 放置位置 | 最小闭环验收 |
| --- | --- | --- | --- |
| 作者编排 | 资产目录、模板选择、网段/端口/交换机/路由器/连线、区域分组、校验、布局、设计版本和发布版本。 | 底座 + 场景定义。 | 从空白场景到发布版本，画布、JSON、校验结果和版本内容互相一致。 |
| 作者复用 | 场景克隆、场景模板、已验证版本、依赖清单、不可变模板引用和发布版本。 | 场景/发布层。 | 两个比赛选用同一发布版本，互不覆盖拓扑和运行资源。 |
| 管理员准备 | 节点能力、容量、镜像可用性、分发进度、等待原因和失败诊断。 | 底座运行面。 | 3 支队伍并发准备时不超卖；同一制品只按需要分发；重启后仍能恢复真实进度。 |
| 比赛运行 | 队伍隔离、入口、暂停/恢复/重置/销毁、单资产显式重建、运行事件和资源回收。 | 底座运行面 + 上层比赛绑定。 | 三队环境独立运行；并发操作收敛；销毁不误删仍被其它运行引用的缓存。 |
| 运维人员 | 经授权访问指定队伍的 SSH/RDP/容器终端，查看资产、日志、流量、PCAP、会话和操作历史。 | 底座访问/观测面。 | 会话可创建、可撤销、超时回收并留审计；无权/暂停/销毁状态均给出准确中文原因。 |
| 选手 | 只访问自己的入口和题目所需服务；不看到运维、模板、内部地址、其他队伍流量或凭据。 | 上层比赛 + 底座权限投影。 | 选手 token 枚举所有公开 API 也不能跨队读取或创建运维会话。 |
| 设备包作者 | 登记协议/工艺/网络设备包的版本、端口、参数、资源需求、健康检查和可观测声明。 | 模板/设备包目录。 | 新设备包不改 TeamLab 控制器代码即可被选择、部署、健康检查并上报事件。 |
| 现场管理员 | 登记真实设备或受控网络/串口连接器，授权给场景、查看占用、断连、释放和审计。 | 现场连接器 + 资源池。 | 一个连接器被同一时刻第二个运行申请时稳定拒绝；回收后才能复用。 |

### 12.2 平台、模板、场景和现场连接器的最终职责

| 内容 | 平台底座 | 模板/设备包 | 场景 | 现场连接器 |
| --- | --- | --- | --- | --- |
| 制品形成与认证 | 只接收外部产出的不可变制品和认证清单，校验摘要/签名并登记；不创建构建任务，不启动来宾做模板改造或认证。 | 外部制品流水线负责制作、驱动、系统优化、泛化、功能认证和版本发布。 | 只选择已登记版本，不参与制品制作。 | 适配程序同样由外部构建和验证，平台只登记可用版本。 |
| 网络与调度 | 地址、路由、隔离、跨节点 Fabric、容量、队列、暂停/恢复/销毁。 | 只声明网卡/端口/资源需求。 | 选择网段、连线和资产关系。 | 把获批物理接口映射到分配的运行时。 |
| 软件与协议 | 不安装/不解释 AD、PLC、工业软件或协议业务。 | 提供服务、协议、点位、健康检查和可选事件。 | 填写包公开参数，选择版本。 | 实现厂商协议、串口/网卡/设备驱动适配。 |
| 安全 | 对象授权、操作幂等、审计、密钥保护、网络分段。 | 不携带平台机密。 | 不保存现场地址、驱动口令或平台凭据。 | 只接触已分配的物理端口，不能作为通用跳板。 |
| 可观测 | 流量元数据、PCAP、运行事件、统一查询和留存。 | 上报脱敏协议/工艺事件。 | 选择可用观测策略。 | 上报连接器健康和受控设备状态。 |

### 12.3 建议的实施阶段

| 阶段 | 只做什么 | 不做什么 | 通过标准 |
| --- | --- | --- | --- |
| P0：把现有主线验收做实 | 修复并验收设计、发布、自动准备、试运行、正式比赛、运维会话、流量/PCAP、暂停恢复和清理。 | 不添加协议仿真、3D、现场设备或第二套队列。 | 3 队混合 Docker/Linux VM/Windows VM 场景全链路稳定通过。 |
| P1：资源池与可用性投影 | 节点/镜像/设备/连接器的可用、占用、预约、错误和释放状态；统一 operation 进度。 | 不把原始 libvirt/Docker 命令暴露给前端。 | 并发准备、重复提交、中断重启和销毁重建均无超卖、悬挂或误删。 |
| P2：链路能力与观测关联 | 链路级性能/断连操作、桥接采集点、PCAP、流量元数据和事件时间线。 | 不承诺未解析协议字段，也不从来宾强制安装代理。 | 能解释并检索跨资产路径、筛选条件和 PCAP 对应的同一时间段。 |
| P3：设备包目录 | 设备包描述、版本、参数 schema、端口、健康检查、事件声明和 OCI 制品引用。 | 不在 TeamLab 写 Modbus/S7/PLC/工艺逻辑。 | 至少一个真实协议设备包与 Docker/VM 混合多队运行，事件和报文可关联。 |
| P4：现场连接器 | 受管物理端口/网段/串口登记、授权、独占锁、健康和审计。 | 不提供任意内网桥接或任意串口转发。 | 模拟和真实设备走同一运行/权限/观测模型，失联和回收可解释。 |
| P5：规模与灾难验收 | 容量压测、队伍批量创建/暂停/恢复/销毁、节点短暂失联、控制面重启与恢复。 | 不用无限重试和延长等待伪造稳定性。 | 资源账实一致、错误可恢复、操作审计完整且无残留。 |

### 12.4 外部控制面目标接口

以下是对外应达到的对象面，采用现有 `/api/open/v1` 契约风格，而不是把平台 B 的原始 Docker/PVE 接口复制出来。这里是路线要求，实际已交付接口仍以当前 OpenAPI 为准。

## 15. 高性能专项的目标和责任边界

本专项研究的是 TeamLab 底座如何在大量队伍、多个物理节点和混合 Docker/VM 场景下更快、更稳地完成准备、启动、暂停、恢复、重置和销毁。优化对象是平台控制面、网络数据面、制品分发、宿主机执行和状态观测，不把镜像制作工作放进主站或 Agent。

模板责任边界固定如下：

- 模板由平台外部的管理员或独立制品流水线制作、安装驱动、优化系统、泛化并完成质量验证。
- 平台只登记已经完成的不可变制品及外部认证清单，校验摘要和签名，记录资源需求与已声明能力，并将制品预分发到执行节点。
- 平台不提供模板构建任务，也不通过启动 VM、探测来宾或执行脚本替外部流水线认证模板；节点只验证收到的字节与已登记摘要一致。
- 主站、Agent 和运行时不执行 Packer、系统安装、驱动安装、Sysprep、AD 提升、工控软件安装或未知镜像在线改造。
- Linux/Windows 的开机速度、来宾服务启动和驱动质量属于模板质量；平台必须把自身的调度、网络、磁盘克隆和启动调用开销压到稳定上限，但不能用延长等待掩盖模板问题。

目标规模采用商业化总纲的 300-500 支队伍在线基线，并额外覆盖每队 20 个资产的常用场景和每队 50 个资产的大型场景。最终容量必须由目标硬件实测确认，本文不给未执行的吞吐数据填估算值。

## 16. 当前实现的真实性能基线

### 16.1 已经具备且应保留的能力

| 能力 | 当前事实 | 结论 |
| --- | --- | --- |
| 统一调度 | `DeploymentQueueTicket` 是运行任务事实；调度和长耗时执行已分为独立 Worker。 | 架构方向正确，不新增第二套队列。 |
| 原子容量 | TeamLab 多分片容量在统一容量账本中预留，Docker 与 KVM 能力独立判断。 | 保留，继续补目标硬件容量验收。 |
| 并行执行 | 镜像准备与网络应用并行；依赖图同一就绪批次通过 `Task.WhenAll` 并行创建。 | 不重写依赖图，只优化节点执行和数据面。 |
| 分发去重 | 镜像分发已有异步 Worker、节点内限流和同制品 single-flight。 | 保留，但把“比赛启动时兜底传输”进一步收敛为异常路径。 |
| 轻量磁盘克隆 | VM 已使用 `qemu-img create -b` 创建写时复制 overlay。 | 正确，启动时不应复制完整系统盘。 |
| 部分事件驱动 | 受控 VM 使用运行信号等待网络和观测就绪，libvirt 关机已有生命周期事件等待。 | 扩展到完整生命周期，减少轮询。 |
| 并行清理 | TeamLab 按分片并行清理，并在事实核对后释放容量。 | 保留，优化分片内部批量删除与存储回收。 |

当前开发基准只证明 8 个 WorkerNode、32 个不可拆分网络、128 个 Docker 资产的纯放置算法首次运行 578 ms、第二次 26 ms。300 个并发创建、真实镜像传输、网络应用、VM 启动和销毁仍没有生产容量签收，不能据此宣称整体性能已经达标。

### 16.2 已确认的结构性开销

| 热点 | 当前证据 | 为什么会放大 |
| --- | --- | --- |
| 网络命令进程风暴 | `TeamLabCommandExecutor` 对命令数组逐条启动 `/bin/sh`。单个网段仅 bridge 和 DHCP/DNS 就至少启动 9 个 shell 进程，尚未计算路由、防火墙和 Fabric。 | 大场景和多队并发时，进程创建、文本解析和部分失败清理成为线性开销。 |
| 每网段一个 dnsmasq | 每个运行网段创建独立 hosts、lease、pid、log 和 dnsmasq 进程，并轮询 53/67 端口就绪。 | 300 支队伍、每队 4 个网段时会形成约 1200 个常驻 dnsmasq 进程，运维和回收成本随网段数增长。 |
| VM 生命周期依赖命令行 | VM 创建、查询、暂停、恢复和删除通过 `qemu-img`、`virt-install`、`virsh` 子进程完成；生命周期事件也通过 `virsh event` 子进程读取。 | 每台 VM 多次进程创建并解析文本；断连、语言环境和命令版本会增加不确定性。 |
| Operation 每秒查库 | TeamLab operation handler 每秒查询一次部署票据并回写进度，直到终态。 | 并发 operation 增加时，空转查询和重复进度写入与任务数近似线性增长。 |
| 兼容 VM 主动轮询 | 无来宾信号的 VM 最多执行 120 次 1 秒网络探测；Docker 最多 30 次。 | 这是兼容资产的兜底能力，不应成为所有资产的默认就绪机制。 |
| 启动仍可能等待分发 | 发布准备和预分发能力存在，但运行创建仍保留目标节点缺制品时的兜底等待。 | 大制品在比赛开始时传输会直接进入用户可见启动时间，并形成 Registry 扇出。 |

这些问题不是通过增加重试次数、扩大超时或提高 Worker 数量就能解决。根因分别位于网络数据面、虚拟化控制方式、制品准备时机和状态通知模型。

## 17. 三条技术路线比较

| 路线 | 主要组成 | 性能收益 | 代价与风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 演进现有底座 | 保留 TeamLab API、统一队列和调度；网络切到 OVN/OVS；VM 切到原生 libvirt API；本地 NVMe 制品缓存和 qcow2 overlay；事件驱动状态。 | 直接消除网络 shell/dnsmasq 进程风暴和 VM 命令行往返，保留现有业务模型，迁移面最小。 | 需要一次受控的数据面切换和节点环境升级。 | **推荐主路线**。 |
| B. Kubernetes 全栈 | Kubernetes + KubeVirt + CDI + Multus/OVN-Kubernetes + CSI/Ceph。 | 获得成熟的集群调度、控制器、声明式资源和标准运维生态。 | KubeVirt 仍通过 `virt-launcher`、`virt-handler`、libvirt/QEMU 启动 VM，不能直接缩短 Windows 来宾启动；会与现有队列、容量、权限和 operation 重叠，迁移量最大。 | 仅在基础设施已统一 Kubernetes、节点规模和运维团队足以承担时作为可插拔 Provider。当前不整体迁移。 |
| C. Incus 集群 | Incus 统一管理系统容器、OCI 应用容器、QEMU VM，可配 OVN 和分布式存储。 | 执行面 API 比直接管理 Docker/libvirt 更统一。 | 仍使用 QEMU；与现有 Docker 语义、镜像分发和 Agent 能力存在迁移成本，Windows/复杂竞赛链路仍要专项认证。 | 可做隔离原型，不作为当前主线。 |

### 17.1 为什么不把“上 Kubernetes”直接等同于高性能

KubeVirt 官方架构明确说明：VM 对象由控制器调度，节点上的 `virt-handler` 配合 kubelet 启动 `virt-launcher` Pod，并继续使用 libvirt/QEMU。它解决的是 Kubernetes 统一管理和调度，不会消除 QEMU 启动、系统开机、镜像分发和复杂网络配置成本。

Kubernetes 路线在以下条件同时成立时才值得进入正式选型：

1. 物理节点数量和业务种类已经要求统一集群运维、滚动升级和自动节点替换。
2. 运维团队已经具备 Kubernetes、KubeVirt、CNI、CSI 和分布式存储生产经验。
3. 实测证明现有调度/Agent 架构无法达到容量目标，而瓶颈确实位于集群控制而非来宾启动或存储。
4. TeamLab 对外 API、权限、operation 和审计保持不变，Kubernetes 只作为执行 Provider，不能让外部平台直接操作 Pod、VMI 或 CNI。

### 17.2 Firecracker、Kata 和轻量 VM 的适用边界

Firecracker 官方规格对受控 Linux microVM 给出 VMM 内存开销不高于 5 MiB、从 `InstanceStart` 到 Linux `/sbin/init` 开始不高于 125 ms 的持续集成目标。这个结果依赖极简 Linux 内核和 rootfs，适合短时 Linux 服务或函数，不支持 TeamLab 所需的通用 Windows、任意设备模型和现有第三方虚拟机模板。

因此 Firecracker/Kata 只能作为未来可选的 `LinuxMicroVm` 执行类型，不能替代 KVM/libvirt 主路径。没有明确的大量短时 Linux microVM 需求前，不引入第二个 VM 后端。

## 18. 推荐的高性能执行架构

### 18.1 控制面保持简单

外部平台继续只调用版本化 TeamLab API。主站负责权限、场景发布、放置、容量、operation 和审计；PostgreSQL 保存唯一事实，Redis 只负责唤醒和短期协调。高性能改造不新增消息队列、不新增第二套运行状态机，也不让外部调用方或业务 Controller 直接访问 OVN、Docker、libvirt 或 Agent。

一次运行创建按以下顺序执行：

1. 主站在一个事务内完成发布版本确认、容量预留、分片放置和 generation 围栏。
2. 确认所有目标节点已经拥有所需不可变制品；正常比赛路径不传输镜像。
3. 网络 Provider 在一个 OVN Northbound 事务内提交逻辑交换机、路由器、端口、DHCP、DNS、ACL 和观测端口。
4. 等待 OVN 的配置版本从 northbound 收敛到各 chassis，而不是固定 sleep。
5. 每个节点按有界并发创建本地 qcow2 overlay、定义/启动 VM，并通过 Docker API 创建容器；不同节点并行。
6. Docker 事件、libvirt 生命周期事件、DHCP/邻居事件和受控来宾信号推进资产状态；只对没有来宾信号的兼容资产执行声明式端口健康探测。
7. 全部必要资产到达可用状态后开放玩家入口。观测、运维和非必要资产不能阻塞基础网络就绪。

### 18.2 网络数据面：OVN/OVS

建议将当前“Linux bridge + router namespace + 每网段 dnsmasq + shell 路由/防火墙”替换为 OVN/OVS Provider：

- 画布交换机映射为 OVN logical switch，平台路由器映射为 logical router，资产网卡映射为 logical switch port。
- DHCP 和 DNS 使用 OVN 的逻辑 DHCP/DNS 表，不再为每个网段常驻一个 dnsmasq 进程。
- ACL、QoS、端口镜像和流量导出使用 OVS/OVN 数据面能力，不为每条规则启动 shell。
- 跨节点使用 Geneve/VXLAN 逻辑隧道；节点间底层连通和加密属于常驻集群 underlay，不随每个队伍环境重复创建。
- 玩家 WireGuard 入口与跨节点 Fabric 分离。WireGuard 只负责授权入口和必要的节点间加密，不承担场景内部交换/路由状态机。
- OVN Northbound 事务作为网络期望状态提交点；`nb_cfg/hv_cfg` 或等价 chassis 收敛事实作为“网络已生效”的证据。
- OVS integration bridge 采用 fail-secure；控制面短时不可用时，已下发流表继续转发，新变更暂停并明确报错。

这条路线与 TeamLab 的交换机、路由器、网段和端口模型直接对应，也能承载队伍间地址重叠。Cilium 原生路由适合唯一 Pod CIDR；TeamLab 需要大量重复 RFC1918 地址和显式虚拟拓扑，因此不能简单用主机路由表替代逻辑网络。Cilium 官方也明确说明 VXLAN/Geneve 封装会降低有效 MTU和单连接最大吞吐，实际部署必须统一 MTU；有条件时使用 9000 MTU underlay，不能靠默认值猜测。

### 18.3 VM 执行：原生 libvirt 事件与写时复制

- 保留 KVM/QEMU 和外部制作的通用 Linux/Windows 模板，避免破坏系统兼容性。
- 保留本地不可变 base image + 每实例 qcow2 backing overlay；QEMU 官方说明这种 overlay 只记录与 base 的差异，创建时无需复制完整镜像。
- Agent 新增窄接口的 libvirt 原生适配器，直接定义、启动、暂停、恢复、查询和删除 domain，并订阅 domain/agent/block-job 事件；切换完成后删除 `virt-install`/`virsh` 文本编排主路径，不永久保留双轨。
- Windows 使用哪种网卡和磁盘设备由外部模板的认证能力决定。已声明具备 VirtIO 驱动的模板使用 virtio；未声明的模板使用兼容设备。服务端不安装驱动，也不按 Windows 版本写分支。
- CPU pinning、hugepages、专用 I/O thread 只作为经过基准证明的高性能规格，不默认启用；默认启用会降低密度并增加调度碎片。
- 来宾系统启动时间单独统计。平台开销从“容量已分配”到“QEMU 已启动”统计，不能把 Windows 开机时间混入控制面开销，也不能排除在最终用户 SLO 之外。

### 18.4 制品与存储：比赛前完成分发

默认小中型集群采用本地 NVMe 内容寻址缓存：

- 外部流水线产出并认证不可变 Docker/VM 制品和能力清单；平台只登记 digest、签名、大小、资源需求和已认证能力，不负责构建或认证模板。
- 场景发布或比赛绑定后计算所需制品集合，并按可调度节点提前分发；正式开启前形成“所需副本数已就绪”的硬门禁。
- 调度优先选择已经具备全部制品的节点；比赛启动时发生传输视为准备未完成，进入明确的准备状态，不占用 VM/容器创建通道。
- base image 被活动发布版本或运行时引用时禁止淘汰；overlay 只引用本机已验证的 digest 路径。
- 销毁实例只删除轻量 overlay 和运行资源，不删除仍被发布版本或其他运行时引用的 base cache。

可选扩展按实测瓶颈启用：

| 扩展 | 启用条件 | 不默认启用的原因 |
| --- | --- | --- |
| Dragonfly P2P 预热 | Registry 在多节点并发预分发时成为明确带宽瓶颈。 | 当前分发已有 single-flight；小集群增加 P2P 组件收益有限。 |
| Ceph RBD 克隆 | 需要跨节点共享 VM 存储、快速故障迁移，并具备至少 3 个存储节点和独立高速存储网络。 | Ceph 提升共享和快速 COW 克隆，但引入存储集群运维；本地 NVMe 通常有更低启动 I/O 延迟。 |
| eStargz/Nydus 懒加载 | 开发/临时环境确实受容器冷拉取影响，且 Registry 在运行期始终可靠。 | 官方资料说明懒加载会把部分读取延迟转移到运行期；Docker 主路径本身不支持 eStargz 懒拉取。正式比赛更应完整预热。 |

Ceph 官方明确说明 RBD snapshot layering 能快速创建大量 COW VM 克隆，同时提醒删除是异步的、flatten 成本随镜像大小增长。因此使用 Ceph 时，运行销毁和物理空间回收必须是两个状态，不能在对象进入回收队列时立即虚报磁盘已经释放。

### 18.5 暂停、恢复和销毁

暂停/恢复按节点批量下发，而不是主站逐资产串行往返：

- 暂停前关闭玩家和运维入口，随后并行 pause Docker、suspend VM；网络、地址、overlay 和容量事实保持不变。
- 恢复只恢复计算资源和入口，不重新分发制品、不重建网络、不重新分配地址。
- 同一 runtime/generation 只允许一个互斥的生命周期目标，`pause`、`resume`、`reset`、`destroy` 冲突在 admission 阶段拒绝。

销毁采用“先隔离、后回收、再核对”的节点级计划：

1. generation 墓碑先阻止新连接和迟到的 create。
2. 各节点有界并行停止容器、VM、抓包和访问会话。
3. OVN 在一个事务中删除该 runtime 的逻辑端口、交换机、路由器和策略。
4. overlay 使用原子 rename/unlink 或存储 Provider 的 trash 机制快速退出运行路径，物理回收异步执行。
5. Agent inventory、OVN 期望状态和容量账本全部确认不存在该 generation 后，operation 才进入 Succeeded。

重试不是正确性的来源。中断恢复依赖 generation 围栏、不可变 digest、数据库期望状态、节点 inventory 和 OVN/libvirt/Docker 事件；重新执行只允许重放同一个期望状态，不创建新的身份或猜测上一次是否成功。

### 18.6 状态通知和管理性能

- `DeploymentQueueTicket` 终态通过现有生命周期 observer/wakeup 通知 TeamLab operation，替代每个 operation 每秒查询并重复写进度。
- PostgreSQL 仍是状态事实；Redis 或进程内事件只负责唤醒。通知丢失时使用低频、有界 reconciliation 扫描恢复，不让高频轮询成为正常路径。
- Docker 使用 Engine event stream，libvirt 使用 domain/agent lifecycle callback，网络使用 OVN 配置版本，镜像使用分发进度事件。
- 前端和外部平台通过 operation/event 游标读取真实阶段；状态变化不得要求用户刷新，也不为每个资产建立单独轮询。
- 节点 inventory、运行状态和观测元数据采用批量快照/增量事件，禁止运行列表按资产扇出调用 Agent。

## 19. 稳定性设计原则

| 原则 | 正确性来源 | 禁止做法 |
| --- | --- | --- |
| 先校验再执行 | 发布版本、模板能力、节点容量、制品副本和网络地址在 admission 前冻结。 | 启动后才发现模板、磁盘或网段不满足。 |
| 原子身份与容量 | operation ID、runtime ID、generation、节点放置和容量预留在数据库事务内形成。 | Agent 自行创建业务身份或主站先调用后补记录。 |
| 期望/事实双核对 | 期望状态来自数据库/OVN；事实来自 Agent inventory、libvirt、Docker 和 OVS。 | 只看命令返回 0 或日志文字就标记成功。 |
| 单调 generation 围栏 | 旧 generation 永远不能修改或删除新 generation 资源。 | 依赖名称相同、超时或重试次数判断资源归属。 |
| 事件驱动 | 生命周期事件推动状态，deadline 只负责判定未完成。 | 固定 sleep 后假设成功，或无限轮询直到碰巧成功。 |
| 明确失败分类 | 校验失败、容量不足、制品缺失、节点离线、网络未收敛、来宾未就绪分别返回稳定错误。 | 所有失败都自动重试或统一写成“超时”。 |
| 数据面独立 | 控制面短时中断不破坏已运行网络和 VM/容器。 | 主站进程存活成为转发链路的一部分。 |
| 有界并发 | Docker、VM、网络、分发、探测和销毁分别限流，限流由节点能力声明。 | 一个全局锁把节点压成串行，或无限并发把磁盘/CPU 打满。 |

## 20. 性能目标与验收矩阵

以下是设计验收目标，不是当前已达成结果。所有时间同时记录 p50、p95、p99，冷启动和预热启动必须分开。

| 指标 | 候选验收目标 | 统计边界 |
| --- | --- | --- |
| 调度 | 300 个 create ticket 的 planning/claim 总批次不超过 5 秒；有容量任务 enqueue 到 Scheduled p95 不超过 2 秒。 | 不包含制品传输和来宾开机。 |
| 正常启动制品传输 | 0 字节。 | 发布/比赛准备已经完成的正式运行。 |
| 网络应用 | 4 网段/20 端口 p95 不超过 2 秒；8 网段/50 端口 p95 不超过 5 秒。 | 从 OVN 事务提交到目标 chassis 收敛。 |
| Docker | 已预热镜像从 create 到健康 p95 不超过 5 秒。 | 包含容器进程健康检查。 |
| Linux VM 平台开销 | overlay 创建、domain 定义和 QEMU 启动 p95 不超过 5 秒；受控模板最终就绪 p95 不超过 60 秒。 | 分开记录平台与来宾时间。 |
| Windows VM 平台开销 | 平台部分 p95 不超过 5 秒；由外部完成并认证的模板最终就绪 p95 不超过 120 秒。 | 不通过在线改造或延长超时达成。 |
| 混合运行时 | 20 资产常用场景 p95 不超过 120 秒；50 资产大型场景 p95 不超过 180 秒。 | 制品已预热，包含 Docker/Linux/Windows 和多网段。 |
| 暂停/恢复 | 20 资产 p95 分别不超过 10 秒；恢复不产生镜像传输和网络重建。 | 从操作受理到所有必要资产收敛。 |
| 销毁 | 2 秒内关闭入口；20 资产计算资源 p95 30 秒内消失；网络与访问资源 p95 60 秒内核对完成。 | 存储物理回收可异步，但容量事实不能提前虚报。 |
| 跨节点网络 | 相对同硬件 host baseline，吞吐损失不高于 15%，额外 p99 时延不高于 2 ms；无丢包和跨队泄漏。 | 分别测 1500/9000 MTU、单流和多流。 |
| 控制面故障 | 主站/Redis 短时中断不影响已运行数据面；恢复后 10 秒内重新取得待处理 operation。 | PostgreSQL 和节点仍可用。 |
| 资源一致性 | 并发创建/销毁/重置、Worker 中断和节点短时失联后，重复实例、容量超卖和跨 generation 误删均为 0。 | 以数据库、OVN、libvirt、Docker、文件和端口 inventory 交叉核对。 |

测试场景固定为三档：

- S：4 个资产、2 个网段，用于单次延迟和回归。
- M：20 个资产、4 个网段，用于 50/100 支队伍并发和比赛常用容量。
- L：50 个资产、8 个网段，用于大型工控/综合场景和销毁压力。

每档覆盖 Docker、Linux VM、Windows VM、交换机、路由器、跨节点连通、流量观测和管理员运维。性能报告必须同时给出 CPU、内存、磁盘 IOPS/延迟、网络吞吐、Registry 流量、OVN 收敛、数据库锁等待和 Agent 各类别并发，防止只看总耗时而误判根因。

## 21. 推荐实施顺序与退出条件

### HP0：建立真实基线

- 在不改数据面的情况下为网络 apply、制品准备、overlay、domain start、来宾 ready、暂停/恢复和销毁建立统一时间戳。
- 在目标节点执行 S/M/L 单队、10 队、50 队基准，定位 CPU、磁盘、网络或数据库的主导瓶颈。
- 退出条件：每段耗时和资源曲线可复现；没有“总共慢”但不知道慢在哪里的结论。

### HP1：把启动路径收敛为零传输

- 将发布/比赛准备变成正式硬门禁，按预计并发和可调度节点准备制品副本。
- 完善节点本地内容寻址缓存、引用保护和淘汰策略。
- 用事件唤醒 operation，删除正常路径每秒票据轮询和重复进度写入。
- 退出条件：正式运行启动期间 Registry 传输为 0；主站重启后准备事实可恢复。

### HP2：原生 VM 生命周期

- 先建立 `IVirtualizationExecutionPort`，在隔离节点验证 libvirt 原生 define/start/event/pause/resume/destroy 和 inventory。
- 通过 Linux/Windows、多网卡、UEFI/NVRAM、重置和中断清理后切换 Agent；切换完成删除命令行主路径，不永久双轨。
- 退出条件：VM 平台开销达到目标，生命周期不靠 `virsh event` 子进程和文本解析。

### HP3：OVN/OVS 数据面

- 先实现独立 `INetworkExecutionProvider` 和拓扑到 OVN 模型的确定性编译，不改变外部 API。
- 在隔离 WorkerNode 验证重叠地址、多网段路由、DHCP/DNS、ACL、MTU、WireGuard 入口、流量镜像和控制面中断。
- 完成同一场景在旧/新数据面的离线结果对照后一次性切换；旧 bridge/router namespace/dnsmasq 主路径随后删除。
- 退出条件：S/M/L 网络收敛、吞吐、隔离、观测和残留检查全部通过。

### HP4：按证据启用分布式扩展

- Registry 扇出超标才引入 Dragonfly；共享存储/故障迁移成为明确需求且具备合格硬件后才引入 Ceph RBD。
- Kubernetes/KubeVirt 只实现为外部执行 Provider 试点，不改 TeamLab 对外契约，也不与现有调度同时拥有同一资源。
- 退出条件：每个新增组件都消除一个已量化瓶颈，并有独立故障、升级和回滚手册；没有收益证据的组件不进入生产。

### HP5：商业容量签收

- 500 支队伍在线、300 个并发 create、50/100 支队伍 M 场景批量启动和销毁。
- 注入主站中断、Redis 中断、OVN 控制面短时中断、单 Worker 离线、Registry 不可达和存储变慢。
- 退出条件：达到第 20 节 SLO，账实一致、无跨队泄漏、无重复实例、无无限等待、无未归属残留。

## 22. 高性能专项来源与证据

| 来源 | 采用的事实 | 设计影响 |
| --- | --- | --- |
| 当前 `TeamLabCommandExecutor`、`TeamLabBridgeService`、`TeamLabNetworkService` | 网络命令逐条 shell 执行、每网段独立 dnsmasq。 | 证明数据面需要事务化 Provider，而不是增加重试。 |
| 当前 `KvmService`、`AgentTeamLabNodeExecutor` | VM 通过 qemu-img/virt-install/virsh 管理；受控 VM 有事件信号，兼容 VM 使用探测。 | 保留 KVM 和事件信号，切换原生 libvirt 生命周期。 |
| 当前 `TeamLabShardDeploymentService`、`TeamLabRuntimeCleanupService` | 镜像/网络、依赖批次和分片清理已经并行。 | 不重写正确并行结构，聚焦节点执行与数据面。 |
| [OVN 架构官方文档](https://www.ovn.org/support/dist-docs/ovn-architecture.7.html) | logical switch/router、OVS integration bridge、隧道端口、VIF 接入和 `nb_cfg/hv_cfg` 收敛。 | 作为复杂隔离拓扑的首选网络 Provider。 |
| [KubeVirt 架构](https://kubevirt.io/user-guide/architecture/) 与 [Clone API](https://kubevirt.io/user-guide/storage/clone_api/) | VM 由 Kubernetes 控制器、virt-handler、virt-launcher、libvirt/QEMU 管理；克隆依赖快照/恢复。 | K8s 是管理方案，不是 Windows 快速开机捷径。 |
| [QEMU qemu-img 官方文档](https://www.qemu.org/docs/master/tools/qemu-img.html) | backing image overlay 只记录差异，base 不被修改。 | 保留本地不可变 base + 轻量 overlay。 |
| [Ceph RBD snapshot/layering](https://docs.ceph.com/en/latest/rbd/rbd-snapshot/) | 快速 COW 克隆、异步删除、flatten 成本和父子引用。 | Ceph 只作为需要共享存储时的可选 Provider。 |
| [Firecracker 官方规格](https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md) | 受控极简 Linux microVM 的 5 MiB VMM 开销和 125 ms 启动目标。 | 仅证明 Linux microVM 专用路径潜力，不用于 Windows/通用模板承诺。 |
| [Dragonfly 官方仓库](https://github.com/dragonflyoss/dragonfly) | P2P 分发文件、容器镜像和 OCI artifact，并支持内容寻址加速。 | Registry 扇出成为实测瓶颈后再引入。 |
| [stargz snapshotter 官方仓库](https://github.com/containerd/stargz-snapshotter) | 懒拉取按需读取，存在运行期读取代价，Docker 主路径不支持懒拉取。 | 正式比赛优先完整预热，不把懒拉取当稳定性方案。 |
| [Cilium routing 官方文档](https://docs.cilium.io/en/stable/network/concepts/routing/) | VXLAN/Geneve 封装、MTU 开销和 native routing 边界。 | 明确 overlay MTU 与吞吐验收，不盲目宣称封装无成本。 |
| [Incus instance 官方文档](https://linuxcontainers.org/incus/docs/main/explanation/instances/) | 同时支持系统容器、OCI 应用容器和 QEMU VM。 | 作为替代执行面的研究对象，不直接替换当前主线。 |

本专项的推荐结论是：先让运行时真正做到“零传输启动”，再以 OVN/OVS 和原生 libvirt 消除重复进程与文本控制，把事件和 inventory 作为稳定性事实；Kubernetes、Ceph、Dragonfly 和 Firecracker 都必须由明确瓶颈触发，不能因为名气或理论扩展性直接堆入生产。
