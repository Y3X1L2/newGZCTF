# YINYU AWDP 手工验收指南

## 1. 目的与范围

本文用于测试人员在浏览器中完整验收 AWDP 赛制，覆盖：建赛、服务配置、双队报名、启动、攻击、修补、重置、恢复、榜单、日志和停止清理。

本流程必须使用隐藏的临时测试比赛，不得在正在使用的正式比赛上执行。测试过程中记录比赛 ID、队伍 ID、实例 ID、各阶段时间和异常截图。

## 2. 测试前准备

### 2.1 账号与队伍

准备三个浏览器会话，或使用三个互相隔离的浏览器配置文件：

| 会话 | 角色 | 用途 |
| --- | --- | --- |
| 管理端 | 管理员或超级管理员 | 建赛、配置服务、启停和观察全局状态 |
| 选手 A | 临时学生账号、临时队伍 A | 攻击、修补、重置和恢复 |
| 选手 B | 临时学生账号、临时队伍 B | 提供被攻击实例并核对独立环境 |

账号和队伍名称统一使用 `AWDP-ACCEPT-日期-序号` 前缀，便于测试后检索和删除。不得使用现有教师、学员或正式队伍。

### 2.2 服务素材

使用已在平台验证过的 AWDP Docker 镜像、Checker 和 EXP。当前测试环境可在现有 AWDP 测试比赛的服务管理页中查看并复制一套已知可用配置，不要临时使用未知镜像。

建议参数：

| 字段 | 建议值 |
| --- | --- |
| 服务名 | `AWDP-ACCEPT-SERVICE` |
| 暴露端口 | 镜像实际监听端口，例如 `9999` |
| 原始分 | `1000` |
| 攻击得分 | `50` |
| SLA 得分 | `20` |
| 修补得分 | `100` |
| 服务异常扣分 | `200` |
| 每轮最大攻击次数 | `3` |
| 攻击阶段 | `5` 分钟 |
| 修补阶段 | `5` 分钟 |
| 总轮数 | `1` |
| 最大重置次数 | `2` |
| 最大恢复次数 | `2` |

五分钟阶段便于人工观察，不建议为了加快测试改成一分钟，否则部署、获取 Flag 和上传补丁容易跨阶段。

### 2.3 补丁包

准备一个 `.tgz` 或 `.tar.gz` 文件，归档根目录必须包含可执行逻辑正确的 `update.sh`：

```text
awdp-patch.tgz
└── update.sh
```

补丁需要同时满足：

1. `update.sh` 在容器内执行成功。
2. 原 Checker 仍返回正常，业务服务没有被破坏。
3. 原 EXP 无法再获得 Flag。

只让服务停止或让 Checker 失败不算修补成功，会触发服务异常或修补失败判定。

## 3. 创建临时 AWDP 比赛

1. 管理员登录平台，进入“比赛管理”。
2. 点击“创建比赛”。
3. 比赛名称填写 `AWDP-ACCEPT-日期-序号`。
4. 赛制选择 `AWDP`，勾选“隐藏”和“测试比赛”。
5. 开始时间设为当前时间前 2 分钟，结束时间至少晚于当前时间 30 分钟。
6. 报名审核可设为自动通过；若选择人工审核，后续必须在报名管理中批准 A、B 两队。
7. 保存并记录生成的比赛 ID。
8. 进入该比赛的“AWDP 服务”页面，添加 2.2 节准备的服务配置。

预期：

- 比赛详情显示 AWDP 赛制。
- 服务列表能重新打开并完整显示镜像、端口、Checker、EXP、计分和轮次参数。
- 刷新页面后服务不会消失。

异常判据：

- 保存后赛制变为 CTF、Theory 或其他类型。
- 服务保存后缺少镜像、脚本或轮次参数。
- 刷新页面后配置丢失或出现 500。

## 4. 双队报名与权限隔离

1. 选手 A 登录，进入临时比赛并使用队伍 A 报名。
2. 选手 B 登录，进入临时比赛并使用队伍 B 报名。
3. 若需要审核，管理员在比赛报名页通过两队。
4. A、B 分别刷新比赛详情并进入 AWDP 页面。

预期：

- 两队均显示报名已通过并能进入 AWDP 工作区。
- A、B 不能操作对方的重置、恢复和补丁上传。
- 管理员能看到两个队伍，选手端不得出现管理比赛、修改服务或停止比赛按钮。

异常判据：

- 未批准队伍也能进入或操作实例。
- A 可以重置、恢复或修补 B 的实例。
- 普通选手能修改服务配置或启停比赛。

## 5. 启动与攻击阶段

1. 管理员在 AWDP 服务管理页点击“启动比赛”。
2. 管理端观察状态，等待两个队伍的服务实例都变为运行中。
3. 选手 A、B 刷新 AWDP 页面，记录阶段、剩余时间、实例入口和操作次数。
4. 从队伍 A 按题目既定方式攻击队伍 B 服务，取得 B 当前轮 Flag。
5. A 在 AWDP Flag 提交区提交 B 的 Flag。
6. 再次提交同一个 Flag，并尝试提交 A 自己的 Flag。
7. 查看 AWDP 榜单和攻击日志。

预期：

- 启动后状态为“攻击阶段”，轮次为第 1 轮，倒计时持续递减且刷新后不重置。
- 每队每个服务只有一个独立实例，实例入口可访问，Checker 在合理等待后显示正常。
- A 必须能够获得其他队伍服务的可达入口；如果页面只显示自己的入口且没有其他发现方式，应记录为流程阻塞缺陷。
- 首次提交 B 的有效 Flag 返回成功，A 增加配置的攻击分。
- 重复 Flag、无效 Flag、自身 Flag 均被拒绝，不增加分数。
- 攻击日志记录攻击队、被攻击队、服务名、时间和分值。

异常判据：

- 平台显示实例运行，但入口不可访问。
- 两队共用同一容器、同一 Flag，或一队操作影响另一队。
- Flag 判定成功但榜单不加分，或重复提交重复加分。
- 攻击日志缺少攻击方、被攻击方或服务信息。

## 6. 重置与恢复

在攻击阶段或平台允许操作的阶段，由选手 A 对自己的实例执行：

1. 点击“重置”，确认操作。
2. 等待实例重新运行，验证入口、Checker 和当前轮 Flag 可用。
3. 记录剩余重置次数是否减少 1。
4. 点击“恢复”，确认操作。
5. 等待实例重新运行，再次验证入口和 Checker。
6. 记录剩余恢复次数是否减少 1。

当前后端两种操作都会基于原始服务镜像重建容器并保留当前轮 Flag；区别主要是独立的次数额度和审计记录。“恢复”不是浏览器刷新，也不是仅重启进程。

预期：

- 操作只影响 A 自己的实例。
- 每次重建后入口可重新访问，Flag 仍属于当前轮和当前队伍。
- 重置与恢复分别扣减自己的计数，不能超过配置上限。
- 已应用的补丁状态在重建原始镜像后失效，页面状态与真实实例一致。

异常判据：

- 操作导致 B 的实例中断。
- 次数未扣减、扣错类型或刷新后恢复。
- 操作成功但旧容器仍残留，或新实例一直处于创建中。
- 重建后使用了其他队伍 Flag。

## 7. 修补阶段

1. 等待倒计时自然进入“修补阶段”，不要修改系统时间。
2. 选手 A 选择对应服务并上传准备好的 `.tgz`。
3. 等待平台执行 `update.sh`、Checker 和 EXP。
4. 查看修补结果、服务状态、补丁记录和榜单。
5. 在修补阶段尝试提交 Flag，确认平台拒绝。

预期：

- 阶段自动从攻击切换为修补，前后端显示一致。
- 合法归档被接收，能看到上传时间、服务和最终状态。
- Checker 正常且 EXP 失败时，状态应表示漏洞已阻断/修补成功，并增加修补分。
- Checker 失败时不能标记为已防守，应显示服务异常或修补失败，并按规则扣分。
- 修补阶段不能提交攻击 Flag。

补充说明：实例页的 Checker 是服务健康检查，不等同于“漏洞是否被阻断”。修补成功的正确组合是“Checker 正常 + EXP 失败”；若页面只显示“部分异常”而补丁记录显示成功，应截图并核对 Checker 详情和 EXP 详情，不能仅凭一个摘要标签判定。

## 8. 结束、历史与清理

1. 检查管理端和选手端榜单是否一致。
2. 检查攻击日志、补丁记录、重置记录、恢复记录和 Checker 状态。
3. 管理员点击“停止比赛”。
4. 刷新管理端和两个选手端。
5. 确认状态为已结束，实例全部停止并释放。
6. 删除临时比赛，再删除临时队伍和临时账号。
7. 在节点/实例/队列管理页搜索测试标记，确认无运行实例和未结束队列。

预期：

- 停止后不再生成新轮次和 Flag，不再执行周期 Checker。
- 历史榜单、攻击日志和补丁结果在比赛删除前可查看。
- 所有容器、端口映射和队列任务最终释放。
- 临时比赛删除后不残留 AWDP 实例、轮次、Flag 或补丁外键记录。

## 9. 测试记录模板

| 项目 | 结果 | 证据/说明 |
| --- | --- | --- |
| 建赛与服务配置 | 通过/失败 | 比赛 ID、服务 ID、截图 |
| 双队报名与权限隔离 | 通过/失败 | 队伍 ID、权限异常 |
| 双队实例创建 | 通过/失败 | 实例 ID、入口、Checker |
| 攻击与 Flag 得分 | 通过/失败 | Flag 提交时间、攻击日志、榜单前后值 |
| 重复/自身/无效 Flag 拒绝 | 通过/失败 | 返回提示截图 |
| 重置 | 通过/失败 | 次数变化、实例重建时间 |
| 恢复 | 通过/失败 | 次数变化、实例重建时间 |
| 修补双验证 | 通过/失败 | Checker、EXP、FinalStatus |
| 修补计分 | 通过/失败 | 榜单前后值 |
| 停止与资源清理 | 通过/失败 | 实例、队列、端口残留检查 |

任一核心步骤失败时，不要反复点击按钮。保留比赛和实例状态，记录时间、账号、队伍、实例、服务、队列 ID 和页面错误，再交由开发人员定位。
