# YINYU vNext Phase 07：通用管理闭环

> 基线：`bbb2173 feat: 完成 vNext 认证与个人主页`
>
> 范围：用户、战队、学员组、系统设置。TeamLab、练习模块和新的后端契约不在本阶段内。

## 1. 阶段目标

本阶段补齐平台正式运营所需的通用管理入口，使管理员无需回退到旧前端或直接调用 API 即可完成以下工作：

1. 查询、创建、编辑、停用、重置密码和删除用户。
2. 查询、编辑、锁定和删除战队。
3. 创建、编辑和归档学员组，维护组内学员与负责教师。
4. 分区维护平台基础信息、账号策略和容器生命周期策略。

完成后，vNext 管理端应形成“业务配置 + 运行资源 + 通用治理 + 系统设置”的基础闭环。

## 2. 设计与架构约束

- 遵循 `yinyu-vnext-design-language-draft.md` 的日间优先、稳定网格、低装饰密度和生产性动效规则。
- 遵循 `frontend-component-boundary.md`：页面只负责路由与编排，SWR 和写操作进入 controller hook，API 调用进入模块适配层。
- 使用现有 `AdminPageHeader`、`MetricStrip`、`FilterToolbar`、`DataTable`、`DetailDrawer`、`VNextDialog` 和 `VNextConfirmDialog`。
- 不引用旧管理页面 DOM、CSS、Mantine 页面壳或历史 `yy-*` 全局样式。
- 不伪造总数、角色、组关系和配置状态；接口没有的数据展示正式空态。
- 桌面端以 1366px 为主要密度基线；390、1920、2560 宽度不得出现页面级横向滚动或文字重叠。
- 危险操作必须说明影响范围；删除用户、删除战队需要输入实体名称确认。

## 3. API 契约

### 3.1 用户管理

| 行为 | 接口 | 说明 |
| --- | --- | --- |
| 分页查询 | `GET /api/admin/users` | 使用 `count`、`skip`、`keyword`、`role`、`groupId` |
| 创建用户 | `POST /api/admin/users` | 当前页面提交单元素数组，保留后端批量能力 |
| 修改用户 | `PUT /api/admin/users/{userId}` | 只提交编辑字段 |
| 重置密码 | `DELETE /api/admin/users/{userId}/password` | 返回一次性随机密码 |
| 删除用户 | `DELETE /api/admin/users/{userId}` | 后端拒绝自删、删除最后一名超管和删除队长 |

角色分配由后端 `RolePolicy` 最终裁决；前端仅按当前管理员角色减少无效选项，不代替权限校验。

### 3.2 战队管理

| 行为 | 接口 | 说明 |
| --- | --- | --- |
| 分页查询 | `GET /api/admin/teams` | 使用 `count`、`skip` |
| 关键字搜索 | `POST /api/admin/teams/search` | 搜索模式最多返回后端允许的结果 |
| 修改与锁定 | `PUT /api/admin/teams/{teamId}` | 名称、简介和锁定状态使用同一接口 |
| 删除战队 | `DELETE /api/admin/teams/{teamId}` | 删除前显示成员数量和名称确认 |

### 3.3 学员组

| 行为 | 接口 | 说明 |
| --- | --- | --- |
| 查询 | `GET /api/admin/student-groups` | 支持关键字及归档记录 |
| 详情 | `GET /api/admin/student-groups/{groupId}` | 返回成员和管理教师 |
| 新建/编辑 | `POST/PUT /api/admin/student-groups` | 名称和说明 |
| 归档 | `DELETE /api/admin/student-groups/{groupId}` | 当前后端是软归档，不称为永久删除 |
| 学员维护 | `POST/DELETE .../members` | 候选用户来自用户查询接口 |
| 教师维护 | `POST/DELETE .../managers` | 仅管理员可维护，候选用户限定教师 |

当前没有取消归档接口。归档记录只读展示，不提供伪恢复按钮，该缺口记录在阶段验收结果中。

### 3.4 系统设置

| 分区 | 字段 | 写入方式 |
| --- | --- | --- |
| 平台身份 | 标题、标语、描述、页脚 | 仅提交 `globalConfig` |
| 账号策略 | 注册、自动激活、验证码、邮件确认、域名列表 | 仅提交 `accountPolicy` |
| 容器策略 | 用户实例上限、默认时长、延期时长、延期窗口、自动清理 | 仅提交 `containerPolicy` |
| 品牌资源 | Logo/Favicon | 使用独立上传和重置接口 |

`apiEncryption` 不在首轮表单中开放。启用该项会触发密钥轮换，必须在后续具备专门运维说明和回滚验证后再提供界面。

## 4. 页面设计

### 4.1 用户管理 `/admin/users`

- 顶部指标：服务器总用户数、当前页已激活、当前页停用、当前页管理员数量。
- 工具栏：关键字、角色、学员组筛选，新建用户。
- 列表：身份、角色、账号状态、实名/学号、所属学员组、最后访问。
- 点击行打开右侧详情抽屉；抽屉内编辑资料、角色、激活状态和学员组。
- 重置密码成功后显示一次性密码和复制按钮，不写入日志或 URL。

### 4.2 战队管理 `/admin/teams`

- 顶部指标：战队总数、当前页开放、当前页锁定、当前页成员数。
- 工具栏：关键字搜索和刷新状态。
- 列表：战队、锁定状态、成员数量、队长、简介。
- 详情抽屉展示成员列表，并可编辑名称、简介和锁定状态。

### 4.3 学员组 `/admin/student-groups`

- 顶部指标：当前可见组、学员数、负责教师数、归档数。
- 工具栏：关键字、是否包含归档、新建学员组。
- 列表：名称、状态、学员数、管理教师数、更新时间。
- 详情抽屉分为基本信息、学员、负责教师三个连续区段。
- 添加人员使用搜索后选择，不一次加载全部用户。

### 4.4 系统设置 `/admin/system`

- 页面不是巨型表单卡片，而是三个独立设置区段和一个品牌资源区段。
- 每个区段独立保存、独立反馈、独立回读。
- 数值字段在前端按后端 DataAnnotation 做范围校验。
- 离开页面不会自动写入；未保存修改通过区段状态提示。

## 6. 验收标准

1. 所有列表具备加载、错误、空态和刷新状态。
2. 查询条件写入 URL，刷新页面后筛选状态可恢复。
3. 写操作成功后从服务器回读，不依赖只改前端内存的假成功状态。
4. 删除、归档、重置密码和 Logo 重置均有明确确认流程。
5. 用户不能从界面删除自己；最终约束仍由后端执行。
6. 系统配置分区提交不覆盖其他分区的最新值。
7. 抽屉拥有单一纵向滚动容器，无水平滚动条，关闭后焦点回到触发元素。
8. 所有新增路由不依赖旧页面视觉类或历史全局 CSS。
