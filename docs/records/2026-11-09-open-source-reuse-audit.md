# 平台开源组件复用审计

审计基线为 `origin/main` 的 `fcb14137`，包含 PR #35。范围为仓库源码、依赖、现行契约和上游官方资料。本文记录代码具备的能力及候选方案，生产接入情况需另行核对。

## 优先决定

先接通管理端概览和节点详情的持久化历史读路径。节点已经上报、缓冲和写入分钟数据，刷新丢失曲线的原因在展示与读取链路。另行用 Prometheus、Grafana 和现成 exporter 建立运维监控。站内管理页继续通过本平台授权读取节点、槽位和调度状态，运维人员在独立入口看主机资源、服务健康、告警与跨系统排障。

## Prometheus 与 Grafana 的渐进接入

1. **P0 · 读回已有历史。** [NodesController](../../src/GZCTF/Controllers/NodesController.cs) 的心跳、Redis live state 与 PostgreSQL fallback 喂给 [NodeMetricPersistenceWorker](../../src/GZCTF/Modules/Runtime/Infrastructure/NodeMetricPersistenceWorker.cs)。该 worker 按 `WorkerNodeId` 与 UTC `ReceivedAt` 分钟写入 `WorkerNodeMetricSamples`，还会持久化节点状态并对账容量预留。[保留策略](../../src/GZCTF/Infrastructure/Persistence/Governance/DataRetentionOptions.cs) 默认 180 天，[索引](../../src/GZCTF/Modules/Runtime/Infrastructure/Persistence/WorkerNodeMetricEntityConfiguration.cs) 支持节点和时间窗读取。沿 Runtime 查询契约提供有管理员授权、时间窗和点数上限的只读 API。站内曲线读分钟数据，实时卡片继续看当前心跳。区分空窗与实际零值，聚合时声明参与节点和口径。验收看刷新后历史仍在、无样本断线、离线节点保留已有历史、未授权请求被拒绝和最大窗口查询受控。
2. **P1 · 用现有指标试点。** 先在测试环境由 Prometheus 抓取主站内网 `MetricPort`，Grafana 按版本管理 datasource 和面板，先覆盖队列积压、Agent 失败率与时延、日志缓冲、应用健康。对照实际导出核对名称、标签、单位和多主站聚合口径，避免把多个主站上报的同一全局 gauge 相加。现有 .NET pull exporter 适合验证，上游生产建议优先稳定的 OTLP。有持续采集需求时可评估现有 OTLP → Collector → Prometheus OTLP HTTP 接收端，明确启用接收、协议和信号路由，同一指标选择一条摄取链。按样本速率和磁盘容量设置保留期，单节点 TSDB 的故障容忍范围需记录。验收包含停采、恢复、缺样和面板查询。[.NET 导出](https://opentelemetry.io/docs/languages/dotnet/exporters/)、[Prometheus OTLP](https://prometheus.io/docs/guides/opentelemetry/)、[存储](https://prometheus.io/docs/prometheus/latest/storage/)、[Grafana 配置](https://grafana.com/docs/grafana/latest/administration/provisioning/)
3. **P1 · 先补主机与外部探测。** `node_exporter`（Apache-2.0）采 Linux 主机 CPU、内存、文件系统和网络，`blackbox_exporter`（Apache-2.0）从指定网络验证固定目标的 HTTP、TCP 等连通性。节点对应关系用配置好的稳定标识。主机 CPU、内存口径要与 Agent 心跳指标区分，连通性、节点在线、可调度和端口映射 ACK 分别展示。控制采集端口访问，并为探测目标设置允许清单。[node_exporter](https://github.com/prometheus/node_exporter)、[blackbox_exporter](https://github.com/prometheus/blackbox_exporter)、[Prometheus 安全模型](https://prometheus.io/docs/operating/security/)
4. **P2 · 根据盲区补组件。** 按需启用 `postgres_exporter`（Apache-2.0）观察数据库端锁和连接，`redis_exporter`（MIT）观察 Redis 服务端内存与命中率，以最小权限的监控账户接入。容器层需要独立用量诊断时试 cAdvisor（Apache-2.0），先评估主机挂载、容器运行时访问权限和短生命周期容器的标签增长。标签优先使用环境、服务、节点和固定状态，排除请求和用户 ID。Flag、Token、私钥、完整命令及 user-data 禁止进入指标与日志导出链路。[PostgreSQL exporter](https://github.com/prometheus-community/postgres_exporter)、[Redis exporter](https://github.com/oliver006/redis_exporter)、[cAdvisor](https://github.com/google/cadvisor)、[cAdvisor 许可](https://github.com/google/cadvisor/blob/master/LICENSE)、[标签规范](https://prometheus.io/docs/practices/naming/)
5. **P2 · 验证告警与日志关联。** 用 Alertmanager 承接先前手册里的可计算规则，优先验证指标消失与真实故障的区分。诊断日志有跨系统检索需求时接 Loki，用 trace/correlation 字段检索并回到平台审计定位业务结果。Grafana 使用独立运维入口和认证。采购或交付前锁定版本，核对镜像、插件和传递依赖的许可证及 NOTICE。Grafana/Loki 修改、再分发或作为网络服务交付时单独复核 AGPL 条件。

Quartz.NET、ELK、Keycloak 与对象存储迁移放在明确痛点出现后。各自用单一场景验证收益、故障模式和回退成本。仓库内暂保留本记录供相关任务决策。

## 验证与交接

本次为源码与上游文档审计，交付物是本记录。文档门禁涵盖文档链接、模块索引、相对 `origin/main` 的文档影响和 Git 差异格式。前后端全量测试及实机采集、告警、部署验收未执行。后续接手先核对持久化历史读路径的实现和测试结果，再使用现有 `/metrics` 做独立试点。

依赖维护也需要纳入后续工作。本轮 .NET restore 对现有 ImageSharp 3.1.12、MessagePack 2.5.302、System.Security.Cryptography.Pkcs / Xml 等包报告 NuGet 漏洞告警；这些并非本轮新增依赖。接手时运行完整传递依赖审计，核对可达路径与修复版本，以独立升级 PR 验证，不能把采用开源组件等同于免维护。
