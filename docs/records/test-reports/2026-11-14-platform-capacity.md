# 2026-11-14 平台容量测试

以第 23 场 CTF 赛事为样本，分别测主站公网访问、多账号登录、容器创建和独立容器入口。生产主站仍使用组网前端 `f800a987` 发布目录。测试前有 3 台在线可调度节点、0 个活跃队列任务和 1 个现有赛事容器。赛事有 11 支队伍，每队最多 3 个容器。节点处于自动容量模式，面板的 110 个配置槽位不能用来推断实测容量。

## 多账号与容器

北京时间 20:46，两个临时账号通过公网并发登录，均成功，最慢 235 ms。两支临时队伍通过参赛审核后，并发启动第 19 题。两个请求都进入队列，均调度到 `.31`，排队至开始执行分别约 0.065 秒和 0.167 秒。

其中一个创建任务成功，容器开始后约 25.86 秒收到入口确认，实际 HTTP 200。另一个创建任务返回 `docker.operation_failed`。节点清单显示失败对象已创建但没有进入运行态。主站公网探测 4 / 4 为 HTTP 200，原有容器及测得的测试容器入口也分别返回 HTTP 200。当前证据指向容器启动路径，具体 Docker 错误仍待节点日志核实。此处停止同题加量。

北京时间 20:53，另两个临时账号通过公网并发登录，均成功，最慢 266 ms。两个账号分别启动第 19、21 题，均调度到 `.31`。第 19 题在发出请求后 3.42 秒观察到入口就绪，公网访问返回 HTTP 200。第 21 题返回 `docker.operation_failed`，节点同样留有未启动对象。包括清理阶段在内，主站首页 11 / 11、原有容器入口 7 / 7 返回 HTTP 200。原有入口出现最长约 1.22 秒的响应，样本不足以判断延迟是否与发布路由有关。

两档各有一个容器正常运行，均未达到 2 / 2 成功。测试在这里停止，无法用这四个启动样本确定平台稳定容器数量或容器入口在更高负载下的表现。节点 `.31` 上的 Docker 原始启动错误未读取，具体根因待排查。[后续事项](../../backlog.md)见 RUN-04。

## 清理与复查

首轮脚本将带赛事名前缀的队伍标签与队名直接比较，导致自动清理暂停。测试队伍和账号移除后，后台列表因对象解绑未再显示成功容器，但数据库和节点仍显示它运行。通过节点清单核对本轮对象名称、原生标识和代际，移除两轮遗留对象。首轮成功容器的记录通过平台销毁任务进入 Destroyed，公网映射查询不再包含该记录。第二轮成功容器通过正常业务销毁流程清理。

最终核对临时账号、队伍、节点 Docker 对象、有效测试路由和活跃队列均为 0。赛事参赛数恢复为 11，三个节点在线，唯一原有容器仍在运行。主站首页、赛事 API、原有容器入口均返回 HTTP 200，已回收测试端口未能返回 HTTP。主站和 FRP 客户端进程 PID 与测试前一致，未发生重启。

原始脱敏结果位于工作站容量测试目录的 `web-measurements.json`、`web-followup-measurements.json` 和 `web-steady-measurements.json`。脚本及原始文件保留在本机。
