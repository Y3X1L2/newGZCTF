# TeamLab 生产仿真与容量测试汇总

日期：2026-09-18

## 1. 结论

TeamLab 的控制面和 Docker 执行面已经完成可复核的性能验证。控制面在约 600 req/s 的混合负载下保持 600.07 req/s，总 P95 为 11.87 ms；单环境 100 个 Docker 资产从受理到运行完成用时 35.54 秒，5 个环境共 100 个资产并发创建用时 41.69 秒，双 Worker 80 个资产创建用时 29.73 秒。

生产两小时仿真完成了两队各 20 个混合资产的持续运行。共记录 169,670 次请求，成功 165,482 次，成功率 97.53%，P50 11.08 ms，P95 56.82 ms。4,188 次失败全部来自蓝队 Web，根因是 HostGateway 的 OVN 端口 MAC 与 Linux 接口 MAC 不一致。修复后连续 20 秒新增 283 次成功访问，失败数不再增加；三台 Agent 已同步修复版本。

本轮高并发数据面测试曾先后经过临时公网入口和本机 WireGuard 路由。这两段结果受测试路径影响，不能作为平台容量指标。关闭本机 WireGuard 后，内网 500 req/s 的独立 30 秒核对达到 499.2 req/s、成功率 100%、P95 92.3 ms。后续完整分档测试期间本机网络再次中断，因此 1000 req/s 以上的数据只保留为故障线索，不作为容量结论。

当前最明确的性能约束不是主站 API，而是生产容量声明和数据面测试路径。生产第二队运行环境曾因节点容量不足等待 453.30 秒，实际部署执行只用了 33.84 秒。数据面经过 nftables DNAT 和 OVN/OVS 内核转发，主站 C# 代码不参与逐请求处理；后续必须用 10.24 内网的独立负载节点，将“资产直连、Worker 内网转发、跨 Worker Fabric”分开测，才能判断瓶颈属于题目容器、Linux conntrack/转发还是 OVN Fabric。

执行面已测操作中，5 个环境共 100 段抓包停止用时 17.96 秒，是唯一明显超过 10 秒批量操作目标的项目。其余 100 资产暂停、恢复、链路策略和销毁均在 10 秒内完成。

## 2. API 全流程验证

P1 使用独立 PostgreSQL、Redis、Docker Engine、真实 OVN/OVS 和正式 Agent，通过一条 API 流水线完成：控制范围、镜像、设备模板、拓扑、发布、运行环境、文件操作、资产控制、链路策略、服务开放、终端、会话审计、授权隔离和销毁。

| 项目 | 结果 |
| --- | --- |
| 运行资产 | 2 个真实 Docker 资产 |
| 数据一致性 | API、数据库、Agent、Docker、OVN、OVS 一致 |
| 整网链路策略 | 2 个资产接口均生效并恢复 |
| 服务开放 | 创建、访问、撤销完整通过 |
| 远程终端 | 真实 WebSocket PTY 通过 |
| 权限隔离 | 第二控制范围 Token 无法越权读取 |
| 销毁清理 | Docker、OVN、OVS 无本轮残留 |

这条流水线证明 Docker API 底座闭环，不代表 VM、SFTP、VNC 和多 Worker 已由 P1 覆盖。

## 3. 控制面性能

测试对象为 80/100 资产拓扑读取、校验、计划和并发修订写入，4 个受限 Token 混合请求，持续 20 秒。

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 实际吞吐 | 592.87 req/s | 600.07 req/s |
| 总 P95 | 323.56 ms | 11.87 ms |
| 80 资产计划 P95 | 571.16 ms | 11.74 ms |
| 100 资产计划 P95 | 573.42 ms | 7.94 ms |
| 5xx / 429 / 死锁 | 未形成稳定基线 | 0 / 0 / 0 |

总 P95 降低 96.33%，80/100 资产计划 P95 分别降低 97.94% 和 98.62%。优化来自删除重复限流和重复授权查询、批量写 API 审计、复用不可变拓扑数据；没有通过降低数据库连接池或请求并发换取结果。

## 6. 文件传输与 VM 问题

64 MiB Docker 文件上传、下载和 SHA-256 校验通过：

| 队伍 | 上传 | 下载 |
| --- | ---: | ---: |
| 红队 | 12.18 MiB/s | 26.34 MiB/s |
| 蓝队 | 12.24 MiB/s | 27.40 MiB/s |

Linux VM SFTP 当时返回 503。Agent 现场错误为 `runtime.identity_conflict`：TeamLab 原生 VM 使用 TeamLab UUID，文件接口却按通用 KVM UUID 和 sidecar 校验，同一台合法 VM 必然被拒绝。代码已经改为使用 TeamLab 的 `domain name + UUID + generation` 身份规则，并在同一次身份锁内读取业务地址和管理地址。三台 Agent 当前均运行修复后二进制，SHA-256 为 `51d9dab2504a5ee5dad26455da26ea85eafe61cddf01148dd561ba5e1cd4dc8a`。受本轮网络中断影响，真实 SFTP 64 MiB 回归尚未完成。

## 7. 数据面压力结果

### 7.1 不作为平台指标的数据

公网混合测试把 HTTP、SSH 和 RDP 短连接混在同一个成功率中，并从 Worker 经公网地址回环。2000 req/s 档中，HTTP 连接失败 187,735 次、SSH `OSError` 53,569 次、RDP 错误或超时 41,964 次。这反映了测试源临时端口、连接跟踪和临时公网链路限制，不能解释为平台 HTTP 成功率。

本机 WireGuard 开启时，WSL 到内网 Worker 的单请求约 220 ms，500 req/s 只有 3.89% 成功。关闭 WireGuard 后单请求降至约 39 ms，同一 500 req/s 核对达到 499.2 req/s、成功率 100%、P95 92.3 ms。该对比确认第一轮低成功率主要来自测试机路由。

### 7.2 中断前的内网原始数据

完整分档第二次运行在 1000 req/s 后出现本机网络中断，数据保留但不作为平台容量门槛：

| 目标 | 实际完成 | 已完成请求成功率 | P95 |
| ---: | ---: | ---: | ---: |
| 500 req/s | 491.33 req/s | 98.19% | 140.34 ms |
| 1000 req/s | 730.86 req/s | 61.11% | 6,115.21 ms |
| 1500 req/s | 800.03 req/s | 0% | 6,486.83 ms |
| 2000 req/s | 1,257.13 req/s | 0.14% | 7,158.37 ms |

该路径为：WSL2 -> `10.24.0.27:30000/30002` -> Worker nftables DNAT -> OVN/OVS -> 两个测试 Web 容器。主站 API 不在逐请求路径中。测试同时受 WSL2 网络、本机路由和两个题目容器处理能力影响，当前数据只能说明 500 到 1000 req/s 之间出现排队，不能把瓶颈直接归因于平台代码。

## 8. 已确认瓶颈与优化方向

### 8.1 已经定位并修复

1. 控制面重复限流、重复授权查询和逐请求审计写入已经删除或合并，总 P95 从 323.56 ms 降到 11.87 ms。
2. HostGateway MAC 错配已经修复；这是两小时仿真 4,188 次失败的唯一原因。
3. VM 文件身份规则错配已经修复；不保留旧算法兼容分支，不增加第二套 VM 状态。
4. 压测脚本已删除 SSH/RDP 与 HTTP 混合成功率，数据面地址改为必须显式指定内网 Worker。

### 8.2 不需要改平台代码

第二队等待 453.30 秒是节点声明容量不足，不是调度器执行慢。容量满足后，20 个混合资产实际部署只用 33.84 秒。处理方式是按比赛规模配置 Docker/VM 容量并预分发镜像，不应通过绕过容量预留或扩大调度并发掩盖资源不足。

服务开放的数据面只安装 nftables DNAT/SNAT 规则，连接建立后不经过主站或 Agent 的 C# 请求处理。当前没有证据支持修改 API、增加中继服务或新建转发队列。

### 8.3 还需要一次定向定位

抓包停止可以直接优化。现有结果表明并发环境下的分段停止和制品收尾仍有串行等待，应按 Worker 并行停止、每个 Worker 使用现有执行额度，并在同一批完成后统一保存状态。该修改复用现有抓包任务和部署事实，不增加队列或状态机。

高并发数据面的下一次测试只需要一台稳定的 10.24 内网负载节点和一个确定性 Web 镜像，分别测三条路径：

1. Worker 本机直连资产 IP；
2. 内网客户端访问 Worker DNAT 端口；
3. TeamLab 流量客户端跨 Worker Fabric 访问资产。

每条路径记录同一档 500、1000、2000 req/s 下的成功率、P95、容器 CPU、宿主 softirq、conntrack 使用量和丢包。直连失败说明题目镜像或资源配额不足；直连通过而 DNAT 失败说明 Linux conntrack/nftables 需要调整；DNAT 通过而跨 Worker 失败才进入 OVN/Geneve 调优。没有这组三段对照前，不应盲目修改平台代码。

## 9. 当前清理状态

本轮和先前卡在销毁中的测试运行环境已经通过正式管理接口清理；活动部署票据和活动服务开放映射均为 0。三台 Agent 均为 `active`，二进制哈希一致。生产中仍可能存在其他业务运行环境，本报告没有修改或清理非测试资源。

## 11. 性能瓶颈判断

| 项目 | 判断 | 是否能优化 | 下一步 |
| --- | --- | --- | --- |
| 控制面 API | 旧瓶颈已经消除，目前不是主矛盾 | 已完成主要优化 | 保持现有架构，不再为数字增加缓存或队列 |
| 运行环境容量等待 | 生产蓝队等待 453.30 秒，属于节点容量声明不足 | 能，通过赛事前容量配置解决 | 按队伍数声明 Docker/VM 容量并提前分发镜像 |
| Docker 部署 | 100 资产约 36 秒，双 Worker 80 资产约 30 秒，当前表现正常 | 可以继续优化，但优先级低 | 后续只看真实多 Worker 扩展，不改统一部署队列 |
| VM 启动 | 三资产混合环境约 101 秒，时间主要在 VM 启动 | 能，但依赖 libvirt 和镜像准备 | 预热镜像；补充 Linux/Windows 分项计时后再调 VM 并发 |
| 抓包停止 | 100 段停止 17.96 秒，唯一超过 10 秒目标的已确认批量操作瓶颈 | 能 | 按 Worker 并行停止，同批状态一次保存 |

数据面三段对照可以直接确定责任位置：资产直连已经失败，问题在题目服务或容器资源；直连通过而 DNAT 失败，检查宿主机 `conntrack`、端口队列、softirq 和 nftables；DNAT 通过而跨 Worker 失败，再检查 OVN/Geneve。三段结果出来前，不修改主站 API，也不增加中继、重试或新的转发层。

## 12. 历史参照与功能验收

2026-08-17 的旧环境基线只用于观察量级：2 个 Docker 资产在 V2 下冷启动 8.94 秒，后续启动 3.31-4.19 秒；1 Docker + 2 VM 的混合环境 V2 三次创建平均 77.43 秒、销毁平均 9.01 秒。测试机器、镜像和版本均与本轮不同，不能直接与本轮 101 秒混合环境作回归对比。

2026-08-18 的真实链路验收完成了 Modbus/TCP 读写、OVS Mirror 抓包、链路时延与丢包、访问规则、OVN DNAT/SNAT、连接器租约和协议事件回读。Modbus 抓包包含 330 帧、300 条 TCP/502 数据；200 ms 延时策略实测平均 200.223 ms，恢复后回到正常链路。这些结果证明对应功能链路真实执行，不属于容量测试，也不能替代本轮的大规模性能数据。
