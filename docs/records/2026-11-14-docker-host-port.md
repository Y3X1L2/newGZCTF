# Docker 并发启动端口修复

状态为本地和生产验收通过。起点为 `origin/main` 的 `2d1d236f`，分支为 `codex/docker-host-port`。

## 为什么修改

两支队伍同时在同一节点启动容器时，旧逻辑可能给两次请求选同一个宿主机端口。Docker 启动到绑定端口时，先到的一支队伍成功，另一支失败。11 月 14 日在生产 `.31` 上确认四次冲突，涉及 `42760` 和 `42761`。`.30` 的远程 Agent 和 `.27` 的主站本地执行也有这段逻辑，当天日志里未发现同类冲突。

两条路径共用一套端口规则，由 Docker 在启动时选取和占用端口，之后将实际端口交给主站。网关继续按「公网端口 → 节点地址和端口」转发。范围内无端口可用时，先删除本次没启动的容器，再让 Docker 自动分配一次。显式指定端口仍要求原值。

## 本地验收

用隔离的主站、Agent、PostgreSQL、Redis 和 Nginx，逐轮只允许一个节点接单。每轮两支独立队伍各发一次比赛容器启动请求，Docker 事件显示两个容器都创建后才开始启动。使用仓库的网关同步脚本发布路由并回传确认，再用 HTTP 读取每个入口并核对返回的队伍号。

| 执行路径 | 队伍号 | 节点端口 | 网关入口 | 结果 |
| --- | --- | --- | --- | --- |
| 主站本地 Docker 29.1.3 | 5、6 | 42760、42761 | 30360、30361 | 两个入口均为 HTTP 200，分别返回 5、6 |
| 远程 Agent / Docker 29.5.3 | 7、8 | 42761、42760 | 30362、30363 | 两个入口均为 HTTP 200，分别返回 7、8 |
| 主站本地端口段满 | 9、10 | 32769、32768 | 30365、30364 | 两个入口均为 HTTP 200，分别返回 9、10 |

远程 Agent 另外验证了端口段满时自动分配新端口，以及指定已占用端口时返回失败并清理本次容器。联调镜像只返回测试队伍号，远程镜像预先加载到节点。本地 Release 构建、11 个定向后端测试通过。发布提交的 GitHub 后端、前端和文档检查均通过。
