## 当前状态与技术结论

**IMPLEMENTED / VERIFIED（前端自动化及隔离浏览器）：U1 前端可初步验收。NOT_RUN（真实后端及数据库联调）：尚不构成整场验收。**

- 新增 `/league`、`/league/new`、`/league/:matchId`，沿用 vNext 壳层与 feature adapter。入口位于“全部模块”，构建开关 `VITE_LEAGUE_ENABLED=true` 时显示；默认关闭，直接访问关闭路由也不请求联赛数据。
- 对接生成客户端的真实 League API；场景及 release 复用 TeamLab 目录，战队复用当前用户战队 API。未修改生成代码或契约。
- 列表支持游标分页、返回恢复、刷新及空态/错误态；身份隔离 SWR 缓存。未登录显示登录入口，管理员与队长操作按身份及服务端 `allowedActions` 展示。
- 创建/编辑支持名称、初始金币、固定场景发布版本；配置 revision 随写请求传递。409 后刷新服务端数据并保留脏输入，要求显式载入最新配置；写操作不自动重试，进行中禁止重复提交。未保存配置离开时提示确认。
- 队长只能选择本人担任队长、未锁定且尚未报名的战队；管理员先审核，再从已通过战队选择两个不同席位。界面成功状态只来自服务端返回。准备后不再显示配置写入口。
- 现行 vNext 源码/门禁使用 `--yn-*` 语义 Token，沿用该约定；旧样式文档的 `--yy-*` 未作为新实现依据。
- 暂不展示参赛成员名单：后端准备前 `MemberIds` 为空的问题按用户要求保留。报名战队、审核状态和席位仍可操作。

## 初步验收步骤

1. 在获授权的测试环境使用本分支后端并确认其迁移；配置 `League__Enabled=true`。前端以 `VITE_LEAGUE_ENABLED=true` 构建或启动。需要管理员和两位未锁定战队的队长账号，以及已发布的 TeamLab 场景。
2. 管理员从“全部模块 → 数字攻防联赛”进入，创建名称、整数金币、场景及 release；刷新确认配置回读。也可先不配置场景创建草稿。
3. 两位队长各自报名，管理员通过审核，分别保存席位 1/2；刷新确认队伍及顺序。重复席位必须被禁止，非队长及锁定战队不能提交。
4. 两个管理员窗口同时编辑：先保存一个，再保存旧 revision，应显示冲突并保留输入，显式载入后才能再次保存。检查离开未保存表单的确认提示。
5. 检查列表翻页、返回、匿名/普通用户权限、接口禁用/失败态。准备与开赛不是本轮 UI 验收项；准备后的只读状态已有前端自动化覆盖。
