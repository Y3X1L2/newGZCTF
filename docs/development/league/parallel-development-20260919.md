# 联赛多人并行开发与合并约定

2026 年 9 月 19 日 · 开发准备规范

## A1 执行原则与责任

本规范配合[开发路线](roadmap-20260919.md)使用。组织责任已经确认：lxy 为规则与优先级最终确认人、PR 合并及迁移协调人，lmr 为技术协调替补。共享文件分工、接口约定和迁移顺序从第一笔业务代码开始采用。

每项任务指定一位实现负责人、一位非作者审查人，以及涉及接口时的接收人。集成人负责 PR 顺序和集成状态，模块作者负责自己的测试与问题修复。规则负责人决定金币、KO、暂停、加时和对外验收标准。

本文“集成人”“迁移协调人”均指 lxy，技术协调由 lmr 替补；“规则负责人”指 lxy。lmr 代班时按已确认规则协调技术工作，业务规则变更仍交 lxy 确认。

同一开发者可以同时承担多个任务，但每个任务使用独立分支和 worktree；同一目录只有一个执行者。多人或多个 AI 同时工作时，各自的临时数据库、服务端口和输出目录也要隔离。

### 开发前共同确认的产物

1. 通过的 main 基线、已知限制及统一依赖版本。
2. 本阶段规则快照、接口版本、请求响应样例与失败结果。
3. 任务编号、负责人、改动目录、依赖 PR 和验收用例。
4. 共享文件维护人、迁移合并顺序、API 生成安排。
5. 联调环境、场景版本、测试数据及合并后的回归流程。

对尚未确认的接口，先提交短设计说明共同审查。需要改动另一人的目录时，先登记影响文件和接收人，再安排同一 PR 或前置 PR。

## A4 接口冻结与变更流程

接口的生产方先提交契约 PR，包含 DTO、字段含义、权限、错误、时序与正常/失败样例。所有直接消费方审查通过后合入 main，再开发依赖它的实现。

### 契约必须包含

标识类型、字段单位、金额精度、UTC 时间格式、空值含义、枚举、默认值、状态转换、重复请求处理、并发冲突、结果查询和重试条件。场次规则、内容版本及 runtime generation 在需要验证的操作中明确携带。

### 变更顺序

1. 生产方列出变更字段和所有消费方，补充行为样例。
2. 优先新增可选字段或兼容能力，消费方分批更新。
3. 对必填字段、状态语义、权限及删除操作的改变，共同确定迁移方案。
4. 先合入生产方兼容能力，再合入消费者；最后清理确已无引用的旧行为。
5. 对公开外部 API，按既有版本标准处理破坏性变化，不能用更新快照掩盖语义变化。

本地同进程契约与对外 HTTP 契约分别管理。前端使用 feature adapter，展示组件不依赖生成客户端。开发期固定样例只用于组件和契约测试，集成验收连接真实接口。

### 金额和裁判的语义审查

金额字段名称相同并不代表规则相同。PR 应附一例购买和退款、一例 10 秒收入、一例任务重复领奖，以及涉及本次改变的临界时间样例。裁判变化附对应的证据、挑战或改判样例，交规则负责人确认业务含义。

## A5 分支拆分与依赖顺序

一个分支承载一个可独立审查、可验证的结果。建议控制在 1–3 个工作日能完成的范围，大任务按可运行步骤分成多笔 PR；迁移、生成文件和必要测试不按行数强行拆开。

分支命名示例：`codex/league-t06-ledger-command`、`codex/league-t07-runtime-binding`、`codex/league-t12-shop-panel`。这些是后续示例，本次没有创建业务开发分支。

### 推荐合并批次

| 批次 | 合入内容 | 后续可开始的任务 |
| --- | --- | --- |
| B0 | T00 基线修复 | 全团队从通过基线继续 |
| B1 | T01 公共契约与 T04 基础模块 | 场次、账本、运行适配和基础页面并行 |
| B2 | 场次和账本命令、运行适配的各自可测试实现 | 订单编排、收入及正式接口联调 |
| B3 | 商店订单、Checker 与产币、自动 KO 的执行和判定 | 真实购买、挑战、收入及页面集成 |
| B4 | 自动 KO 终局、金币终局及已连接真实接口的页面 | V1 联合验收；CTF 回执在 V2 合入 |

同批任务能并行开发；涉及迁移、公共 DTO 或生成文件的 PR 按维护人登记的顺序合并。没有直接依赖的 UI 组件可以提前提交，入口仍由功能开关控制。

### 依赖 PR 的处理

常规做法是先让前置契约 PR 进入 main，再创建依赖分支。紧急联调可以在专用临时 worktree 中组合未合并分支，验证后仍逐个审查原 PR。临时集成分支不作为新功能的长期开发基线，也不整体绕过各包审查合入 main。

已经公开的任务分支使用 merge 同步 main，保留原提交历史。全团队采用普通 merge commit 合并为默认流程，避免依赖链因混用 squash、rebase 和手工 cherry-pick 变得难以追踪。

## A6 Worktree 与日常同步

以下命令是后续开发示例。执行前确认当前目录及工作树状态；每个人替换自己的任务名称与目录。

### 创建任务

```powershell
git status --short --branch
git fetch origin --prune
git worktree add ..\newGZCTF-league-t06 -b codex/league-t06-ledger-command origin/main
git -C ..\newGZCTF-league-t06 status --short --branch
```

前置 PR 尚未进入 main 时，先做独立工作或契约审查；进入实现前确认前置提交已包含在当前分支。

### 同步主线

在任务 worktree 内先提交本人的阶段改动，再同步主线。发现其他人的未提交修改时停止并确认目录归属。

```powershell
git status --short --branch
git fetch origin --prune
git merge --no-edit origin/main
git diff --check
```

同步发生冲突时，查看双方修改用途，由对应文件维护人与作者一起处理。完成后运行受影响测试，再提交解决结果。不要用整文件选取 ours/theirs 处理模型快照或生成 API。

### 提交与 PR

```powershell
git diff --check
git status --short --branch
git add <本任务的文件>
git commit -m "feat(league): describe one verified change"
git push -u origin HEAD
```

建立草稿 PR 后，注明依赖任务和暂未完成项。待实现、测试、迁移与文档齐全，再标记为待审。当天至少更新一次合并依赖和已知问题，避免只在聊天中同步接口变化。

## A7 数据库迁移的并行办法

当前 AppDbContext 是 partial，OnModelCreating 会扫描模块内的 EF 配置。各包在自己的业务目录中维护实体和配置，公共 DbContext 增量由迁移协调人安排。数据库仍是同一个业务事实源。

### 正式迁移只占一个合并位置

两人可以同时设计模型和写仓储测试，但准备合并时登记迁移顺序。排在前面的 PR 先同步最新 main、生成迁移、跑验证并合入；后一笔再同步已经包含前一迁移的 main，生成自己的正式迁移与快照。

业务模型、迁移、快照、读写代码和必要测试在同一笔可运行变更中提交。处于后序的草稿 PR 可以暂未达到最终迁移门禁，标明等待前置迁移，不能提前合入生产模型。

### 验证范围

1. 新数据库从全部迁移创建成功。
2. 从上一个主线数据库版本前向升级成功。
3. 已有业务数据、唯一键、外键、索引和默认值符合预期。
4. `dotnet ef migrations has-pending-model-changes` 无模型漂移。
5. 涉及数据回填或删除限制时，在隔离 PostgreSQL 或备份副本验证失败恢复。

已共享或已应用的 migration 作为历史保留。前置迁移变化导致冲突时，迁移协调人检查完整迁移链，以合并后的模型重新生成并核对快照；需要实际 schema 调整时追加前向迁移。不能直接保留某一边快照后假定另一边模型已经包含。

联赛之外的主线迁移也要纳入这一合并顺序。最终合并前如果 main 又增加迁移，当前迁移 PR 重新同步和验证。仓库已有历史迁移来源缺口，生产发布时继续使用新鲜备份副本验证升级。

## A8 OpenAPI 与前端生成代码

当前前端 `pnpm genapi` 从 `http://localhost:8080/openapi/v1.json` 生成 `src/generated/Api.ts`。外部 API 快照是 `docs/commercialization/openapi/open-v1.json`，对应 `/openapi/open-v1.json`。两者用途不同，生成时核对目标文档。

### 生成顺序

1. 后端契约、Controller 和 DTO 在当前 PR 中达到可运行状态。
2. 从该 PR 对应代码启动受控开发服务，记录提交和端口，确认不是其他 worktree 的旧进程。
3. 生成内部客户端或外部快照，审查新增、删除和必填字段变化。
4. 运行接口、TypeScript、前端架构与契约兼容测试。
5. 将契约变化和生成结果放在同一 PR；合并后其他任务同步 main 再生成自己的增量。

生成文件发生冲突时，先合并源代码和契约，随后从合并后的实际服务重新生成。两份 generated/Api.ts 的手工拼接无法保证声明与服务一致。

外部 API 兼容性沿用 `scripts/verify-openapi-contract.ps1`；它与快照一致性测试共同执行。更新快照时必须说明预期差异，本次 main 的快照失败先在 T00 中单独解决。

### 减少全局文件冲突

联赛 feature adapter、controller/hook 和 panel 放在所属目录。`VNextApp.tsx` 只装配联赛入口，联赛自己的路由在 feature 内拆分。公共 token、locale 汇总、包依赖和 lockfile 由维护人统一审查，功能 PR 只带本次确有需要的变更。

## A9 联调环境与测试数据隔离

开发者各自使用独立数据库或隔离实例、Redis 命名空间、服务端口、临时文件目录和测试身份。固定场景可共享定义，运行实例和测试数据分别创建。实例关联包含任务或场次标识，清理只处理本次拥有的资源。

仓库 `docker-compose.dev.yml` 固定映射了 5432 和 6379。多人在同一机器开 worktree 时，需准备各自端口及配置覆盖；只换 worktree 或 Compose 项目名不足以避免端口冲突。

### 四类验证环境

| 环境 | 使用方式 | 负责人与边界 |
| --- | --- | --- |
| 单元与契约测试 | 本地及 PR CI，使用固定且无秘密的样例 | 各包作者维护，消费方运行同一契约样例 |
| 数据库集成 | PostgreSQL Testcontainers 或隔离数据库 | 作者验证真实约束和事务，迁移协调人复核升级 |
| Docker/TeamLab 联调 | 真实主站 API、队列、Agent 和隔离场景 | yhr 管运行基线，其他人按分配范围使用 |
| 候选比赛环境 | 已合并提交、固定规则与镜像版本 | 集成人组织双队流程，主办方参与裁判验证 |

多个人同时使用真实 Worker 前，先验证 scope、网络、端口和资源配额隔离。硬件、网关或网络配置会影响其他测试时，登记使用时间，由 yhr 协调。共享联调库只由合并后的候选版本升级，个人分支不直接迁移共享库。

### 每次联调保留

main/PR 提交、规则与场景版本、数据库迁移头、场次/队伍/订单/operation/票据/runtime/generation 标识、操作时间与结果。敏感字段使用受控存储或引用，报告和仓库不保存 Flag、密码、Token 或私钥。

前端 mock 验证布局和交互，后台契约样例验证调用约定。V1 阶段验收必须补真实接口、数据库约束和基础设施结果。

## A10 PR 内容与合并步骤

### PR 说明模板

每笔 PR 写明任务编号、触发场景、完成后的行为、改动目录、依赖 PR、共享文件、契约变化、迁移及生成文件、通过的测试、未执行项目、回退办法。附一条可复验的正常流程和本次重要失败分支。

纯文档可以执行链接、内容和格式检查。业务 PR 按影响范围运行仓库门禁；共享契约、调度、计分、迁移和认证扩大验证。对已有失败说明基线与本次增量，合并所需门禁仍需恢复通过。

### 合并前

1. 作者确认工作树干净，提交已推送，PR 只包含本任务内容。
2. 集成人核对前置任务已经进入 main，共享文件与迁移没有另一笔占用。
3. 作者同步最新 main，解决冲突，重跑相关验证；CI 检查最新提交与主线组合。
4. 接口接收人核对行为，非作者审查通过。
5. 集成人按排定顺序正常合并；如果 main 又前进，重新确认检查对应最新组合。

### 合并后

更新合并记录和依赖任务，候选环境按明确提交构建。其他作者拉取新 main，推进下一批任务。main 的 push CI 失败时，先暂停后续合并，区分确定的代码问题和环境故障；必要时通过正常 revert 提交回退业务变更。

应用回退与数据库回退分别判断。有数据迁移时优先采用兼容代码或前向修复，生产数据库按发布手册处理。分支清理在确认已推送、已合并、工作树干净且没有待交接修改后执行。

## A11 冲突处理与协作节奏

| 情况 | 处理人 | 处理方式 |
| --- | --- | --- |
| 两个分支改同一 DTO | 接口生产方与全部消费方 | 先确认语义和兼容性，再合源代码与测试 |
| 两个迁移改同一表或快照 | 迁移协调人与模型作者 | 重新排序，验证完整迁移链和前向升级 |
| 生成客户端冲突 | API 生成维护人 | 合源契约后重新生成，检查消费方编译 |
| 两个页面改路由/locale/依赖 | lcx 与对应作者 | 公共变更拆成前置 PR，页面继续各自开发 |
| 合并无文本冲突但业务失败 | 对应状态写入负责人 | 用订单、事件和状态序列定位，补跨模块回归 |
| 前置 PR 延期 | 依赖任务负责人和集成人 | 调整顺序，先做独立组件或测试，保持契约变更可追踪 |

建议每天用简短记录说明：当前任务、依赖变化、共享文件修改和联调结果。每周演示一条已合并的真实流程，检查各包是否在使用同一规则、场景和接口版本。具体会议频率按四人的投入安排确定。

接口争议由生产方、消费方及技术负责人解决；金币和裁判语义交规则负责人确认。决定记录写入仓库，包含适用版本、决定人、日期和受影响任务。

### 开工验收

四位开发者分别从同一 main 基线建立独立 worktree，运行本地基本门禁，读取同一组契约样例。先用一笔契约 PR 和两笔无共享改动的功能 PR 演练“创建、审查、CI、合并、同步”；再用一笔迁移及生成客户端 PR 验证串行维护流程。

演练通过后开始并行任务。规范本身不保证零冲突，它使冲突尽早出现，并让每类冲突有明确处理人、验证方法和合并顺序。

本次已核查仓库现状，以上目录拆分、保护设置、契约文件和开发演练均为后续实施要求。实施状态和确认人员记录在任务交接中。

### 金币与运行的共同样例

采用已冻结的基础价及规则，测试队初始余额 3000。购买价格 800 的业务后余额为 2200；同一请求重试仍对应原订单。通过产币资格检查后，连续 3 个有效周期各收入 20，余额为 2260。

再购买一项价格 800 的资产，部署明确失败并退款后余额恢复到 2260。最后的分录总和与余额一致。V2 接入 CTF 后再加入奖励样例：完成 200 金币任务，余额变为 2460；重复提交或重复消费同一完成事件，奖励总额仍为 200。

分别在扣款已保存、远程创建已受理、部署已完成而回调尚未处理时中断服务，重启后查询和继续原操作。部署结果未知时保留处理中状态，确认结果后完成订单或一次补偿。

场次结束后核对终局只执行一次，新的购买和奖励请求按终局规则处理；必要证据已归档，访问已关闭，资源准确回收，另一测试场次保持正常。

这组样例由四人共同维护一份预期结果。每次相关接口或规则改变，先更新样例并共同确认，再修改各自实现。

## A13 Checker 与自动 KO 的交接约定

出题人提供具体检查逻辑，yhr 提供执行架构，lmr 提供通用自动裁判。三方先用同一个固定场景完成交接，再加入更多题目。

| 交付方 | 必须交付 | 接收与验收 |
| --- | --- | --- |
| 出题人 | 镜像版本、正常业务样例、业务 Checker、访问证明、非破坏写入、随机挑战生成/验证、失败与修复样例 | yhr 核对可运行性，lmr 核对能否支持规定判据，具体业务含义由出题人签收 |
| yhr | 脚本版本管理、参数投递、执行隔离、超时限制、结果回传、证据保存与运行身份 | lmr 用正常、失败、未知和过期结果验证接收行为 |
| lmr | 60 秒挑战调度、6 次结果聚合、中断、去重、判定状态及验证结论 | lxy 接收带规则和证据的判定结果，调用一次性场次终局用例 |

### V1 最小任务与结果字段

执行任务至少包含任务标识、场次、目标逻辑资产、runtime/generation、脚本版本、检查类型、一次性挑战标识和截止时间。检查类型区分健康、访问证明、业务写入和持续挑战。秘密参数使用受控引用或加密投递。

执行结果至少包含原任务标识、Passed/Failed/Unknown、观测时间、运行代次、脚本版本、挑战标识及证据引用。Unknown 表示尚无可靠检查结论。接口接收方验证结果来自授权执行端，并匹配原任务和当前代次。

### 自动 KO 联合验收

使用真实场景取得访问证明并完成限定业务写入，随后在 60 秒内每 10 秒完成一次随机挑战，共 6 次。全部结果有效且证据一致，系统产生一次 KO，lxy 的终局用例只结束场次一次。

验收还覆盖任意一次挑战失败、执行超时、旧代次结果、相同挑战重放、另一目标的证明，以及检查过程中服务重启。连续控制证据无法恢复时，该次挑战明确中断，重新获取证明后发起新的挑战，保留旧记录。
