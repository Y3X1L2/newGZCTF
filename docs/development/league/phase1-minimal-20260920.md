# 联赛第一阶段最小实现与分工

2026 年 9 月 20 日更新

第一阶段完成一场双队比赛的基本流程：选手进入模块、报名，管理员配置并启动比赛，选手取得对方核心 Flag 后提交，平台校验并判定 KO。金币提供加减、余额和流水。目标仍为 9 月 30 日左右跑通。

这次调整已由 lxy 与负责人商讨后提出，替代此前首期必须完成 Checker 自动 KO、服务得分及经营结算的安排。lxy 已确认管理员审核两队并手动开赛、服务端首笔有效终局判胜，以及受限业务账号与防守配置范围。本文据此安排开发和验收。

### 最小使用流程

管理员创建场次并开放报名；参赛成员用现有战队报名，管理员审核并确定两队。准备环境时保存参赛名单和配置快照。两队环境就绪后，管理员点击开赛；选手查看入口、攻击对方核心、提交 Flag，页面显示 KO 结果。

首期采用人工审核、单场双队、管理员手动开赛。结束方式包括有效 Flag 触发 KO，以及管理员填写原因中止场次；中止记录为无胜者。赛时长、自动到时结算和赛中暂停可随以后确定的赛规加入。

## 2 核心 Flag 和金币的最小规则

### 核心 Flag

每队预置一套核心环境，平台按场次、目标队、核心和运行代次生成独立 Flag。开赛前完成安全注入和读取验证；正常判题只需校验提交值及其归属。首期使用单场固定值，下一场或环境重建时更换。

提交方身份从登录和报名关系确定，目标固定为本场对手。后端校验场次正在进行、参赛资格有效、Flag 对应当前对方核心，随后在同一数据库事务中保存有效提交和 KO 结果。自身、其他场次和旧代次 Flag 均按无效提交处理。

采用已确认的“最先在服务器完成有效判定并成功写入终局的队伍获胜”规则。以数据库事务先后为准，客户端时间与页面提示时间只用于展示。另一队的并发请求返回已结束结果；同一请求重试返回原处理结果。首期验收提前公布这一规则。

Flag 校验记录与赛果分别保存。记录至少包含场次、攻击队、目标队、核心、运行代次、提交人、判定方式、结果和服务器时间。判定方式先支持核心 Flag，后续 Checker 可以提供另一种依据，再调用相同的终局用例。

Flag 明文通过受保护的注入通道进入核心，校验信息保存在服务端。管理列表、玩家接口、日志、文档和提交快照均只展示必要的脱敏信息。比赛期间核心保持当前代次；故障需要重建时，首期先中止原场次，再新建场次开赛。

### 场景权限

首期只开放经过测试的业务账号与少量配置权限，平台管理入口和核心 Flag 的覆盖、删除权限由主办方保留。采用固定靶机权限模型，先验证一条双向攻击路线。

如果直接给防守方整机最高权限，停服务或封掉所有入口就可能使对手无法取 Flag。扩大到自由修补和任意防守操作时，需要同时补充业务可用性约束；只读挂载 Flag 本身无法解决停服问题。yhr 与出题人需在场景样例中明确并验证可操作范围。

### 金币

建议金币使用非负整数，每个场次内每队一个账户；初始金币作为一笔发放流水保存。管理员输入加减金额和原因，系统原子更新余额并保存流水。余额不足、越权和超出数值范围时返回明确结果，重试与并发请求按业务编号去重。

金额在后端校验。首期只允许管理员调用调整接口，选手读取本队余额和流水。赛果与余额独立，结束后账户转为只读；确有账务错误时追加有审计的更正记录。测试商品如启用，使用后台固定价格，并与扣款记录在同一事务保存，重复购买请求只扣一次。

lxy 统一拥有场次状态和最终赛果写入用例；lmr 的判定用例校验 Flag 后调用它，二者参与同一本地事务。lmr 独立维护金币写入入口。yhr 保存或查询运行绑定，运行状态继续以 TeamLab 和统一队列的真实记录为准。前端展示后端结果。

### 先约定这些接口

1. 场次：创建和修改草稿、报名和审核、确定两队、准备、开赛、中止、查询结果。
2. 运行：按场景版本准备双队环境、查询就绪与访问状态、关闭访问、销毁和重试查询。
3. 判定：生成并交付注入材料、提交核心 Flag、查询本人提交结果；终局写入由场次用例执行。
4. 金币：初始发放、管理员调整、查询余额和流水；测试商品按需调用同一扣费入口。

这些是待开发的用例名称，具体 HTTP 路径和 DTO 在首笔契约 PR 中统一。接口明确身份、权限、状态条件、版本、重复请求及错误含义。部署和销毁继续使用 DeploymentQueueTicket；业务记录放在 PostgreSQL，异步恢复复用现有 operation 能力。

联赛报名与现有 Game/Participation 的接入方式在契约 PR 中选定：优先复用现有赛事报名事实，通过公开 Application 接口增加双队选择和名单冻结。若现有公开接口不足，在所属模块补充，避免同时维护两套报名名单。

## 4 状态与失败处理

玩家流程保持简单，后台区分草稿、报名中、准备中、待开赛、进行中、已结束和已中止。准备中的失败作为可查询的准备结果保存，修复后重试原操作，或中止场次。

只有两队环境、Flag 注入和所需网络入口都确认就绪，才能进入待开赛。比赛开始时统一生效参赛权限与攻防访问。环境提前准备期间，选手入口和攻击通路保持关闭；TeamLab 的玩家访问开关与跨队攻击网络需要分别验证。

准备开始后使用固定配置和参赛名单。首期通过中止、清理和创建新场次处理名单或场景变更，减少在同一场次中切换环境的复杂度。

| 情况 | 首期处理 |
| --- | --- |
| 只有一队部署成功 | 保持准备状态，展示失败原因；重试复用原操作标识，已建资源可清理 |
| 连续点击准备或开赛 | 返回已有处理结果，保持一套有效环境和一个开赛时间 |
| 双方同时提交有效 Flag | 数据库原子终局只确认一个胜者，另一请求返回已有结果 |
| 管理员中止与 Flag 提交并发 | 使用相同的场次终局约束，保留先成功提交的终局及原因 |
| 请求超时或主站重启 | 查询数据库及运行记录恢复操作，返回已保存的提交、余额与赛果 |
| 已 KO 但关闭访问或销毁失败 | 保留赛果，清理显示待重试；后台可继续处理并核对残留 |

赛果和资源清理各自有状态。终局事务一并保存需要关闭访问和清理的持久化意图，执行失败可以重试。页面刷新、服务重启或清理完成都沿用原赛果。

后续扩展保留四处边界：场景以版本绑定到场次；判定记录带判定方式和证据引用；金币只从统一账本入口变更；最终胜负只从终局用例写入。首期实现一种 Flag 判定即可，通用规则编辑器和多插件调度可在有实际需求时再设计。

### 合并批次

第一批合入最小契约与模块基础，明确场次终局、Flag 注入和账本事务约定。第二批并行开发报名配置、运行适配、Flag 判定、账本及独立页面，按依赖逐笔合入。第三批连接真实接口并完成整场验收。

每个任务从最新 origin/main 创建独立 codex 分支和 worktree。生产方与消费方先审查接口，契约合入后依赖方同步 main。已推送分支用正常 merge 同步主线；每个 PR 包含自身代码、测试和必要文档。

lxy 排定数据库迁移顺序，lmr 替补。实体、迁移、快照和读写代码在同一 PR 中提交；后一笔迁移在前一笔合入后同步并生成。lcx 统一处理前端路由和生成客户端，生成文件按合并后的源契约重新生成。各人按场次、运行、判定、金币、前端目录分文件，避免共改一个总服务。

沿用[并行规范](parallel-development-20260919.md)中的工作区隔离、审查和生成文件规则；其中旧商城、产币、Checker 任务及旧排期由本页取代。

## 7 第一阶段验收

首期签收用真实页面、主站接口、数据库和隔离运行环境完成以下流程。场景获取 Flag 的操作由出题人或授权测试人员执行，记录只保留脱敏编号和结果。

| 验收项 | 应看到的结果 |
| --- | --- |
| 进入和报名 | 两队从正式入口报名，管理员审核；非参赛用户的操作被权限校验拒绝 |
| 配置和准备 | 选择固定场景并保存，两队各有正确环境、核心和独立 Flag；准备期间访问关闭 |
| 统一开赛 | 两队就绪后成功开赛，双方能够通过公布入口完成允许的攻防访问 |
| Flag 与 KO | 从对方核心真实取得 Flag 并提交，页面显示正确胜负和提交编号；刷新后仍一致 |
| 提交边界 | 错误、自身、跨场、旧代次及开赛前提交均无 KO；重复和并发请求只保存一个终局 |
| 金币加减 | 测试初始 100，加 30、减 20 后为 110；重复同一请求仍为 110；不足扣减保持原余额 |
| 恢复与清理 | 主站重启后状态一致；一队准备失败可查可处理；终局后访问关闭、资源回收可重试 |

金币并发另测两笔各扣 80、初始余额为 100 的请求，只允许一笔成功，余额为 20。测试商品若启用，额外验证固定价格、余额不足和重复点击；这些数字仅为验收样例。

真实验收需确认另一场测试环境仍可正常访问，清理只处理本场资源。页面检查 390、1366、1920、2560 像素宽度、日夜主题、键盘操作及减少动效设置。

后端和前端按 AGENTS.md 完成相应门禁。共享契约、迁移、认证、金额和终局并发需要数据库及跨模块验证。结果记录对应的提交、场景版本、场次和运行代次，未执行项目明确说明。
