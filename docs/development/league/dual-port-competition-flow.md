# 双港调度争夺比赛背景与总流程

2026 年 9 月 21 日

本方案说明首个 Demo 的故事、目标和比赛过程。首版沿用已确认的双队核心 Flag 规则，后续玩法见第 4 节。公司名称和剧情文案采用本稿建议，场景素材在出题时细化。

## 1 故事与比赛目标

### 一次应急运输保障竞标

台风打乱了沿海运输计划，大批救援物资需要转运。东港运输公司和西港物流公司争取同一份应急运输保障合同。组织方在竞标前安排一次封闭的数字攻防演练，两队分别代表两家公司的安全团队。

双方在虚构企业环境中同时攻防，保护自己的调度核心，也寻找对方的薄弱点。旧系统留下了维护资料、遗留账号和配置疏漏，选手需要追踪线索、接近核心；防守方在公布的权限范围内调整业务账号和防护配置。

### 首版的目标

每家公司有一处核心目标。攻击方取得对方核心中的比赛凭证，向平台提交；平台校验有效并成功保存终局后，判定对方被 KO，比赛结束。核心凭证在技术上采用本场独立的 Flag。

故事中，这次行动被描述为“对方核心调度凭证失守”。首版验证的是取得正确凭证这一结果。后续若要表达“掌握调度签发能力”或“持续控制核心”，再加入对应业务操作与可信验证。

### 场景里的设施

| 设施 | 在故事中的作用 | 选手可以接触的内容 |
| --- | --- | --- |
| 业务门户 | 企业对外服务与业务入口 | 公告、业务页面、公开资料及入口线索 |
| 办公与身份服务 | 员工处理内部事务 | 虚构账号关系、权限和遗留配置 |
| 文件或维护资料库 | 保存设备与系统维护信息 | 旧文档、维护记录及通往核心的线索 |
| 调度核心 | 保存核心凭证，后续可承载调度任务 | 本场最终攻击目标 |

首版可以合并部分设施，先验证一条完整取 Flag 路线。双方使用相同目标、对应资源与操作限制，路径长度和防守成本尽量接近；具体设施数量由场景测试决定。

## 2 从进入比赛到开赛

流程概览：了解背景 → 报名审核 → 配置场次 → 准备双队环境 → 管理员开赛 → 双方攻防 → 提交核心凭证 → KO 与剧情结局 → 回收环境。

### 第一步 进入并了解任务

选手从联赛入口查看比赛详情。页面说明双港背景、本场目标、报名要求、允许的操作和胜负条件。此时可以阅读共同公开的任务说明；本场环境入口在开赛后开放，内部线索与核心凭证需要在场景中探索取得。

玩家最终要理解三件事：自己代表哪家公司，哪些内容可以操作，以及怎样取得本场胜利。

### 第二步 报名并确定双方

选手使用现有账号和战队报名，管理员审核并确定两支参赛队，将它们分配到东港和西港。本场双方都承担攻击与防守任务，使用同一套胜负规则。

两队在一场比赛中完成对抗。场景可采用不同的名称、资料和经过测试的细节变体；公平性主要通过目标、初始条件和难度测试来保证。当前首版不依赖同一场景换边重赛来平衡结果。

### 第三步 配置并准备场景

管理员选择固定场景版本，确定两队席位和初始金币，随后准备比赛。平台固定本场名单和配置，为双方建立独立环境，并向各自核心注入不同的 Flag。比赛期间沿用这一版本。

双方环境从赛前模板准备好，首版无需购买机器才能参赛。初始金币进入本场账户，先用于验证账务流程。管理员能够加减并填写原因，选手查看本队余额和流水。

准备页面显示两队各自的进度与失败原因。环境、Flag 和必要入口都确认就绪后进入待开赛。准备期间，选手访问和攻击通路保持关闭；一队准备失败时，先处理失败，再确认开赛条件。

### 第四步 管理员统一开赛

管理员点击开赛，平台记录开赛时间，并开放双方约定的访问入口。选手看到自己代表的公司、目标说明、本队允许的防守操作、对方公开入口、余额和 Flag 提交位置。

正式开赛后，双方才能访问本场攻防环境。正常运行、业务权限和比赛管理分开：选手使用公布的业务账号与防守配置，平台保留场次、核心凭证和环境生命周期的管理权限。

首版采用一次开赛到终局的流程。若故障需要重建环境，管理员先中止本场，再以新场次和新凭证重新开始。赛中暂停、阶段切换和自动到时结算随后续规则确定后加入。

## 3 双方攻防与比赛结束

### 第五步 追踪线索并保护本方核心

开赛后，两队自行分配攻击和防守精力。攻击人员从对方已开放的业务入口调查线索，尝试接近核心目标；防守人员查看自己有权操作的配置，修正允许范围内的弱点。

一条建议的故事路线是：选手在对方门户发现旧维护系统的线索，进入场景内的资料区，逐步获得访问调度核心所需的信息，最终取得核心 Flag。具体漏洞、步骤和材料由出题人设计并测试，这条叙述用于说明体验，属于场景内容建议。

另一队同样可以从对应路线进攻。玩家的选择会影响双方进度：投入更多人查找线索，可能更快接近目标；安排成员处理已发现的配置弱点，可以增加对手推进的难度。首版通过受限业务账号和明确的操作范围控制防守力度。

### 第六步 提交对方核心凭证

选手在平台提交取得的 Flag。平台从登录和参赛关系识别提交队，校验它是否对应本场对方核心的当前运行实例与代次。

错误、自身、其他场次或旧代次的 Flag 返回无效结果。开赛前及终局后的新提交按场次状态处理。Flag 明文仅用于受保护的场景注入与提交校验，页面记录和日志使用脱敏信息。

首版由平台直接校验 Flag，成功后写入 KO。后续“完成业务目标，再由 Checker 核验”的过程属于另一种判定方式。

### 第七步 确认唯一赛果并显示结局

最先在服务器完成有效校验并成功写入终局的提交获胜。双方几乎同时提交时，以数据库成功保存终局的先后为准；重复请求沿用原结果。页面展示胜者、被 KO 的队伍、结束时间和对应提交编号。

| 本场结果 | 建议的剧情结局文案 |
| --- | --- |
| 东港获胜 | 西港核心调度凭证失守。东港在本轮攻防演练中取得优势，获得应急运输项目的优先候选资格。 |
| 西港获胜 | 东港核心调度凭证失守。西港在本轮攻防演练中取得优势，获得应急运输项目的优先候选资格。 |
| 管理员中止 | 本轮演练中止，评审结果待定。保留中止原因与已有记录，本场无胜者。 |

剧情由真实赛果触发。金币余额、临时展示信息和资源清理状态都不改变已确认的胜负。首版尚未取得有效 Flag 时继续对抗；需要结束时由管理员填写原因中止。

### 第八步 关闭访问并回收环境

终局后关闭选手访问，回收本场资源，保留赛果和必要审计记录。资源处理失败时显示待处理或可重试状态，随后继续清理。再次举办时使用新的场次、环境和核心 Flag。

## 4 后续完整玩法的方向

后续加入情报选择、资源使用和业务目标，让攻防选择影响比赛。先用双港验证，再考虑国家、战争、潜伏或重大事件改编等背景。

### 情报与能力商店

预算用于购买对方设施情报、虚构人员与社工线索、利用工具或 EXP，以及 WAF 等防护能力。设施主要在赛前布置。

购买维护资料可获得入口线索，购买 WAF 可启用已验证的防护配置。线索、工具效果和防护代价经同一场景测试后，再确定价格与额度。

### 分阶段展开故事

后续可组织成“初步调查 → 线索与能力开放 → 核心目标争夺 → 结局”的战役，按阶段说明任务和资源，成批开放预设内容。服务和镜像赛前确定。

阶段节奏与角色侧重通过试赛调整。先保留双方都能攻防，再尝试能力有所侧重的场景，比较双方完成目标的实际难度。

### 从取得凭证走向验证业务能力

后续可要求选手使用取得的权限，完成限定的模拟调度单。选手申请后，平台产生本次任务；选手执行，可信 Checker 核对效果和归属并保存结果。持续控制目标再定义时长和挑战规则。

业务可用性、任务与胜负的关系在相应赛制采用前确定。检查逻辑随场景交付，平台提供执行和结果记录能力。

### 开发会话按下面的范围理解

| 内容 | 首期采用 | 后续方向 |
| --- | --- | --- |
| 比赛目标 | 取得并提交对方核心 Flag，判定 KO | 验证业务目标，按规则决定得分或终局 |
| 参赛形式 | 固定双队，双方都能攻防 | 更多场景及经过测试的角色侧重 |
| 环境与权限 | 固定场景，受限业务账号和防守配置 | 分阶段内容，配套可用性规则后扩大防守 |
| 金币和商店 | 基础加减、余额和流水；测试商品按需 | 情报、工具、WAF 及经营机制 |
| 表现形式 | 背景说明、状态、提交和赛果页面 | 剧情阶段、观赛与回放；3D 后续，AI 独立 |

场次、队伍、配置、环境、提交与赛果使用通用比赛模型；公司名称、设施和剧情属于场景内容。首期开发以第 2、3 节的 Flag 流程为准。
