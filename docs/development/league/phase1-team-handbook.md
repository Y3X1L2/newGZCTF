# 联赛第一阶段开发分工手册

2026 年 9 月 21 日

本手册用于四人共同开发首版联赛。按一场比赛的操作顺序安排任务，说明每个人做什么、依赖什么、交给谁，以及怎样确认完成。先完成基本比赛流程和金币加减，目标仍为 9 月底左右跑通；具体工作按依赖推进。

## 1 先把一场比赛走通

主流程：进入联赛 → 报名审核 → 配置两队 → 准备环境 → 手动开赛 → 提交对方核心 Flag → KO → 关闭访问与清理。

| 步骤 | 操作和应看到的结果 | 后端对接 |
| --- | --- | --- |
| 进入 | 管理员创建场次；选手从导航进入列表和详情 | lxy |
| 报名 | 选手使用现有战队报名；管理员审核并确定两队 | lxy |
| 配置 | 管理员选择固定场景版本、初始金币；准备时固定名单和配置 | lxy；金币由 lmr 接收 |
| 准备 | 页面显示两队准备情况；环境和 Flag 均就绪后允许开赛 | lxy 调用 yhr；lmr 提供 Flag |
| 开赛 | 管理员点击开赛，双方获得允许的访问入口 | lxy 决定开赛；yhr 开放访问 |
| KO | 选手提交对方核心 Flag，页面显示胜负和提交结果 | lmr 校验；lxy 保存终局 |
| 清理 | 赛果保留，访问关闭，环境回收；失败可查询和重试 | lxy 发起；yhr 执行 |

页面和前端请求由 lcx 负责。管理员加减金币、本队余额和流水作为一条独立流程接入；金币先与胜负分开。商店后续再接，确有演示需要时增加一个测试扣费商品。

首期已确认：管理员审核两队并手动开赛；最先在服务端校验有效并成功写入终局的提交获胜；场景开放约定的业务账号和防守配置。Checker 自动业务验证、自由主机防守和复杂经营规则留到后续阶段。

### 各自承担的责任

lxy 组织整条流程、确认规则和优先级，并实现报名、配置及场次状态。yhr 负责运行接入和场景交付对接。lmr 负责 Flag 与金币。lcx 负责页面和前后端连接。各作者完成自己的测试和修复，lxy 组织整场验收。

下文 T 编号表示后端或场景任务，U 编号表示 lcx 的页面任务。每项工作可以包含多次个人提交，按一个可检查的结果交接。

## 2 开工前共同完成 T0

T0 由 lxy 组织，四人参加。交付一份简短接口约定，以及可编译、可测试的模块基础和必要的场次数据结构。共享部分合入 main 后，各人从同一基础开始实现。已有账号、战队、报名及运行能力优先复用。

lxy 先提出第 1 节的流程和需要调用的能力。下面各能力的提供者补齐接口草案，调用方检查是否够用。流程中的一步可以对应内部服务调用或已有 API，具体路径在这一步确定。

| 能力提供者 | 交给谁使用 | 先说明清楚的内容 |
| --- | --- | --- |
| lxy 场次与报名 | lcx、yhr、lmr | 场次和队伍标识、名单、状态、可执行操作、配置版本 |
| yhr 环境准备 | lxy；由场次接口供页面查询 | 准备任务编号、两队进度、就绪条件、失败原因和重试 |
| lmr 核心 Flag | yhr 注入，lxy 调用准备流程 | 场次、目标队、核心、运行代次的绑定，以及秘密材料的交付方式 |
| lmr 提交判定 | lcx 发起提交；判定调用 lxy 的终局用例 | 身份来源、正确和错误结果、重复提交、同时提交 |
| lmr 金币 | lxy 发放初始金币，lcx 调用管理和查询 | 金额单位、权限、流水编号、余额不足和重复请求 |

每项接口约定只需写明：调用者、输入、输出、失败和重试方式，并附成功与失败样例。场次状态和金额等共享字段使用同一份定义。前端开发样例与后端测试使用相同约定。

### 用准备环境的交接做一次演练

lxy 交给 yhr 场次、两队和场景版本；lmr 提供对应的 Flag 注入材料。yhr 返回准备任务编号，后续可查询每队是准备中、已就绪还是失败。已就绪包含约定的环境、Flag 和入口准备检查；选手访问仍等待开赛开放。

yhr 尚未完成时，lxy 在测试里模拟三种准备结果，验证自己的状态处理；lcx 用这些样例开发页面；yhr 用测试身份和临时生成的秘密验证真实运行接入。各人完成自己的部分，真实接口可用后一起连接验收。

依赖的接口含义还没确定时，先与提供者说明需求；接口已确定但实现未完成时，可以使用测试替身。测试替身只用于开发和测试，联调使用真实服务。

### T0 完成条件

四个人都能说明自己调用什么、返回什么、哪些状态需要等待。lxy 明确数据归属和最小公共模型；各人确认自己的第一项任务。代码基线、开发配置和现有失败同时核对，问题注明负责人。

## 3 并行完成报名 场景和 Flag

### T1 场次和报名 负责人 lxy

开始条件：T0 的场次基础和身份约定已确定。

完成场次创建、列表和详情、草稿修改、报名、审核、两队选择，以及场景版本和初始金币配置。准备时固定参赛名单和配置；管理员与选手按各自权限操作。报名接入现有账号和战队，明确报名事实由哪里保存。

交给 lcx 的 U1：可调用的接口和样例。交给后续任务：可查询的场次、参赛关系和固定配置。验收时用两队完成报名审核，刷新后记录一致；重复报名和越权操作返回明确结果。

### T2 固定双队场景接入 负责人 yhr

开始条件：T0 的运行输入与状态约定已确定，出题人提供场景素材。场景素材未齐时，yhr 负责向 lxy 说明缺什么及其影响。

yhr 与出题人确定一个固定版本、取 Flag 路线、注入位置、可使用的账号和防守配置。复用 TeamLab 完成双队环境准备、状态查询、场次与运行实例绑定，验证准备期间访问关闭、开赛时允许的访问路径及队伍隔离。部署继续使用统一队列。

报名接口未完成时，可以用测试身份调用运行底座。Flag 生成器未完成时，使用临时生成的测试值验证注入，随后与 T3 连接。平台管理凭据与 Flag 明文通过受保护通道处理，文档和日志保留脱敏编号。

交给 lxy 的 T4：真实准备接口、每队状态和访问控制能力。验收覆盖双队准备成功、单队失败、重复准备，以及允许的实际网络访问。出题人签收场景内容，yhr 负责把素材和运行结果交齐。

### T3 核心 Flag 生成与绑定 负责人 lmr

开始条件：T0 的场次、目标队、核心和运行代次约定已确定；注入位置与 yhr 对齐。

为本场每队核心生成独立 Flag，保存校验所需信息，提供给 yhr 注入。双方先约定运行编号和代次何时可得，先建立准备记录，再将注入材料与实际运行身份对应；开赛前确认绑定一致。重复准备复用有效记录，新场次或环境重建使用新值。

交给 yhr 的 T2：受保护的注入材料与绑定信息。交给自己的 T5：校验能力。先用测试目标验证隔离，再在真实核心确认注入正确；本队、跨场及旧代次材料不会被识别为本场对方核心。

### 这一批怎样同时推进

T1、T2、T3 可以各自开发和测试，lcx 同时做 U1。T2 与 T3 对齐注入方式后先做小范围联调；T1 完成后，T4 接入真实参赛数据。每项代码完成先交接，完整场景结果在连接后确认。

## 4 接通准备 开赛和 KO

### T4 场次准备与结束用例 负责人 lxy

开发时先用 T0 的接口和测试结果；真实联调需要 T1、T2、T3 可用。

管理员点击准备后，校验并固定配置，调用环境准备能力，保存操作编号并查询两队进度。两队就绪后进入待开赛；管理员开赛时与 yhr 的访问控制连接，记录统一开赛状态和时间。操作部分失败时保留可恢复记录，页面显示真实进度。

同时提供给 T5 调用的终局用例：保存胜者和结束原因，保证场次只结束一次。有效提交与 KO 结果在同一本地数据库事务中确认。管理员中止也走同一终局约束，记为无胜者，并保存后续清理意图。

交给 lcx 的 U2：准备、开赛和中止接口；交给 lmr 的 T5：终局用例。验收覆盖一队失败时保持待处理、重复开赛、服务重启后恢复原操作和终局并发。

### T5 提交核心 Flag 并判定 KO 负责人 lmr

开发需要 T3 和 T4 的终局约定；真实验收需要 T4 已开赛、T2 环境可访问。

从登录和参赛关系确定提交者，校验本场对方核心 Flag，保存提交记录，并调用 lxy 的终局用例。按已确认规则，以服务器成功写入终局的先后确定胜者；重复请求返回原结果，场次已结束时返回已有赛果。

交给 lcx 的 U3：提交和结果查询接口。lxy 与 lmr 一起验收有效提交只产生一个赛果，以及错误、自身、跨场、旧代次、开赛前和结束后提交的处理。最后由出题人或授权测试人员真实取得对方 Flag，完成整条验证。

### T6 关闭访问与清理 负责人 yhr

清理能力可随 T2 一起开发；正式触发需要 T4 保存终局和清理意图。

根据本场绑定关闭访问、回收环境，返回清理状态；失败后允许继续处理。部分准备失败或管理员中止也使用这条路径。lxy 连接终局触发，lcx 在 U3 展示清理状态。

验收时核对本场访问已关闭、资源无残留，另一场测试环境仍正常。清理失败和主站重启后能够继续处理，已确认的赛果保持一致。

这三项连接完成后，应能演示一次真实开赛到 KO，再完成环境回收。各作者检查自己负责的接口，lxy 负责组织整条流程验收。

## 5 金币和页面怎样安排

### T7 金币账户与流水 负责人 lmr

场次与队伍基础可用后即可开发；同一人的任务按 Flag 主流程优先安排。金币接口就绪后，由 lxy 在配置固定时调用初始发放，lcx 接入 U4。

每场每队一个账户，提供初始发放、管理员加减、余额和流水查询。首期采用非负整数，调整有原因和操作者；余额与流水一起保存，同一业务请求只处理一次。选手查询本队账务，管理员按权限调整；终局后普通调整停止。

测试用初始 100、加 30、减 20，结果为 110；重复原请求仍为 110。初始 100 时两笔并发各扣 80，只允许一笔成功，余额为 20。金额不足、越权和初始发放重试也要验证。

### lcx 的页面按四项推进

| 页面任务 | 需要接入的后端 | 页面完成条件 |
| --- | --- | --- |
| U1 入口和报名配置 | T1 | 正式导航可进入；创建、报名、审核、配置均能保存并回读 |
| U2 准备和开赛 | T4 对外接口，内部连接 T2/T3 | 显示每队真实状态；条件满足后可开赛，失败原因可见 |
| U3 提交和结果 | T5、T4；清理查询由 T4 对外提供 | 可提交 Flag、查看 KO 或中止结果及清理状态，刷新后一致 |
| U4 金币 | T7 | 管理员可加减，选手看到本队真实余额和流水 |

lcx 在接口约定完成后可先用开发样例做页面，按 U1、U2、U3、U4 逐项连接真实后端。使用 vNext 页面结构、语义样式和业务 API 适配层，界面只展示当前用户有权查看的信息。

### 接通顺序

先做 T0，然后并行推进 T1、T2、T3 和 U1。T1–T3 可用后，把 T4 与 U2 接起来；随后接 T5、T6 和 U3。T7 可独立推进，U4 在账务接口可用后接入。

T4–T6 的独立代码和测试可以提前开发；这里列的是完成真实流程的依赖顺序。lmr 同时负责 Flag 和账本，lcx 同时负责各页面，个人任务按上述优先级安排。

第一批直接领取：lxy 做 T0 并推进 T1；yhr 对齐 T0 的运行约定并做 T2；lmr 对齐 Flag 约定并做 T3；lcx 会审页面所需字段并做 U1。接口缺口及时找提供者确定，lxy 协调影响多人的决定。

## 6 只保留必要的协作步骤

### 一张任务卡就够

用 GitHub Issue 记录任务，可以直接使用本手册的编号。保留负责人、交付内容、前置任务和验收方法，开发时补充状态及关联 PR。需要总览时加一个看板：待做、开发中、待联调、已完成。遇到等待，写明等哪个任务和谁处理。

例如：T2，yhr 负责；交付真实双队环境和状态查询；依赖 T0 与场景素材；按第 3 节验收。个人代码通过检查后可交接，整条流程通过后再确认功能完成。

### 个人提交和团队合并

各任务从最新 origin/main 建立独立 codex 分支和 worktree。开发者按需要提交自己的进展。一项可验证的工作完成后，合并请求写清三件事：改了什么、怎样验证、还有什么依赖或限制。

合并前同步最新 main，由一位同伴看改动和测试；接口变化请调用方一起看。lxy 安排依赖和合并顺序，lmr 替补。lxy 与 lmr 互审；lcx 页面由 lxy 看，金额与提交调用由 lmr 看；yhr 的运行接入由 lxy 看，Flag 交接由 lmr 看。

完成部分先合入并保持未完成入口关闭，真实接口接通后联合验收。合并后的代码可以用于开发和测试；对外开放与部署单独安排。

### 接口和数据库变动时多做一步

改接口前告诉调用方改了哪个字段或状态含义，并更新共同样例。lcx 从本次真实后端契约重新生成客户端，随后检查页面调用。

数据库模型可以分工开发，正式迁移由 lxy 排顺序。前一笔合入后，后一人同步主线、生成并核对自己的迁移与完整模型快照，带上读写代码和测试。已共享或已应用的迁移保留，后续修正追加前向迁移。每人使用独立开发库、端口和测试资源，共享联调库使用合并后的版本。

### 首期签收

1. 用管理员和两队账号，从创建、报名、配置实际走到准备与开赛；两队只获得约定的访问权限。
2. 真实取得对方 Flag 后提交，保存唯一 KO；错误、重复和并发提交按规则处理。
3. 金币加减及流水一致，权限、余额不足和并发扣费结果正确。
4. 中止、准备失败、主站重启和清理重试可处理，赛果可回读，本场资源完成回收。
5. 前端连接真实接口，检查常用宽度、日夜主题、键盘操作；按 AGENTS.md 执行影响范围内的测试，记录未执行项。

验收记录只需保存版本、已验证流程和遗留问题，附必要的脱敏证据。运行接入依据见[TeamLab 对接文档](../../commercialization/teamlab-integration-guide.md)，代码与质量边界见[项目协作规范](../../../AGENTS.md)。
