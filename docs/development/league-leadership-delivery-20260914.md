## 2. 今晚应该交什么

### 2.1 平台产品说明

建议文件名：`01 隐喻平台产品说明 V0.1.docx`；正文约 3–5 页，读者是领导、教师和合作方。

1. 产品定位：服务安全培训、日常练习和赛事组织，统一管理账号、内容、实验环境和学习竞赛结果。
2. 培训：课程、章节资源、报名与教师管理、实验、课后理论、学习进度；说明教师和学员分别得到什么。
3. 练习：题库筛选、题目附件、独立实例、Flag 提交与练习记录；说明来源导入与内容可见性。
4. 比赛：CTF、理论考试、AWDP、TeamLab 相关赛场；说明现有赛制差异，联赛单列为后续建设。
5. 支撑：Docker/KVM、模板、节点、统一队列、组网、开放接口与审计；用业务语言说明用途。
6. 能力状态表：区分“源码已有”“某环境已有验收记录”“目标环境仍待验收”“计划新增”。

开头可直接写：

> 隐喻平台面向安全教学与演练，提供培训课程、自主练习和赛事组织能力。教师可以组织课程与实验，学员可以练习题目和提交答案，赛事组织者可以配置比赛、管理参赛队伍并查看结果。平台通过统一的镜像、节点和运行队列管理实验环境。数字攻防联赛拟作为新业务模块接入，复用现有内容与运行能力，并新增经营账本和联赛裁判规则。

写到什么程度：领导读完能回答平台给谁用、学练赛各能做什么、哪些功能还有使用限制。联赛和 AI 教学应标为待建，未经实测的性能应标为目标。

### 2.2 平台使用手册

建议文件名：`02 隐喻平台使用手册 V0.1.docx`；建议 8–12 页，以跑通关键流程为先，不追求一晚覆盖所有管理按钮。

每个流程使用同一结构：**角色和前提 → 页面入口 → 操作步骤 → 成功结果 → 常见失败及处理**。截图必须取自实际目标环境，标注版本与角色；拿不到截图时使用准确的文字步骤并记录待补截图，不制作假的操作结果。

| 必须覆盖的流程 | 当前源码注册入口 | 手册应呈现的完成结果 |
| --- | --- | --- |
| 登录与身份 | `/account/login` | 登录后进入相应页面；解释未登录、无权限和账号状态问题 |
| 学员参加培训 | `/training`、`/training/courses/:courseId` | 报名状态可见，进入已获准章节，阅读资源并完成实验或理论任务 |
| 教师组织培训 | `/training/courses/new`、课程编辑与章节编辑页 | 保存后重新打开，能看到课程、实验和学员管理配置；按该角色的实际权限写步骤 |
| 日常练习 | `/practice/browse`、`/practice/challenge/:id`、`/practice/stats` | 找题、读题、启动适用实例、提交并查看结果，结束后释放实例 |
| 队伍参加 CTF | `/teams`、`/games/:gameId/challenges`、`/games/:gameId/scoreboard` | 组队与报名通过，完成一道题，查看提交状态及榜单 |
| 组织比赛 | `/admin/games`、`/admin/games/:gameId/challenges` | 保存后能重新查看比赛、题目、参赛审核和赛程配置；按钮名称以当前页面为准 |
| 理论考试 | `/games/:gameId/theory` | 获取试卷、保存草稿、正式提交、按开放规则查看结果 |
| AWDP 与组网入口说明 | `/games/:gameId/awdp`、`/games/:gameId/pentest`、`/admin/teamlab` | 说明适用条件与专项手册入口；不把仍待实机验收的流程承诺为普遍可用 |

练习章节的写作样例：

1. 学员登录，进入“自主练习”，按分类或难度筛选并打开一道可见题目。
2. 阅读题面与附件。需要容器的题目提交启动请求后，查看排队及实例状态；排队期间还不能使用环境。
3. 等待页面返回真实可用入口，再按题面操作。将答案填入 Flag 提交区，以服务器判定结果为准。
4. 查看练习记录；不再使用时执行销毁，再查询是否已销毁。创建失败时记录题目和任务标识，由管理员检查队列、节点与镜像状态。

以上样例按源码流程编写，正式手册仍需用所选交付环境走查实际按钮文案、权限与截图。

## 3. 以 V1.2 正文整理联赛规则

依据为《数字攻防联赛 赛事设计稿 V1.2 经营攻防清晰版》的第 1–8 节。下表是材料中已经写出的规则，不代表当前平台已经实现或赛事参数已经获最终批准。

| 规则 | 设计稿要求 | 需要开发什么 |
| --- | --- | --- |
| 组织与时序 | 建议 4 队邀请赛；单场两队；0–10 分钟构建，10–90 分钟自由攻防，90–100 分钟清算/VAR | 赛程与单场时钟、阶段转换、核心清单冻结、访问策略和操作冻结 |
| 胜负 | 核心 KO 优先；未 KO 比最终金币；同币加时 5 分钟，再同币判平 | KO 与最终清算状态机；加时与 VAR 时间关系待定 |
| 联赛积分 | KO 胜 3、金币胜 2、平局各 1、负 0；同分依次比较 KO 胜场、金币净差、核心平均可用率 | 单场赛果映射至联赛排名；健康度不是单场第三层判胜条件 |
| 经济 | 初始 3000 金币；每 10 秒结算；三档业务价格 800/1400/2200，满健康收入 20/14/10，残值上限 20%/40%/70% | 同一账本记采购、收入、奖励、恢复、退款和清算；残值公式仍需确定 |
| 配额与就绪 | 产币业务最多 2 个；攻击机最多 2 台；同类防御最多 1 个；部署及恢复连续检查 30 秒通过后产币 | 服务“启动可用”和“满足产币条件”分别表达 |
| 后程加价 | 60–70 分钟加 20%，70–80 加 40%，80–90 加 60%；覆盖新增购买与付费恢复 | 冻结价格版本；阶段边界、取整和加时价格要补充 |
| CTF 支线 | 初中高任务奖励 200/350/500；每队每任务一次 | 复用内容与判题，联赛按队伍发金币，不能使用个人练习完成记录直接领奖 |
| 非核心攻破 | GetShell 需交互会话与动态证据；奖励 150；同一设施每场只奖一次；被攻破后停产 | 验证器、奖励去重、健康与生产状态关联；恢复不能重置奖励标识 |
| 核心 KO | 权限与非破坏业务写入证明，再每 10 秒随机挑战，共 6 次；任次失败中断，证据一致确认 KO，低置信度 VAR | 证据关联、持续挑战、失败中断、人工裁决；仅 WebShell、停机或扫描命中不算 KO |
| 攻防边界 | 10 分钟起已购攻击机自由访问对方公开业务面，无审批、冷却和路线限制；资产及工具仅来自平台 | 开放业务面仍受队伍隔离和管理面保护；不出售 EXP、漏洞或自动攻击结果 |
| 观看与审计 | 选手按本队与允许发现目标可见；裁判实时全局；观众延迟 60 秒；敏感字段脱敏 | 服务端按这三类角色筛选返回数据并校验权限；只在前端隐藏数据会泄露信息 |
| 验收与冻结 | 服务/攻击机 30 秒内可用；至少 50 场盲测，双方胜率 45%–55%，服务净值差不超过 10%；KO/Checker 赛前 14 天冻结，价格等提前 7 天冻结 | 都是建设目标，需约定硬件、镜像、并发、计时起点、样本与计算方法后验证 |

### 5.1 一条合格需求的写法

**L04.02 购买扣款与失败退款**

1. 使用条件：已批准参赛队伍，在允许购买的阶段，从冻结版本商店购买尚未超过配额的资产。
2. 输入：场次、商品版本、数量、幂等请求标识。队伍和操作者以认证身份与参赛关系推导，价格由服务器计算，拒绝客户端指定金额。
3. 处理：校验阶段、余额和配额；在数据库事务内记录唯一购买事实、扣款及持久化部署意图，随后通过现有运行能力推进。不能把数据库事务声称为覆盖远端容器部署的跨机原子事务。
4. 输出：交易标识、扣款后余额、资产状态、异步 operation/队列关联；收到受理结果后，还要继续查询部署是否成功。
5. 异常：同请求同参数返回原交易；同标识不同参数拒绝；余额不足不扣款；明确部署失败后只补偿一次。网络超时状态未知时先查询实际运行状态，避免既退款又留下可使用资产；迟到成功须按既定补偿规则回收或完成交易。
6. 验收：余额 3000，基础价 800，同一请求并发重试只扣一次；五笔不同的 800 请求并发最多三笔成功，余额 600；失败资产只退一次，不超额占用配额；主站重启可继续处理；赛事终局后新请求被拒绝。

这里采用基础价是测试前提，不表示加价阶段仍收费 800。正式接口字段和错误码由负责人与接口维护者确认，不能把本稿示例当作已发布 API。

### 5.2 模块之间怎样调用和交接

```text
联赛页面 → 联赛 Contracts/Application → 场次规则与金币/赛果
                                  → 题目快照与判题适配
                                  → Runtime/TeamLab 公共能力 → Agent
                                  → Checker/证据适配 → 裁判结论
                                  → 授权事件投影 → 裁判/观众界面
```

联赛拥有金币、赛制、奖励领取、核心登记与裁决事实；内容模块拥有源题和镜像资产；运行底座拥有部署与资源事实。数据库是业务事实源，Redis 只做协调/缓存。新增 League 模块前，须评审并更新允许依赖矩阵与架构测试；本稿不提前给未注册模块放宽依赖权限。

题目与裁判只返回可验证结果，金币仅由联赛账本根据规则写入。共享题目定义可以复用，正式 Flag、实例、提交、比赛结果和个人学习进度不得混用。单体内部使用 application contract；跨部署边界使用版本化 API，同进程调用无需额外绕 HTTP。

各任务包至少约定：身份与授权范围、`matchId/teamId` 与资源映射、内容/规则版本、请求幂等标识、事件 ID 和时间、runtime 代次、结果状态、错误、重试语义、证据引用。观赛脱敏命令与裁判证据分开管理，不将 Flag 或凭据写入普通日志。跨服务部署失败后，服务端按已保存的操作记录重试或补偿；前端以查询结果为准，不能用等待时间判断成功。

## 6. AI 教学与外部场景如何写进需求

通话 01:07–01:24 点名 AI 教学及普通/流量侧接入，02:42–03:11 提到将另发场景资料。现有附件没有该额外场景包、AI 服务协议、部署地址或数据字典；以下是供对接讨论的建议，不把这些资料假定为已经具备。

1. **普通教学接入**：从课程、题目或实验页面进入教学辅助；服务端根据用户权限提供允许使用的题面、学习上下文与会话标识，接收答疑或提示。约定模型/服务供应方、鉴权、返回流、超时、取消、额度、教师可见范围与答案开放策略。最小验收包含正常问答、无权限题目拒绝、服务不可用提示。
2. **流量侧接入**：将授权实验的流量摘要、事件或限定 PCAP 引用提供给教学分析服务，返回证据位置、分析结论和建议。约定采集点、协议、数据时窗、脱敏、大小限额、保留时间与报告归属。最小验收包含报告能回指实际证据、无数据时明确提示、不同队伍不可交叉读取；不能把有抓包接口当作已有 AI 分析。
3. **外部场景接入**：对接方提交镜像/制品摘要、运行依赖、网络拓扑、服务端口、启动健康条件、参数、生命周期和可采集指标。平台校验资源与权限后适配 Runtime/TeamLab，返回异步状态。使用合格样例完成创建、访问、观察、重置、失败、销毁，不能只有嵌入一个外部页面的效果。

建议首期先确定普通教学接口和流量证据格式，流式分析、3D 与正式赛事内 AI 辅助是否启用分别评审。教学数据复用不代表正式比赛允许 AI 获取隐藏 Checker、Flag 或对手情报。
