# TeamLab 比赛环境仿真测试计划

制定日期：2026-09-17

测试基线：生产服务器当前部署版本 `2c1e14ed5f94cbdb795c473662c8c08b1ff1e1f1`

正式测试时长：2 小时

## 1. 测试目标

本次测试不是重复接口压测，也不是用一批相同的轻量容器证明“能够创建资产”。测试环境按一场小型真实比赛组织，两支队伍同时使用各自的混合组网环境，裁判在同一时间执行管理、审计、运维和网络操作。

测试需要回答以下问题：

1. 两支队伍的混合环境能否通过正式调度、部署队列和 Agent 执行面完整创建并稳定运行。
2. Docker、Linux VM、Windows VM 和 Modbus 设备模板能否在同一拓扑中正常通信、隔离、运维和回收。
3. 选手持续访问、Flag 提交、裁判查询、抓包、链路策略和远程运维同时发生时，平台是否保持正确和稳定。
4. 运行状态、数据库事实、Agent 现场资源、OVN/OVS 网络和选手实际访问结果是否一致。
5. 资产热更新是否真正完成新增、替换、移除和网络状态更新，未涉及的资产是否保持可用。
6. 两小时持续运行中是否出现性能退化、状态卡死、资源泄漏、跨队访问或错误计分。

所有结论必须来自正式 API、真实资产、真实网络流量和现场资源检查。接口返回成功不能代替资产可访问，页面显示正常不能代替 Agent 现场状态正常。

## 4. 框架设计

测试框架采用一个独立的 Python 进程，不引入 Grafana、Prometheus Server、ELK、Locust、消息队列或新的数据库。

目录规划：

```text
scripts/validation/teamlab-match/
  runner.py              测试入口和阶段编排
  scenario.json          资产、角色、负载和时间线
  Dockerfile             固定运行依赖
  web/                    单页实时看板
  probes/                 HTTP、TCP、SSH、RDP、Modbus 探测
```

框架使用 `asyncio + aiohttp` 完成 API 调用、并发访问、SSE 看板和实时汇总。SSH、RDP、WireGuard 使用容器内现成的系统客户端，Modbus 使用原始 TCP 报文验证，不再引入第二套测试服务。

框架以临时容器运行，限制为 1 个 CPU 和 512 MiB 内存。容器只为两支队伍建立独立 WireGuard 网络命名空间，具备 `/dev/net/tun` 和 `NET_ADMIN`，不挂载 Docker、libvirt 或平台数据库套接字。看板默认监听 `19090` 端口。

### 4.1 控制链路

框架通过平台正式入口完成：

- 管理会话：创建测试比赛、队伍、参赛关系和 Penetration 绑定。
- Open API：创建控制范围、拓扑、发布版本、运行环境、抓包、链路策略、远程会话和独立热更新环境。
- 选手会话：读取工作区、创建访问授权、提交 Flag 和查询计分板。
- 节点接口：读取心跳、Fabric、Agent 版本、资源使用和调度结果。

框架不直接写 PostgreSQL，不直接创建业务容器或 libvirt 域，不调用 Agent 内部接口代替平台流程。

### 4.2 数据保存

框架在内存中按 5 秒窗口聚合数据，只落盘以下内容：

- 阶段开始、完成和状态变化；
- 失败请求和失败操作的必要上下文；
- 每 5 秒一条性能与资源汇总；
- 测试资源 ID、镜像摘要、Agent SHA 和调度结果；
- 抓包文件摘要、关键流量验证结果和清理结果。

同一错误按“错误码 + 阶段 + 资源”合并，记录次数、首次时间、最后时间和一条代表证据。正常访问不逐条写日志。

## 5. 比赛资产设计

每支队伍拥有 20 个资产，两支队伍使用相同发布版本，但运行环境、地址、Flag、访问授权和运行事实完全隔离。

| 类型 | 每队数量 | 镜像或用途 |
| --- | ---: | --- |
| 真实 CTF Docker 服务 | 8 | 模板 53、54、56、57、58、59、60、46 |
| 确定性业务服务 | 6 | Python HTTP、Node HTTP、原始 TCP，各 2 个实例 |
| 队内流量客户端 | 2 | HTTP/TCP/SSH/Modbus 访问和固定流量生成 |
| Modbus PLC | 2 | `yinyu/modbus-plc:1.0.0` 设备模板 |
| Linux VM | 1 | 模板 115，Ubuntu 24.04 |
| Windows VM | 1 | 模板 1，Windows Server 2022 |

模板 53、54、56、57、58、59、60、46 在正式准备阶段各执行一次短启动检查，确认实际监听端口、健康结果和动态 Flag 行为。任一模板不满足要求时，使用同技术栈的确定性测试镜像替换，不在正式两小时中临时修镜像。

拓扑包含入口区、服务区、核心区和工控区四个网段，通过受管路由连接。入口区可以访问授权服务，工控区只能经核心区到达；没有连接关系的路径必须不可达。两支队伍之间任何地址和服务均不得互通。

## 6. 热更新验证环境

比赛运行环境由 rollout 管理，当前产品明确拒绝直接调用运行时热更新接口。因此本次不把比赛环境伪装成可热更新环境。

测试期间另外运行一个小型直接运行环境：

- 初始资产：2 个 Docker、1 台 Linux VM、1 台 Windows VM；
- 目标版本：新增 1 个 Docker、替换 Linux VM、移除 1 个 Docker；
- 网段、路由和基础设施保持不变；
- 使用正式预览接口确认差异，再提交正式热更新操作；
- 验证 `PlanRevision` 增加、运行代次不变、OVN 端口更新、未涉及资产持续可达。

报告中分别给出“比赛 rollout 链路”和“直接运行环境热更新链路”的结果，不混写为同一能力。

## 7. 自动化角色

### 7.1 选手

每支队伍模拟 25 名选手。每个选手循环执行真实业务动作，而不是反复请求同一个健康接口：

- 登录并读取比赛工作区；
- 通过本队 WireGuard 访问 Web、TCP、SSH、RDP 和 Modbus 服务；
- 完成查询、登录、读写寄存器等有状态操作；
- 从目标服务取得动态 Flag 并通过 `/api/pentest/games/{gameId}/submit` 提交；
- 混合正确、错误、重复和跨队 Flag，核对判定与计分；
- 查询计分板，确认两队成绩和提交事实一致。

平稳阶段每名选手每 1 至 3 秒执行一次操作。每 15 分钟进行 60 秒突发阶段，将并发选手数提高到每队 50 人。请求类型按资产权重分散，避免单个服务成为唯一瓶颈。

### 7.2 裁判

裁判模拟器持续执行以下操作：

- 查询两队运行状态、事件、资产、设备健康和流量；
- 应用并恢复时延、丢包和断链策略；
- 启动、停止和下载抓包，验证已知 HTTP、TCP 和 Modbus 流量；
- 停止、启动、重启、暂停和恢复指定资产；
- 创建 SSH、RDP、VNC 会话并结束会话；
- 生成和下载操作审计证据，核对摘要；
- 执行运行状态检查，核对平台状态与现场资源；
- 在指定阶段重启一个 Agent 服务，观察心跳和状态收敛。

节点和资产操作始终通过现有调度、部署票据和平台接口完成。测试框架不替平台决定资产放置。

## 8. 自动监控和故障记录

框架直接读取现有指标，不建设新的监控系统。

| 数据 | 采样方式 | 频率 |
| --- | --- | ---: |
| API 延迟、状态码、吞吐 | 框架请求计时 | 实时，5 秒汇总 |
| 资产访问延迟和成功率 | 选手探测结果 | 实时，5 秒汇总 |
| 节点 CPU、内存、容器、VM | 节点管理接口 | 5 秒 |
| Agent、Fabric、心跳 | 节点管理接口 | 5 秒 |
| 运行状态、票据和阶段 | 轻量运行状态接口 | 运行中 10 秒，状态变化时 2 秒 |
| 流量和路径 | TeamLab 流量接口 | 15 秒 |
| Flag 和计分 | Penetration 提交及计分板 | 每次提交后 |
| 平台指标 | 现有 `/metrics` | 5 秒 |

故障按固定规则归类为部署失败、数据面失败、Flag/计分错误、权限隔离错误、状态不一致、Agent 不可用、性能超限和清理残留。出现异常时才采集关联运行事件和相关服务最近日志，不持续复制完整 journal。

实时看板只显示：

- 当前阶段、已运行时间和剩余时间；
- 两队运行状态、正常资产数和异常资产数；
- 请求速率、成功率、P50、P95、P99；
- Flag 正确、错误、重复和跨队拒绝数量；
- 每队流量、延迟、丢包和访问失败；
- 节点 CPU、内存、容器、VM、Agent 和 Fabric 状态；
- 热更新、抓包、远程会话和审计状态；
- 聚合后的故障列表和发生次数。

## 9. 两小时时间线

| 时间 | 测试内容 |
| --- | --- |
| 0–10 分钟 | 创建比赛、两队运行环境和独立热更新环境，验证 44 个资产实际就绪 |
| 10–35 分钟 | 平稳访问、动态 Flag 提交、计分和网络隔离 |
| 35–50 分钟 | 访问突发、链路时延和丢包策略、策略恢复 |
| 50–65 分钟 | 抓包、流量路径和 Modbus 读写 |
| 65–80 分钟 | 独立运行环境新增、替换和移除资产 |
| 80–95 分钟 | SSH、SFTP、RDP、VNC、文件操作和操作审计 |
| 95–105 分钟 | 重启一个 Agent，验证工作负载、心跳和状态恢复 |
| 105–115 分钟 | 恢复后的持续访问、状态检查和最终一致性检查 |
| 115–120 分钟 | 停止比赛、销毁环境、检查残留并生成报告 |

故障操作有固定开始和结束时间。其影响窗口从正常可用性统计中单独标记，但恢复时间和影响范围必须进入报告。

## 10. 通过标准

### 10.1 功能与正确性

- 两队各 20 个资产均通过正式调度和部署队列创建。
- Docker、Linux VM、Windows VM 和 Modbus 均有真实服务验证，不以进程存在代替可用。
- 正确 Flag、错误 Flag、重复 Flag和跨队 Flag 的判定 100% 符合预期。
- 两队之间不能访问对方资产、授权和运行事实。
- 链路策略只影响选定网段或资产，恢复后访问恢复正常。
- 抓包文件包含预先生成的已知流量，摘要与下载结果一致。
- SSH、RDP、VNC、文件操作和操作审计形成完整闭环。
- 热更新完成后发布版本、资产、计划修订和 OVN/OVS 现场状态一致。
- 不允许数据库显示成功而 Agent 现场未生效，也不允许现场成功而平台长期停留在处理中。

### 10.2 性能与稳定性

- 正常阶段资产访问成功率不低于 99.5%。
- 控制面读取请求 P95 不高于 200 ms。
- 写操作受理 P95 不高于 500 ms。
- 业务 5xx 比例低于 0.1%，未知错误码为 0。
- 突发阶段不出现持续队列积压、数据库死锁或 Agent 执行槽饿死。
- Agent 重启后 60 秒内恢复心跳和现场状态读取。
- 热更新期间未涉及资产的访问成功率不低于 99.5%。
- 两小时内无进程崩溃、状态卡死、跨队串流量和无界资源增长。

### 10.3 清理

运行环境销毁后，必须确认以下资源没有本轮残留：

- Docker 容器和网络命名空间；
- libvirt domain、overlay 和 seed 文件；
- OVN logical switch、port、router 和 OVS 接口；
- WireGuard 授权和路由；
- 公网端口租约和转发规则；
- 抓包进程、PCAP 暂存和远程会话；
- 活动部署票据、容量预留和连接器租约。

任何残留均判定本次测试失败，不能通过手工删除后改写为通过。

## 11. 测试报告

框架结束后自动生成 HTML 和 JSON 两份报告。报告至少包含：

1. 测试版本、Agent SHA、节点能力、镜像摘要和场景修订。
2. 两队资产与实际调度分片，不预设节点分布。
3. 功能结果矩阵和失败证据。
4. API 与资产访问的吞吐、成功率和延迟分布。
5. 节点资源、队列、流量和异常时间线。
6. Flag 提交、计分、跨队隔离和审计结果。
7. 热更新前后资产、计划修订和现场网络差异。
8. Agent 重启影响范围和恢复时间。
9. 销毁后的残留检查结果。
10. 按严重程度排列的问题、复现步骤和建议修复位置。

报告中的“通过”必须对应机器可复核的证据；没有执行、条件不足和执行失败分别标记，不使用“基本正常”“理论可用”等含糊结论。

## 12. 实施顺序

1. 修复 `.27` Fabric，完成三个 Agent 的版本同步和能力核对。
2. 构建测试框架、确定性测试镜像和 Modbus 设备模板。
3. 完成一次不超过 10 分钟的短流程检查，只验证框架、账号、镜像和清理链路。
4. 清理短流程资源后，执行一次正式两小时测试。
5. 输出报告并保留证据目录；测试运行环境全部销毁，比赛和控制范围按审计需要归档。

不反复重建环境或重复跑整套测试。短流程只排除框架自身错误，正式结果以唯一一次两小时运行记录为准。

## 13. 实施进度

2026-09-17 已完成轻量测试框架第一版，代码位于 `scripts/validation/teamlab-match/`：

- 单进程完成阶段编排、两队常态/突发并发、HTTP/TCP/Modbus/API 动作和状态采样；
- 同一进程提供 `19090` 实时看板，显示进度、吞吐、成功率、延迟、队伍结果、节点/运行状态和聚合故障；
- 测试结束生成 JSON 与 HTML 报告，凭据和真实资源 ID 由环境变量注入；
- 本地短流程自动测试已验证 API 调用、真实 HTTP 探测、监控字段摘取、阶段结果和报告生成。

框架完成不等于比赛测试完成。生产场景参数、设备模板登记、镜像分发、44 个资产短流程和正式两小时运行仍按第 3、12 节依次执行。
