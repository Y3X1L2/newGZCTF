# TeamLab API P3 并发定位与优化记录

日期：2026-09-15

候选分支：`codex/teamlab-api-product-integration`

代码基线：`b7f4df4`

## 1. 测试范围

本轮只测 TeamLab 控制面本身，不把镜像拉取、容器启动或 VM 启动速度算入 API 性能。常驻环境由一个 API 实例、PostgreSQL、Redis、Registry 和 Guacamole 组成，地址为 `http://127.0.0.1:18080`。Docker Engine 为 29.4.0，分配 16 个 CPU、约 15.4 GiB 内存。

固定使用三份拓扑数据：80 个 Docker 资产、100 个 Docker 资产和一份并发修改拓扑。负载包含拓扑读取、校验、计划计算和同一修订并发写入，四个受限 Token 共同发起请求。

## 2. 找到的问题

优化前，同级 600 req/s 负载实际完成 592.87 req/s，总 P95 为 323.56 ms，80/100 资产计划 P95 分别为 571.16 ms 和 573.42 ms。主要耗时不在拓扑算法，而在请求进入和数据访问链：

- API Token 请求同时经过网页/IP 全局限流和 Token 自身限流；
- 每个外部 API 请求单独创建数据库事务写审计；
- Token 校验反复读取不变的密钥摘要、scope 和资源授权；
- 控制范围的存在性与授权分两次查询；
- 校验和计划反复读取、解码同一修订或不可变发布版本；
- 计划接口重复检查拓扑授权和发布版本授权。

压测脚本原先还按请求速率等量预建 VU，会在启动阶段制造与业务负载无关的连接突发；同资源并发写入只看 HTTP 受理结果，没有等待后台 operation 的最终状态。

## 3. 修改内容

- API Token 请求只执行 Token 自身的限流，不再叠加网页/IP 全局限流。
- 外部 API 审计按最多 256 条或 20 ms 批量写入，队列满时对请求形成反压，不丢审计记录。
- Token 的撤销、过期和创建者角色仍逐次读取，确保撤销和降权立即生效；只有不可变元数据进入进程内缓存。
- 控制范围存在性与资源授权合并为一次数据库查询。
- 拓扑校验按 `TopologyId + Revision` 短暂缓存；不可变发布版本执行定义和短周期容量快照分别复用。
- 计划接口删除重复的拓扑 scope 查询，仍验证发布版本 scope 以及拓扑与发布版本的对应关系。
- PostgreSQL 连接池不降低上限，只把未显式配置时的空闲连接回收时间设为 60 秒。
- k6 按负载需要配置 VU，并等待两个并发 operation 到达最终状态。

## 4. 优化后结果

20 秒综合负载共完成 12,188 个请求，实际吞吐 600.07 req/s：

| 请求 | P95 |
| --- | ---: |
| 全部请求 | 11.87 ms |
| 80 资产拓扑读取 | 12.83 ms |
| 100 资产拓扑读取 | 12.94 ms |
| 80 资产校验 | 7.04 ms |
| 100 资产校验 | 7.17 ms |
| 80 资产计划 | 11.74 ms |
| 100 资产计划 | 7.94 ms |

本轮没有 5xx、429、请求中断、数据库死锁或临时文件。11 个 dropped iterations 集中在启动阶段，没有形成持续积压。压力结束后数据库连接能够回收，未再出现 `too many clients`。

综合负载运行时，本地节点尚未配置 TeamLab 调度能力，因此计划请求按产品规则返回 `409 capability_unavailable`；该响应覆盖了鉴权、版本读取、容量读取和拒绝路径，不作为成功放置证据。补齐稳定控制面容量节点后，另各执行一次真实成功计划：80 个资产返回 80 个资产、1 个分片，100 个资产返回 100 个资产、1 个分片，均为 HTTP 200。

同一修订的两个并发写操作最终一项成功，一项以 `topology_revision_conflict` 失败，说明后台 operation 的修订冲突语义正确。修复过程中发现 Npgsql 无法翻译查询中的 `Guid.ToString("D")`，已改为可翻译形式并重新验证。

## 5. 结论与边界

在上述单实例、本地 Docker Desktop 和 80/100 资产数据规模下，控制面已稳定承受约 600 req/s 的混合读取、校验、计划和冲突写入负载，总 P95 从 323.56 ms 降至 11.87 ms。改动没有通过压低数据库连接池上限换取结果，也没有引入撤销延迟、异步消息系统或新的调度队列。

本结果说明当前热点已经消除，不代表生产 SLA，也不代表 100 个容器可以在这台本地机器上同时运行。80/100 资产成功计划验证的是控制面容量计算；真实数据面吞吐仍应按生产 Worker 的 CPU、内存、镜像和网络容量单独评估。
