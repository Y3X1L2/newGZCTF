# TeamLab API 完善、产品修正与独立运行计划

## 1. 本次任务与后续目标

本次形成实施计划，并完成第一轮 P0 API 静态源码审查；不启动 Docker 测试，不修改或部署业务服务。

后续工作要交付三个结果：

1. 外部系统能通过稳定 API 使用平台承诺开放的能力，完成从准备资源到操作结束的完整流程。
2. TeamLab 的现有功能和近期改动经过本地实际运行；界面、接口结果和节点执行结果相符，用户能够看懂并完成操作。
3. TeamLab 可以作为独立产品安装运行，原平台通过 API 使用它。独立产品不依赖平台的比赛、课程、计分和用户业务表。

API 审查覆盖整个项目；独立拆解以 TeamLab 及其必需的通用运行能力为范围。其他业务模块继续留在平台，需要调整的是它们与共享运行能力的调用边界。

### 1.1 开发原则

- 从用户要完成的事情定义功能。每项配置都应说明用途、默认行为及适用条件；能从已有资源取得的信息，优先让用户选择。
- 简单同步操作直接返回结果。部署等长操作继续使用现有任务和部署队列，不再增加平行状态机。
- 同一业务规则放在一个明确位置。接口负责输入与授权，应用服务负责业务，数据库负责必要的唯一性和事务约束；不在各层重复同样的检查和重试。
- 失败要有真实原因和适用的下一步。部分执行失败时处理已经修改的资源，不能把失败包装为成功。
- 保留必要的资源归属、版本冲突和操作互斥规则。这些直接关系到并发正确性；实现时复用现有机制，不建设通用“防御框架”。
- 功能相近时先整理入口与职责，再判断是否需要新增。没有独立使用价值的设置应删减，不靠说明文字维持冗余设计。
- 测试以脚本完成实际流程。浏览器只检查界面行为与显示结果，不用人工逐页点击承担整个验收。

## 2. API 底座应达到的标准

### 2.1 用完整操作流程检查接口

不能只统计接口数量或检查 Swagger 是否能打开。对每个正式功能，都要回答以下问题：

| 检查环节 | 必须能够完成的事情 |
| --- | --- |
| 调用准备 | 安装后能建立调用身份、获得授权、查询能力和必要配置，不依赖开发者手工改数据库 |
| 资源发现 | 能查询可用资源、名称、稳定标识、状态及限制，创建请求中的引用能通过 API 找到 |
| 创建与编辑 | 必填、默认值、单位、范围明确；前端没有独占的业务计算或隐含默认参数 |
| 异步执行 | 受理后能找到任务，查询阶段、结果、错误和关联资源；断开连接后仍能继续查询 |
| 读取与管理 | 能列出、筛选、分页、查看详情和执行产品允许的后续操作 |
| 文件与连接 | 上传、下载、终端和图形会话具备完整调用说明；拿到会话 ID 后有实际连接办法 |
| 失败处理 | 能分清输入错误、权限问题、当前状态不允许和执行失败；适用的恢复动作可通过 API 完成 |
| 结束与清理 | 可以停止、撤销、销毁或归档；能查询清理结果，失败资源不会在接口中凭空消失 |
| 并发 | 多调用方编辑和操作同一资源时结果明确，互不相关资源可以并行 |
| 独立调用 | 使用服务身份或有范围的 API Token 即可完成流程，不需要浏览器 Cookie、数据库或 Agent 管理权限 |

接口有意不提供的能力，应记录产品理由，例如不可变发布版本不能编辑。普通查询、停止和清理等必要步骤不能用“暂不开放”掩盖缺失。

### 2.2 全项目能力清单

实施时从正式页面操作、模块应用服务和运行中的 OpenAPI 建立一张对应表。结构性依赖使用 CodeGraph 查询；文案、路由字面量和日志使用原生文本搜索。接口文档与源码冲突时，以真实请求及当前实现核实。

| 范围 | 按实际产品边界检查的流程 |
| --- | --- |
| 身份与授权 | 初始管理员、API 调用身份、授权范围、身份停用与撤销；区分管理调用和代表用户执行 |
| 节点与资源 | 节点登记、能力与状态、资源池、镜像查询与导入、分发结果、引用和删除 |
| 内容与题目 | 题目创建、编辑、附件、发布或启用、检索、引用关系及删除 |
| CTF | 赛事配置、战队或参与关系、题目绑定、实例申请与回收、提交和成绩查询 |
| 培训、理论、自主练习 | 内容准备、报名或参与、学习与实验、答卷或提交、结果查询及管理 |
| AWDP | 服务配置、运行与轮次控制、检查结果、重置与结束；攻击行为仍按专项授权边界处理 |
| TeamLab | 控制范围、模板与连接器、草稿、发布、准备、运行、运维、访问、流量、抓包及清理 |
| 通用服务 | 异步任务、事件、操作审计、文件下载、已有通知或 Webhook |

清单每行记录：用户任务、入口、API、权限、前置资源、返回结果、后续动作、验证方式和缺口。状态只使用“可完整调用”“缺步骤”“仅内部接口”“文档不符”“待实测”“产品不提供”，避免一个笼统的“已支持”。

整个项目的审查不能以 TeamLab 通过代替。先完成全项目清单，再按运行依赖和业务重要程度分批补齐。

### 2.3 对外调用契约

沿用 `/api/open/v1`、现有 Token、授权范围、分页、错误模型和异步操作约定。现有 `/api/admin/...` 作为内部接口的事实，不能自动视为稳定外部 API 已覆盖。

具体审查与修正：

1. 对外 DTO 与 EF 实体、页面 DTO 分离。字段单位、枚举、时间格式、可空值、默认行为和列表排序明确，生成的客户端与真实响应一致。
2. 所有创建请求的资源引用都有可用查询入口；对外 ID 不要求调用者推算数据库主键或节点资源名，统一使用当前公开 ID。
3. 受理结果与执行成功分开。长操作复用 `ApiOperation` 和 `DeploymentQueueTicket`；短操作不为了形式统一改成排队任务。
4. 复用现有请求重复提交处理，在实际会产生重复资源的边界验证即可。客户端与服务端不叠加多套重试，不自动重试语义不明的写请求。
5. 读取、修改、下载、会话连接和事件订阅都核对作用范围；普通用户、受限调用方和管理员分别验证，不能只用全权管理员测通。
6. 文件 API 检查目录、覆盖、移动、删除及大小限制。大文件使用现有流式传输能力，避免把前端 Base64 小文件通道直接作为独立产品的全部文件方案。
7. 远程会话说明创建、连接、尺寸调整、断开、结束、过期和审计的完整关系。WebSocket 或 Guacamole 隧道同样属于对外能力，不遗漏在 HTTP 接口清单之外。
8. 已有 Webhook 可作为通知渠道；任务查询始终可用。调用者可以选择轮询，不强制部署回调服务器。
9. 使用同一套示例自动验证文档、OpenAPI 和实际服务，避免三份参数说明分别维护。

对外契约只保留当前产品实际提供的能力。删除没有使用价值或没有真实执行链的能力时，同步删除字段、接口、生成客户端、文档、测试和数据定义，不保留弃用入口、忽略分支或兼容转换。

## 3. 产品问题的处理范围

这一部分先规定预期行为。实施时逐项复现，并把同类问题纳入同一修正，不能只修用户举出的某个页面。

### 3.1 API 创建画布后的默认排版

调用方提交网段、资产和连接关系即可获得能阅读的画布，不要求外部系统计算坐标。

- 创建时未提供布局，由服务端统一生成并返回；按网段分组，组内排列资产，网段之间预留连接和名称空间。
- 编辑时保留已有有效布局，只为新增或缺少位置的对象安排位置。读取页面不偷偷写回草稿或增加修订号。
- 多网卡资产只绘制一个节点，各接口明确连接对应网段；不能复制同一个资产来凑分组。
- 手工布局保留，提供一次明确的“自动排列”操作。历史重叠布局可以用该操作整理，不在每次打开时强制移动用户节点。
- 合法的零坐标不当作缺失值。显式提交的布局与缺省布局要能区分。
- 优先复用已有布局实现；缺失时使用确定性的分组排列，不引入新的可配置布局引擎。

完成条件：纯 API 创建、部分节点新增、手工调整后重开三条路径都可用；同一数据反复读取不改变坐标和修订。

### 3.2 网段、连线和运行状态的颜色

网段使用稳定的类别配色，背景、边框及所属接口连线保持对应，刷新和重新排序后颜色不跳变。颜色从共享 Token 调色板取值；相邻网段尽量不同，网段较多时同时依靠名称、边界和图例识别。

网段颜色表示归属，状态颜色表示运行情况，两者不混用。跨网段路径显示方向和名称，多网卡资产按接口区分连接。不能用一条任意颜色的线暗示实际不存在的通信路径。

场景列表、试运行、运行实例、详情和会话使用同一状态展示规则：

| 状态含义 | 展示方式 |
| --- | --- |
| 等待、调度、部署、探测、清理中 | 明显的阶段文字、进行中图标及适当动效 |
| 部署完成、环境运行中 | 稳定的成功色标签与图标，不持续旋转 |
| 已暂停、已停止 | 警示或中性色标签，明确说明是否保留资源 |
| 执行失败 | 失败色、具体失败阶段和适用操作 |
| 状态尚未取得 | 显示未知或正在获取，不伪装成停止或成功 |
| 已销毁、已结束 | 中性色终态，不再显示进行中动效 |

日间、夜间和减少动效模式都保留文字与图标，不能仅靠颜色或小圆点表达状态。

### 3.3 场景库的“设施”和版本提示

“设施”先核对它实际统计的对象。若对应显式交换机、路由器等网络节点，详情中用具体名称说明；场景卡片优先展示“资产数、网段数”，不把读者无法解释的“0 设施”放在主要位置。隐式网络与显式节点分开统计，不为了好看编造数量。

版本判断统一在服务端定义比较规则：

- 未作修改的保存、打开页面、重新加载、字段顺序变化、等价默认值，都不能产生“有新运行配置”的提示。
- 草稿修订、画布变化、发布版本和执行内容变化分别表达。布局调整可保存为草稿，但不能暗示已有运行需要更新。
- 执行内容使用规范化后的定义及锁定镜像摘要比较。只排序不影响语义的集合；有顺序含义的数组不能排序后当作相同。
- 自动生成的时间、读取时补出的状态、界面坐标和颜色不参与执行摘要。
- 确有差异时说明修改了什么，例如镜像、网络连接或资源配置，不仅展示“发现新版本”。

已有发布包含布局快照的约定要保留兼容。修复重点是比较与提示准确，不新增运行中自动切换版本。

### 3.4 流量观测与抓包

先明确三个概念，避免把不同采集手段变成互相重叠的产品入口：

- 流量概览：查看哪些资产在通信、使用什么协议或端口、收发了多少数据。
- 抓包：在选定时间和范围内保存实际网络报文，下载后可用 Wireshark 分析。PCAP 是文件格式，“按需 PCAP”在操作入口改为“抓包”。
- 网络观测点：平台在网段或资产接口侧创建的抓包位置，只服务于流量概览和抓包，不要求资产内部安装采集组件。

页面只保留“流量概览”和“抓包”两类主要任务。原端点采集没有提供独有、可用的产品结果，相关前端配置、契约、运行字段、Agent 通道和来宾组件已经删除；网络侧观测点继续作为流量与抓包的内部执行位置。

具体要求：

1. 普通组网不依赖端点采集组件；额外观测不可用时不把能运行的环境判定为失败。
2. 采样统计、完整报文和推测的关联路径分别说明来源及限制；不把时间接近的两条记录显示成已证实的同一条路径。
3. 抓包入口直接选择资产或网段、时间及可选过滤条件。范围、启动、停止、下载和失败原因在同一处完成。
4. 不新增抓包档案中心、协议解析平台或第二套采集任务。现有抓包记录提供完成使用所必需的查询与下载即可。
5. 关闭采集、没有流量和采集失败分别显示，避免同样呈现一张空表。

### 3.5 会话审计、导航与其他同类问题

“操作审计”必须完成从点击、加载记录或生成证据，到查看及下载的流程。检查会话未结束、证据生成中、无记录和无权限时的合理行为。不能提供无反馈按钮，也不能用“按钮可点击”替代内容确实可用。

审计范围沿用用户已确认的要求：记录会话操作、对象、时间和结果，不录制终端命令、输出或屏幕内容。

导航按实际路由及页面归属选择唯一活动项，解决“组网资源”和“组网场景”同时高亮的问题，并检查直接打开链接、前进后退及标签切换。

同类问题检查覆盖以下几类：缺少用途说明的参数、必须手写 JSON 的普通操作、名称与实际对象不符、成功后列表不刷新、错误被弹窗遮挡、后台任务被前端计时器判成功、缺少能力却显示可用按钮。每项都归入已有流程修正，避免为修复再增加一层面板。

## 4. 本地实际运行与自动化验证

### 4.1 两套用途不同的运行方式

两种方式使用同一份候选代码、数据库迁移和公开契约，测试结果分别报告。

| 方式 | 组成 | 能确认什么 |
| --- | --- | --- |
| 真实功能环境 | 主站或独立组网服务、PostgreSQL、Redis、真实 Agent、Docker、OVN/OVS、网关；按需加入 libvirt 与 Guacamole | 网络是否连通、策略是否生效、文件和会话是否能用、清理是否完整 |
| 底座压力环境 | 相同服务和真实 PostgreSQL、Redis，Agent 与耗时基础设施使用协议级模拟服务 | API、数据库、队列、编排、事件和状态更新的性能及并发正确性 |

压力环境不提供基础设施验收结论，真实功能环境不承担大规模容器和 VM 启动压力。

### 4.2 本地环境准备

1. 从已有本地编排、H03 样例和自动化脚本中选取可复用部分，整理成一个明确的启动入口。固定服务版本及测试镜像摘要，避免每次临时拼环境。
2. 使用独立 Compose 项目名、网络、数据库和数据卷。保留用户原有本地数据，不以清空 Docker 或删除已有卷作为恢复方式。
3. 基础组合启动数据库、Redis、服务和 Docker Agent；网络组合加入真实 OVN/OVS 与网关；VM 组合按需启动，避免每轮加载所有依赖。
4. Docker Desktop 的 Linux 环境先检查实际内核和权限是否能运行 OVS、网络命名空间及 Agent。条件不足时使用本地 Linux 虚拟机承载 Worker，不把 Windows 普通容器网络假称为完整组网环境。
5. 两个 Worker 使用不同执行身份和隔离的执行环境。若共用宿主内核或仅隔离网络命名空间，报告注明它能验证跨 Worker 编排，不能代表两台物理机器故障隔离。
6. VM 功能优先使用本地 libvirt/QEMU 和小型 Linux 镜像。没有 KVM 时可用 TCG 验证功能，但不据此评价 VM 启动性能。SFTP 需要真实 SSH 服务，VNC 要验证无来宾网络也能连接。
7. RDP 可以先用支持 RDP 的 Linux 测试镜像检查通道；Windows 特有行为需要合格 Windows 镜像，不能把 Linux RDP 结果写成 Windows 验收。
8. 现场连接器使用受控虚拟网卡与独立网络命名空间模拟外部设备；自动网卡发现另核对物理网卡筛选规则。模拟端点不冒充真实交换机或工控设备兼容性验证。

环境启动后自动输出服务地址、代码版本、迁移版本和实际可测能力。缺失组件对应的项目标为“未执行”，不使用模拟成功结果填补。

### 4.3 固定的样例与测试入口

保留一组小而完整的样例：两个网段、跨 Worker 的多个 Docker 资产、一个提供 TCP/HTTP 服务的资产、一个 Linux VM、一个模拟现场连接器。服务镜像本身不依赖临时装入 Python、curl 等工具才能通过平台探测。

通过正式 API 导入设备模板、查询镜像、创建拓扑、发布和运行。业务测试不直接向数据库插入“已运行”实例，也不手工下发 Agent 命令绕过主站。单独做数据库测试数据生成时需明确标记用途，不计入功能通过项。

自动化提供四种操作：准备环境、运行指定流程、收集结果、清理本次创建的资源。沿用现有 .NET 集成测试和脚本，不建设新的通用测试平台。

成功测试清理运行资源，保留可复用模板与场景。需要用户查看时，可使用显式的“保留演示环境”参数，并输出对应页面地址与资源 ID。失败时先收集证据，再清理；无法清理的项目明确列出，不删除用户其他环境。

### 4.4 TeamLab 必跑流程

每条流程以公开 API 发起，必要时从外部客户端发送真实流量，并以只读节点检查核对结果。

| 流程 | 实际操作与通过条件 |
| --- | --- |
| 纯 API 建场景 | 查询模板与资源 → 创建无坐标拓扑 → 更新 → 校验 → 发布 → 准备镜像 → 部署；读取结果完整，页面打开无重叠 |
| 保存和版本比较 | 不修改保存、调整布局、实际修改镜像或网络三种情况分别核对；只有相应变化出现对应提示 |
| 多资产链路策略 | 对同网段不同 Worker 的全部目标施加可测时延或丢包；验证每个目标，再恢复；中途令一个目标执行失败，核对先前目标恢复到操作前状态 |
| 服务开放 | 自动与指定端口、TCP 与 UDP、正确目标网段；从场景网络之外实际访问，撤销后不可访问，销毁后端口租约与转发规则回收 |
| 容器文件运维 | 列目录、新建、上传、下载、重命名、移动、删除非空目录；字节摘要一致，中文和空格文件名正常 |
| VM 文件与终端 | 对真实 Linux VM 完成同样文件操作及 SSH 交互；终端关闭、文件取消和运行销毁不会留下活动会话 |
| 图形控制台 | 无来宾网络时仍可取得 libvirt VNC 图形数据并关闭；RDP 通道另按实际镜像条件验证 |
| 会话及审计 | 创建 → 建立连接 → 查询 → 结束 → 审计读取/证据下载；内容符合会话操作审计范围，错误及未生成状态可解释 |
| 现场连接器 | 自动选择与手工填写均可保存；挂入运行后与模拟现场端点互通；断开和销毁后状态、租约、网络连接正确 |
| 启动顺序 | 无依赖时可以并行；真实服务依赖按检查结果推进；前置服务失败时明确指出原因；未配置观测不阻止普通部署 |
| 流量与抓包 | 发送已知通信 → 查询可支持的概览 → 抓包 → 停止 → 下载 → 解析文件；文件中确有该通信，不以非空文件代替检查 |
| 生命周期 | 创建、允许的暂停/恢复、重置、失败后清理、销毁；核对当前代次、会话、授权、端口、网络及磁盘资源的归属和处理 |
| 调用范围 | 受限 Token 能完成所授权流程；另一控制范围的数据、文件和会话不可读写；缺少能力时返回明确原因 |

公网服务开放在本地可以验证“模拟公网网关 → Worker 隧道 → 资产”的完整路径。报告必须写明这是本地网关路径；没有真实公网客户端参与时，不宣称互联网连通性已经验证。

### 4.5 全项目 API 流程验证

对第 2.2 节中每个正式业务模块，至少保留一条普通调用者的完整主流程。结合 API 清单，补充该模块特有的失败或冲突，不机械复制全部参数组合。

例如，CTF 流程应覆盖资源准备、赛事和题目关联、参与者运行、提交与成绩读取、结束清理；培训流程应覆盖课程内容、参与、实验、提交与进度。具体端点在清单建立后确定，不凭旧文档中的接口名称写测试。

这一批测试用来发现“只有创建接口、没有结果或后续管理接口”等缺口。牵涉真实执行的代表性流程使用 Docker；理论、内容等纯业务功能直接经真实 HTTP 和数据库验证。

### 4.6 浏览器检查压缩到必要范围

浏览器数据由 API 脚本提前准备；浏览器自动化直接打开对应场景、运行和会话，不重复点击创建整套环境。

保留以下检查：

- 无坐标和多网卡画布、网段颜色、连线及标签；
- 场景、试运行、运行实例的阶段显示和终态；
- 操作审计按钮实际打开、内容加载和下载事件；
- 导航唯一高亮、刷新、深链接及前进后退；
- 参数说明和错误反馈是否在实际操作处可见。

这些页面在既定宽度和日夜主题下用同一组自动化截图检查；只对异常位置人工查看。其余业务正确性由 API 和真实执行测试承担。

### 4.7 结果与问题定位

每次运行保存一份结果目录：候选代码版本、环境版本、执行命令、步骤结果、耗时、请求关联 ID、任务 ID、运行 ID 及代次。失败时自动附上该步骤的脱敏响应、相关事件和必要节点状态。

API 状态与实际结果同时记录，例如“接口显示策略生效；三个目标中的第二个实际延迟未变化”。这样可以直接定位至状态推进、目标展开或节点执行，避免只留一张失败截图后重新复现。

结果使用“通过、失败、条件缺失未执行”，模拟与真实执行单独标注。一次修复后重跑失败流程和直接受影响流程；候选版本形成时统一执行构建与相关完整检查，不反复重跑无关的大规模验收。

数据库迁移单独在 PostgreSQL Testcontainers 或本地可恢复副本验证：旧数据升级、关键引用保留、新版本读取写入，以及从备份恢复到旧版本。恢复演练不在用户正在使用的本地库上操作。

## 5. 并发测试与性能问题定位

### 5.1 测量边界

目标是找出底座处理多请求、多操作时的瓶颈。容器启动、镜像拉取、VM 开机和物理设备响应耗时不作为本轮底座性能成绩，但 API 鉴权、数据库、Redis、队列、调度计算、状态更新和事件投影必须真实执行。

需要区分三个时间：

1. 请求到成功受理的时间。
2. 受理到任务实际开始执行的排队时间。
3. 扣除模拟执行等待后，底座完成编排、处理回报并更新最终结果的时间。

只测 HTTP 202 返回速度可能掩盖不断增长的队列。报告必须同时给出任务完成吞吐、队列等待和最老任务年龄。

### 5.2 工具选择和模拟边界

HTTP 负载使用 k6，功能与业务断言沿用 .NET 集成测试。终端和文件通道按现有客户端做专项，不为了统一工具重写全部测试。

协议级 Agent 模拟服务位于测试目录，以真实 Agent 契约通信，支持固定响应时间、受控失败、心跳、资源清单、任务结果和回报顺序。它只替换执行面，不替换主站的应用服务、任务队列、资源分配及数据库。

先让模拟服务与真实 Agent 各跑一条相同的小流程，对照关键请求和状态语义。模拟器要遵守代次、资源身份和容量条件；不能所有请求立刻返回成功，否则测不到真实编排成本。

模拟组件仅在测试启动方式中启用，生产镜像及默认配置不带模拟开关。压力测试数据用固定种子生成；只读大列表可以批量准备测试库，生命周期正确性仍由 API 创建的资源验证。

### 5.3 负载组合

| 组合 | 要观察的问题 |
| --- | --- |
| 列表、详情、事件和状态轮询 | 分页、关联查询、重复查询、响应大小、缓存命中及鉴权成本 |
| 草稿保存、校验、发布、计划生成 | 大拓扑解析、规范化、摘要计算、布局和计划算法的 CPU 与内存成本 |
| 不同运行的创建、重置、销毁 | 队列吞吐、容量预留、调度是否被全局锁串行化 |
| 同一资源同时写入 | 草稿冲突、生命周期互斥、端口分配是否准确；业务冲突不应变成 500 |
| 写操作与高频查询混合 | 状态更新和列表读取是否相互阻塞，最终结果能否及时查询 |
| 心跳、任务回报与事件写入 | 写入批次、数据库锁、投影更新和积压 |
| 文件流与远程连接并发 | 内存是否随总传输量膨胀，慢客户端是否占满线程或连接，普通查询是否被拖慢 |
| 多个 Token 与控制范围 | 单个调用方是否占满处理能力，授权查询是否造成额外热点 |

混合负载初始可采用约 60% 读取、25% 草稿/计划操作、15% 生命周期操作，作为起始实验配置，不当作真实业务统计。单接口测试与混合测试都保留，避免平均数掩盖某一类操作。

### 5.4 执行顺序

1. 固定应用、数据库和负载发生器的 CPU、内存及连接池设置，记录 Docker Desktop 分配和宿主机资源。先确认发生器自身没有饱和。
2. 用小流量建立基线。分别准备小、中、接近当前允许上限的拓扑，已有数据量采用例如 100、1000、10000 个历史对象；超过本地容量的档位明确不执行。
3. 按 1、10、25、50、100、200 个并发调用逐级升压，每级保留足够的稳定采样窗口。并发用户数和每秒请求数分别报告，不互相替代。
4. 对主要组合再使用固定到达速率加压。即使服务变慢，发生器也维持预定请求速率，暴露排队增长；未能发出的请求同样计入报告。
5. 找到延迟或队列明显上升的区间后停止盲目加压，采集该区间的性能证据。
6. 在拟定正常工作区间做一次约 30 分钟的稳定运行，并进行一次短时突发后降载，确认积压能消退、内存和连接能释放。只有发现持续增长才延长测试。
7. 修改实际瓶颈后，只重跑相同负载及受影响的混合组合，使用相同数据规模和资源配额对比。

首次单实例测试后，只有当测量显示横向扩展有价值时，才用两个 API 实例连接同一测试数据库验证。共享协调和队列仍保持唯一资源归属，不预先设计复杂集群。

### 5.5 观测与定位

复用现有日志、指标和 OpenTelemetry；缺少的跨度只补在重要等待点。每条请求能关联到操作、票据、运行和节点命令。指标按接口或操作类型聚合，避免把每个运行 UUID 做成无限增长的指标标签。

| 现象 | 取得的证据 | 优先考虑的改法 |
| --- | --- | --- |
| 查询越多越慢 | SQL 次数、查询计划、返回行数、数据库等待 | 消除重复或逐项查询，补合适索引，减少无用字段 |
| API CPU 满 | .NET CPU profile、拓扑规模与序列化耗时 | 改热点算法和重复计算，避免每次读取全量编译 |
| 排队增长但 CPU 不高 | 锁等待、工作线程等待、连接池和调度耗时 | 缩小锁和事务范围，处理同步阻塞及错误串行化 |
| 状态长时间不更新 | 回报到达、事件写入、投影及查询时间线 | 减少重复写入，调整已有批次或投影更新路径 |
| 内存持续增长 | GC、分配速率、堆快照、文件/事件缓冲大小 | 修复未释放对象、无界缓存或整文件装入内存 |
| 多实例后错误增加 | 资源冲突、锁和同资源命令记录 | 修正共享协调边界，不用全局大锁掩盖问题 |

常用证据来源为 `dotnet-counters`、`dotnet-trace`、PostgreSQL `pg_stat_statements` 与锁等待、Redis 延迟和连接、现有请求 trace。数据库执行计划仅在测试库分析，不把诊断工具常驻为另一套产品。

### 5.6 正确性与性能一起检查

每个压力组合结束后核对：成功受理的操作数量与终态数量、重复资源、重复端口/地址租约、错误代次、未结束会话以及清理结果。模拟器资源清单与业务结果对照，但报告保留“模拟执行”标识。

预期的版本冲突等 409 单列统计；429 配额限流、客户端超时、5xx 和未发出请求也分别统计，不把限流成功当作底座吞吐高。容量测试使用本地测试 Token 的足够配额，配额功能本身另做定向验证，不关闭鉴权和审计。

拟定的首轮参考线为：在确定的目标并发下，常用查询 p95 不超过 300 ms，短写操作受理 p95 不超过 500 ms；p99、最大值、任务等待和错误率同时报告。这些是待本地基线校准的工程目标，不是已具备的性能或商业 SLA。冷启动、文件传输、大拓扑编译及实际节点执行单独评价。

任何错误成功、资源归属混乱或成功受理任务无结果都必须处理。性能结论最终应写成“在何种硬件、数据规模和操作组合下达到多少吞吐，哪个资源首先饱和”，不能只写“支持高并发”或把单机结果外推到任意部署。

## 6. TeamLab 独立产品的技术路线

### 6.1 推荐路线

采用“同仓库、独立进程、独立数据库、单一执行所有权”。先把 TeamLab 与必需的通用运行代码整理为可独立编译的模块，再组成一个独立服务；平台通过稳定 HTTP API 调用。暂不把组网、镜像、调度、审计再分别拆成多个服务。

继续使用 .NET、PostgreSQL、Redis、现有 Agent 和现有网络执行实现。独立进程提供组网 API、相关管理 API、后台任务及一个轻量管理界面。Docker、KVM、OVN/OVS、WireGuard、网关和 Guacamole 仍各司其职，不改写执行技术栈。

| 路线 | 取舍 |
| --- | --- |
| 在原平台前面加一层 API 转发 | 可以临时接入，但独立部署仍需要整个平台，不能作为最终交付 |
| 把整个平台复制一份再隐藏业务菜单 | 快速启动但保留业务表、配置和发布依赖，后续修复还会出现两份代码，放弃 |
| 提取组网及必需通用模块，组成独立服务 | 复用现有实现，能够建立独立数据与发布边界，采用 |
| 将调度、镜像、会话等拆成多个微服务 | 引入大量网络调用和运维成本，当前没有测量依据，不采用 |

最终关系：

```text
平台页面、CTF / 培训 / 练习 / AWDP 等业务
              │
       平台权限与业务适配
              │ 稳定 HTTP API / 文件流 / 会话通道
              ▼
      独立组网与通用运行服务 ◀── 外部客户系统、独立管理界面
       │            │
       │            └── 自有 PostgreSQL、Redis、必要文件存储
       ▼
   唯一部署队列与节点资源管理
       ▼
    Agent → Docker / libvirt / OVN / OVS / WireGuard
       └── 网关、Registry、Guacamole
```

独立组网产品需要的通用运行模块作为内部组成随产品交付。产品名称可以继续使用 TeamLab，不必为这些内部模块再建立多个产品概念。

### 6.2 代码与数据归属

| 内容 | 独立服务拥有 | 平台保留 |
| --- | --- | --- |
| 场景 | 拓扑、布局、发布、执行计划、运行及代次 | 场景与比赛、课程、训练任务的业务绑定 |
| 调度与资源 | 部署票据、节点、能力、容量、地址与端口租约 | 谁能申请环境、业务配额规则、业务结束策略 |
| 镜像与设备模板 | 执行所需的镜像目录、摘要、制品引用、分发与缓存、设备模板 | 题目、课程等内容信息及镜像绑定；普通课程附件仍归平台 |
| 运行运维 | 容器/VM 操作、连接器、服务开放、文件通道、会话和相关审计 | 业务菜单、入口授权、业务操作记录 |
| 观测 | 运行事件、流量、抓包及对应文件 | 业务页面按需读取的摘要 |
| 身份 | 本产品管理员、API 调用身份、控制范围和资源授权 | 平台用户、战队、组织、参赛/学习关系 |
| 业务结果 | 仅保存执行结果 | Flag 判定、分值、答案、成绩、进度和排行榜 |

独立服务中的操作者与外部业务关联使用稳定的调用方标识及外部引用，不再外键关联平台 User、Game、Team、Course 表。执行服务不理解 Flag；平台可按已有秘密参数注入机制传入实例值，判断和计分留在平台。

共享的 `Runtime`、`Fleet`、`VM`、镜像执行能力按实际依赖提取，不能把整个业务模块拖入独立服务。第一阶段查清每个依赖的用途，按“移入、改为 API、留在平台、移除”记录决定。只提取已有用途明确的代码，不先建设通用插件系统。

### 6.3 同一批 Worker 只能有一个调度方

当前平台多种业务共用运行能力。独立后如果两个进程各维护容量、端口和队列，却操作同一批 Worker，会产生重复分配和相互清理。这是拆解中必须提前解决的约束。

目标采用唯一调度所有者：共享 Worker 的通用执行调度移入独立服务，继续使用现有 `DeploymentQueueTicket` 及调度实现。平台的普通 Docker、VM 等业务改为提交规范化运行请求，业务逻辑留在原模块。不得为 CTF 和 TeamLab 对同一资源池各建一套调度队列。

迁移期间按 Worker 资源池划分所有者：旧资源池仍由平台管理，独立服务使用专属测试池。两边不同时管理同一 Worker、同一可写网络控制面或重叠的地址/端口池。独立服务可以先在专属池验证，随后再把原资源池整体转交。

Agent 注册、心跳、命令和 inventory 的接收方随资源池一起切换；平台节点页面读取独立服务 API，不能继续向已转交节点发送管理命令。共享公网网关的映射归属和端口分配也要同时转交，不能只改 Agent 地址。

不追求第一版无中断接管正在运行的所有资源。优先在维护窗口等相关队列和运行自然结束后转交；不能结束的业务继续由旧所有者管理到下一窗口，不强制销毁，不开发一套临时跨服务接管协议。

### 6.4 平台通过 API 调用的范围

“平台改用 API”同时覆盖后端业务调用和前端管理入口，不能只改浏览器请求地址。

1. 在平台定义一个类型化 TeamLab 客户端，契约由 OpenAPI 生成；业务模块通过薄适配器调用，停止直接访问 TeamLab 应用服务和表。
2. 前端保留现有 feature API adapter。平台服务处理自身登录和业务权限，将已授权请求转到独立服务；普通业务编排不搬到 React。
3. 独立服务内部模块继续直接调用应用接口，不为内部函数增加 HTTP 绕行。
4. 平台保存外部资源 ID 与必要业务绑定。运行状态直接读取 API，必要的展示缓存明确标注更新时间，不在平台另建一套可写运行状态机。
5. 终端、图形通道、文件和审计下载均穿过相同授权边界。大文件流式转发，WebSocket 正常转发升级；URL 由服务配置和响应生成，不写死主站域名。
6. 生命周期任务的受理、结果和恢复沿用独立服务返回的 ID。平台不再创建一份平行部署任务，不自行依据超时判定失败或成功。
7. 原管理端路径在过渡期可保留为薄转发入口。切换成功后移除原执行实现，避免“本地调用”和“远程调用”两条长期分叉。

### 6.5 身份和授权

独立安装提供本产品的初始管理员及 API 凭据建立方式，安装过程不要求先启动 YINYU。可以复用已有认证实现中的必要部分，但不复制整个比赛用户体系。

平台作为一个受限调用方接入。后台自动任务使用服务身份；代表用户执行时，同时传递经认证的操作者身份与被授权的控制范围。独立服务核对调用方是否具有该范围权限，审计分别记录调用方和实际操作者。

不能让浏览器任意填写一个用户 ID 就获得权限，也不把平台的全权 Token 放进前端。采用现有 Token/签名能力可表达的最小信任关系，避免另外搭建统一身份平台。

平台用户停用、业务授权撤销和已有会话结束的关系需要明确；使用已有撤销与结束接口实现，不假设已创建连接自动继承后续权限变化。

### 6.6 数据库与文件迁移

目标数据库只包含组网和必要通用运行表；不依赖平台数据库的跨库查询、视图或共享 DbContext。Redis 可共用部署实例，但命名空间和凭据独立，正式部署可单独配置。

推荐分两步：

1. 模块提取阶段可暂时保留原数据库，由原服务单独写入，先验证依赖拆除和 API 契约。
2. 独立服务在空白数据库验证完整安装；现有安装再通过一次明确的数据迁移转交所有权。迁移期间停止受影响写入，不双写两套数据库。

迁移清单包含拓扑、发布、布局、运行历史、控制范围、镜像和模板、节点与资源池、任务和操作记录、访问与端口状态、会话审计、抓包元数据及文件引用。保留既有公共 ID、运行代次和业务绑定；内部数字主键如需变化必须有明确映射，不能影响已有节点资源命名。

文件与 Registry 可继续使用已有存储实现。明确谁拥有文件元数据、删除权及引用，不以“共用一个目录”代替归属设计。执行镜像的权威记录由独立服务管理，平台通过 API 查询和绑定，避免两个镜像目录分别修改同一制品。

加密数据迁移必须同时处理相关密钥及用途配置，确保仍被使用的凭据可读；只迁移本服务需要的内容，不把其他业务秘密一并复制。测试以能实际使用凭据和访问文件为准，不只比较行数。

当前仓库中，删除能力时直接从最初引入它的迁移和后续模型快照中移除，不新增补丁式删除迁移。独立数据库从提取完成后的当前模型生成一份干净的初始迁移，不复制主项目的历史迁移链。旧系统数据通过一次性导入工具转交，且只处理当前模型仍需要的数据。

### 6.7 发布与回退

独立发布应具备：API 服务及必要后台任务镜像、Agent 发布物、轻量管理界面、OpenAPI、客户端生成方式、配置示例、Compose 示例和升级说明。首次安装能完成节点、镜像与凭据配置，缺少可选 KVM 或 Guacamole 时仍能使用相应的 Docker 能力。

回退分两个时间点：

- 切换后尚未接受新业务写入：可以按已验证步骤切回旧所有者及迁移前数据。
- 已接受新写入：优先回退到兼容当前数据库的应用版本或前向修复。不能直接恢复旧备份丢掉新数据，也不能让旧调度器同时恢复对同一资源池的控制。

资源池所有者、Agent 接收方、队列消费者、网关和数据库写入方应作为一次切换一起记录。实际生产迁移与停机时间另行制定，本规划不授权部署。

### 6.8 独立性的验证方式

最终以三个实验确认独立性：

1. 在空白环境仅启动独立产品及其声明的基础依赖，用 API 完成模板、场景、运行、运维、访问和销毁。
2. 在独立产品运行时关闭平台，并阻断对平台数据库的访问，继续新建和管理场景。不能只验证旧容器仍然运行。
3. 平台通过 API 完成代表性的 TeamLab 业务及受影响的普通运行业务；移除平台内的旧执行实现后，流程仍能工作。

代码层另设少量架构检查：独立项目不能引用平台业务程序集；平台 TeamLab 适配代码不能直接访问组网实体与数据库；已转交资源池不能同时启用两套队列消费者。

契约一致后，独立前端复用整理好的 TeamLab 面板及客户端，加一个轻量壳层。单独测试该构建不加载比赛、课程、计分页面和平台专有菜单，避免以嵌入整个平台页面代替独立产品。

## 7. 实施顺序、交付物与完成条件

### 7.1 阶段顺序

| 阶段 | 工作 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| P0：核实基线与接口范围 | 保存并核对前一轮未提交改动；建立全项目 API 流程清单、TeamLab 依赖归属和问题分类 | 一个可识别的候选版本、接口缺口表、依赖归属表 | 分清已有实现、实际缺口、待验证项；没有覆盖用户改动 |
| P1：建立可重复的本地验证 | 整理 Docker/网络/VM 组合和 API 驱动脚本，运行当前候选 | 固定样例、运行入口、第一次实际结果 | 能复现问题并定位失败步骤；缺失条件有明确替代或未执行说明 |
| P2：修正 API 与产品流程 | 先处理错误状态、无效操作、清理和调用断点，再处理布局、状态、命名及冗余配置 | 修复代码、契约、生成客户端、同一份可执行示例 | 第 2 节已确认的 API 缺口和第 3 节产品问题有明确结果；第 4 节相关真实流程通过 |
| P3：测量并处理并发瓶颈 | 建协议模拟环境，建立负载曲线，修正实际热点 | 性能基线、问题原因、修改前后对比、适用容量范围 | 并发正确性通过；目标负载下没有无法解释的积压或错误 |
| P4：提取独立服务 | 按归属提取模块，建立独立启动、数据库、认证、文件配置和专属测试池 | 可单独安装的服务、管理界面与 API | 关闭平台后仍能新建、运行、管理和清理场景 |
| P5：平台改用 API 与迁移演练 | 替换前后端调用，处理共享执行资源，演练数据及资源池转交 | 平台适配器、迁移工具、切换和回退步骤 | 无直接表访问及重复调度；平台代表流程通过；旧数据与文件可读 |
| P6：形成发布候选 | 对最终候选重放完整 API 主流程、相关真实功能和关键压力组合 | 发布物、最终报告、已知限制和操作说明 | 独立与集成两种运行方式均有证据，源码/迁移/Agent/前端版本对应 |

P0 就确定拆解边界，使 P2 新接口能够沿用到独立服务，减少之后再次修改。P1 的脚本在 P4/P5 中只需切换服务地址和配置，再跑同一流程。P3 先记录拆解前基线，P6 对比增加网络调用后的成本，不在每阶段重新设计压测。

不先承诺固定完成天数。P0/P1 结束后，根据真实缺口、已有实现可复用程度和本地 VM 条件给出逐阶段工期。某阶段通过后即结束，不为追求更多测试数字延长工作。

### 7.2 第一批实施工作

获准实施后，最先完成以下内容：

1. 核对 `origin/main` 与前一轮工作树，形成包含待验改动的可追溯候选；不直接拿旧构建运行。
2. 建立全项目 API 流程清单，优先列出 TeamLab 及其依赖的文件、会话、节点、镜像、任务接口断点。
3. 启动隔离的本地 Docker 测试组合，用一个 API 脚本完成建场景、运行、读取和销毁，确认脚本及问题证据能重复取得。
4. 复现画布重叠、审计按钮无反馈、状态显示、版本误报和导航高亮问题，再按第 3 节统一修正。
5. 运行前一轮新增能力的真实流程，处理发现的断点；已有通过结果按代码版本引用，不把过往其他版本的验收当成本次结果。

这批工作完成后，应能明确回答“当前哪些能力外部可以完整使用、哪些实际没跑通、哪些是多余配置”，再继续性能与服务拆解。

### 7.3 如何发现用户没有逐项列出的缺陷

每个功能沿着一次普通用户操作检查：找到入口 → 理解配置 → 提交 → 知道进度 → 得到可用结果 → 继续管理 → 结束清理。

发现问题时记录它影响哪一步，并判断属于以下哪类：

| 类别 | 处理原则 |
| --- | --- |
| 结果错误或假成功 | 优先修正执行和状态推进，并留下直接验证该结果的测试 |
| API 缺少必要步骤 | 在既有应用用例上补接口；确实缺业务能力时再补用例，不把逻辑塞进 Controller |
| 页面不易理解或缺操作反馈 | 合并相近入口、写清用途和默认值，使用统一状态与交互组件 |
| 能力重复或没有使用价值 | 同步删除入口、配置、契约、实现和数据定义 |
| 性能问题 | 用负载和定位证据确认热点，再修改；不凭猜测加缓存、消息队列或锁 |
| 架构依赖阻止独立运行 | 根据归属转移实现或改成 API，避免跨库访问和长期复制 |

每条记录包含复现条件、影响、采用方案和通过证据。相同原因在多个页面或接口出现时合并处理，避免积累一批彼此重叠的补丁。

### 7.4 每阶段如何提交

源码、契约、生成客户端、相关测试与必要文档按完整意图提交。例如“修复无坐标拓扑的默认布局和版本判定”应是一组可以理解和验证的改动，不能把前后端拆成长期不兼容的提交。

独立服务提取、平台客户端替换、数据迁移分成清晰阶段，保留每阶段可启动版本。分支和工作树遵守仓库规则，合并前检查远端变化；不把未经验证的模拟开关、测试凭据或数据卷提交到仓库。

实施改动按完整意图分批提交，全部契约整合后统一生成 OpenAPI 和客户端。发布前对最终候选执行一次前后端构建和直接相关检查；本阶段不修改任何服务器。

### 7.5 最终交付判据

完成报告必须分别回答以下问题，不能以一个测试通过百分比代替：

- 全项目已承诺的 API 任务是否都有完整调用路径，剩余未开放能力及理由是什么？
- TeamLab 各条真实流程是否通过，哪些使用模拟节点或模拟现场设备，哪些缺失硬件条件？
- 用户反馈的每个界面问题如何修正，同类问题是否在其他入口一并处理？
- 原端点采集链是否已完整删除，并且没有影响流量概览、网络观测点和抓包？
- 底座在指定负载下的延迟、吞吐与排队表现如何，瓶颈在哪里，修改后改善多少？
- 独立安装是否需要平台数据库或平台服务，关闭平台后能否继续完整操作？
- 平台是否已通过 API 使用组网和转交的通用执行能力，是否还有直接调用或重复调度？
- 数据、文件、资源池转交和回退是否在副本环境演练，哪些事项仍需生产窗口实施？

不能用“外部接口全部返回成功”掩盖实际资源错误，也不能用一次本地测试推断任意规模和所有设施都无误。结论覆盖具体候选、流程和环境。

### 7.6 保持不扩张的范围

本计划不包含 PVE 管理、A06 快照、协议解析、新工控模拟器、全资源对账平台、会话持久恢复、运行中强制中断、运行实例自动切换新版、场景复制扩建、批量管理页面和抓包档案系统。

已有公开批量部署等能力属于 API 健全性审查范围，检查它们是否能完整使用；这不等于新增对应的管理界面。已有协议样例可用于产生测试流量，不据此扩展协议产品。

### 8.3 P0 API 审查处理结果

以下结论基于源码与契约静态审查。代码结果不代替 Docker、真实组网或业务流程测试。

1. **业务 API 范围已纠正。** 本阶段只闭合 TeamLab 控制面及其镜像、任务、文件、会话等直接依赖；比赛、培训、理论、练习和 AWDP 继续按各自产品边界维护，不因本任务新增一套玩家 API。

3. **control scope 与远程运维已经统一。** Open API 以 token scope 和 `teamlab-scope` grant 授权，同一控制范围内的 token 可以接续运维；审计仍分别记录 token 和 actor，不把 token 提升为管理员。
