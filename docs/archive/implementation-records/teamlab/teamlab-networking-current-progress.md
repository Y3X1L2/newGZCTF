# TeamLab 组网模块建设进度与使用说明

## 一、建设目标

TeamLab 用于建设和运行网络安全演练环境。

管理员可以在可视化界面中放置网络、交换机、路由器、容器和虚拟机，连接出完整的网络场景。场景通过检查并发布后，可直接用于比赛、培训或外部业务。平台会为每支队伍创建一套独立环境，并自动完成服务器选择、镜像准备、网络建立、设备启动、选手接入、流量记录和赛后清理。

组网模块不负责比赛计分、题目判定和虚拟机内的具体业务。例如 Windows 域环境、工控服务和漏洞程序由镜像或预置场景提供；组网模块负责让这些设备按照设计连接起来，并保证环境能够创建、使用、重置和销毁。

## 二、目前能够完成的工作

### 1. 可视化设计网络场景

- 可以创建多个内网，并设置网段、地址分配和域名。
- 可以放置交换机、路由器、容器、Linux 虚拟机和 Windows 虚拟机。
- 一台设备可以连接多个网段，并指定主要网卡和固定地址。
- 可以设置网段之间的访问方向。没有连接的网段默认不能互相访问。
- 可以设置启动顺序。例如先启动数据库，再启动业务系统；先启动域控，再启动成员服务器。
- 可以为设备填写环境参数、敏感参数、启动命令和服务检查方式。
- 支持自动排版、缩放、拖动画布、专注模式、复制、撤销等常用操作。

### 2. 检查并发布场景

- 当前编辑内容作为草稿保存，不会直接影响已经发布和正在使用的环境。
- 发布前会检查网络连接、设备配置、镜像、地址和依赖关系，所有提示均使用中文。
- 检查通过后生成正式版本。正式版本不会随着后续草稿修改而改变。
- 一个正式场景可以重复用于多场比赛和培训，不需要每次重新设计。
- 对初始化时间较长的环境，可以在发布阶段提前完成配置并保存结果，开赛时直接启动。

### 3. 自动选择服务器

- 一台服务器资源足够时，优先把同一队伍的环境放在一台服务器上。
- 一台服务器放不下时，平台按网段将环境拆到多台服务器，并自动建立节点之间的通信。
- 容器只会安排到支持容器的节点；虚拟机只会安排到支持虚拟化的节点。
- 节点缺少虚拟化能力，不会影响它继续承载容器。
- 平台同时计算已经运行、已经分配和正在创建的资源，避免多人同时启动时超过服务器容量。
- 普通比赛容器、普通虚拟机和组网环境使用同一套容量计算，不会相互抢占未被统计的资源。

### 4. 运行混合环境

- 容器、Linux 虚拟机和 Windows 虚拟机可以出现在同一个场景中。
- 同一队伍的设备即使分布在不同服务器上，也可以按照场景设计正常通信。
- 平台能够为受管理的虚拟机写入网络和运行参数，并获取系统启动和服务状态。
- 第三方虚拟机镜像不要求强制改造，也可以接入网络。平台通过地址或端口检查它是否可访问。
- 平台区分“设备已经启动”和“内部服务已经可用”，不会因为虚拟机进程启动就提前宣布环境可用。
- 设备之间存在启动依赖时，前置服务真正可用后才会继续启动后续设备。

### 5. 提前准备镜像

- 容器和虚拟机镜像统一保存在内部镜像仓库。
- 比赛准备阶段会提前把所需镜像发送到符合条件的服务器，减少选手启动时的等待。
- 服务器已有相同镜像时直接复用，不会重复下载。
- 启动环境前会再次核对镜像。确实缺失时单独显示“镜像准备”阶段，不会与“创建设备”混在一起。
- 多场比赛共同使用同一个镜像时，结束一场比赛不会删除其他比赛仍在使用的镜像。
- 只有确认没有比赛、培训和运行设备继续使用时，才会清理节点上的镜像缓存。

### 6. 管理比赛全过程

- 支持赛前准备、批量创建队伍环境、开放选手访问、关闭访问、重置环境和比赛结束回收。
- 每支队伍的环境拥有独立编号和状态，不会与其他队伍混用。
- 重置时先精确删除旧环境，再按同一正式版本重新创建。
- 销毁时会清理容器、虚拟机、临时磁盘、网络、路由、防火墙、选手接入配置、抓包任务和镜像使用记录。
- 如果清理中断，系统会保留“待继续清理”状态，允许管理员继续执行，不会把未完成清理显示为成功。
- 由比赛统一管理的环境不能绕过比赛状态单独重置或销毁，避免比赛管理与组网管理互相冲突。

### 7. 选手接入

- 每支队伍获得一份独立的网络接入配置。
- 选手首先进入场景指定的入口网段，再按照场景中的路由访问后续网段。
- 选手不会自动获得全部内网的直接访问权限。
- 重复点击获取配置不会偷偷更换密钥，也不会导致已经连接的队友掉线。
- 需要更换接入密钥时，必须先撤销旧配置，再生成新配置。

### 8. 流量查看和抓包

- 默认记录通信双方、端口、通信方式、方向、流量大小、时间、所属网段和设备。
- 可以同时从交换网络、路由位置、跨服务器链路和受管理设备获取流量信息。
- 可以查看一条通信经过的多个位置，帮助还原设备 A 到设备 B、设备 B 到设备 C以及返回方向的完整过程。
- 管理员可以按整个队伍环境、指定网段、指定设备或指定通信路径启动抓包。
- 抓包任务可以限制持续时间、文件大小和保存期限，完成后可下载标准抓包文件。

## 三、管理界面如何使用

### 1. 场景设计区

管理界面以画布为中心。设备选择区用于添加交换机、路由器、容器和虚拟机；画布用于放置设备和连接网络；配置区用于修改当前选中设备的参数。

管理员可以直接拖动画布背景移动视角，也可以选中并移动设备。工具栏提供自动排版、缩放、复制、撤销和专注模式，适合编辑设备数量较多的场景。

### 2. 检查和发布区

界面会明确区分以下内容：

- **当前设计**：正在编辑的最新草稿。
- **检查结果**：当前草稿存在的问题和对应设备位置。
- **正式版本**：已经通过检查并发布、可供比赛选择的版本。
- **试运行**：不绑定正式比赛，用于验证场景能否完整创建和销毁。

管理员修改草稿后需要重新检查并发布，已发布版本不会自动混入新的草稿内容。

### 3. 运行情况区

创建环境后，界面按顺序展示：

1. 等待服务器资源。
2. 准备镜像。
3. 建立网络。
4. 创建容器和虚拟机。
5. 等待系统和服务可用。
6. 环境可以访问。

每个阶段都显示对应节点、设备和错误原因。系统日志、部署队列和环境事件可以关联到同一次操作，管理员不需要在多个页面中依靠编号猜测问题来源。

### 4. 比赛结束和清理区

比赛结束后，界面会继续显示关闭访问、销毁设备、删除临时网络和释放镜像使用关系等进度。只有所有节点完成清理后，环境才会显示为已销毁；存在残留时会明确显示待清理内容和失败原因。

## 四、底层实现方式

### 1. 主平台统一管理

主平台保存场景草稿、正式版本、队伍环境、服务器分配、操作进度和事件记录。创建环境时，主平台会：

1. 检查场景和镜像是否满足运行条件。
2. 计算每个网段和设备应放在哪台服务器。
3. 预留所需处理器、内存和实例数量。
4. 向各服务器下发网络和设备创建任务。
5. 根据各服务器返回的真实状态推进后续阶段。
6. 汇总所有节点结果，向界面和调用方提供统一进度。

数据库保存长期状态，缓存服务负责加快消息通知和协调并发。主服务重启后，可以根据数据库记录和服务器上的实际资源继续判断，不依赖只保存在内存中的临时状态。

### 2. 计算节点执行具体工作

每台计算节点运行平台节点服务，负责：

- 创建本机虚拟网络、地址分配、域名解析、路由和隔离规则。
- 将容器和虚拟机网卡接入指定网段。
- 创建、启动、停止和删除容器或虚拟机。
- 从内部镜像仓库准备镜像。
- 建立节点之间的加密网络和选手接入通道。
- 采集设备状态、流量信息和抓包文件。
- 按队伍环境精确清理本机资源。

节点只能删除能够确认属于目标环境的资源。无法确认归属时会停止删除并上报错误，避免误删其他比赛或平台普通容器。

### 3. 多台服务器如何组成一个场景

平台按完整网段分配服务器。例如入口网段放在节点一，业务网段和数据网段放在节点二。节点之间通过固定的加密通道转发流量，平台再根据场景中的连线决定哪些网段可以互通。

容器和虚拟机只需要接入本机网段，不需要知道自己实际位于哪台服务器。这样既能支持大场景拆分，也能清楚控制网络隔离、流量观测和故障范围。

### 4. 如何避免旧任务破坏新环境

每次创建或重置环境都会产生新的执行代次。所有节点操作都必须携带当前代次。较早发出的延迟任务到达节点时，会因为代次已经过期而被拒绝，不能继续修改或删除新环境。

网络配置采用原地核对和更新。配置未变化时不会删除后重建，因此正常重置和状态恢复不会无故改变节点内部地址或选手接入参数。

### 5. 如何保证清理准确

销毁由主平台统一发起，各节点并行清理自己承担的设备和网络。节点根据环境编号、执行代次和资源归属记录进行删除，主平台收到全部节点完成结果后才确认销毁成功。

镜像单独记录使用关系。销毁队伍环境只释放该环境的使用记录，不直接删除共享镜像；确认没有其他使用者和运行设备后，节点缓存才允许被清理。

## 六、当前使用边界

- 一个网段只能放在一台计算节点上，不能把同一个交换网络直接横跨多台物理服务器。
- 单个网段需要的资源超过节点容量时，应拆分网段或增加节点容量。
- 当前不提供按端口单独设置访问权限；访问关系由网段连线、路由方向和选手入口规则决定。
- Windows 域环境、工控协议和漏洞服务由镜像、初始化配置或预置场景提供，组网模块负责其网络、调度、运行和清理。
- 未经过平台认证的第三方虚拟机可以参与组网，但平台不保证自动修改其系统内部配置，也不保证获取内部进程状态。
- 历史上直接登记的外部容器镜像仍可使用；如需全部迁入内部镜像仓库，需要单独执行一次镜像导入。

## 七、开放接口调用规范

### 1. 接口入口

- 组网接口基础地址：`/api/open/v1/teamlab`
- 镜像接口基础地址：`/api/open/v1/images`
- 任务进度查询：`/api/open/v1/operations/{operationId}`
- 部署后的中文接口页面：`/api-docs/`
- 部署后的完整接口定义：`/openapi/open-v1.json`

管理端、比赛模块、培训模块和外部系统都必须通过同一套接口使用组网底座，不能直接调用计算节点，也不能分别维护另一套环境状态。

本章列出的是允许客户系统调用、并承诺保持版本兼容的开放接口。平台管理界面、比赛管理和计算节点之间还存在内部接口，但这些接口只供平台自身使用，不属于外部接入契约。

### 2. 身份认证和权限

请求使用平台签发的访问令牌：

```http
Authorization: Bearer gzctf_pat_...
Content-Type: application/json
```

| 权限代码 | 允许的操作 |
| --- | --- |
| `images:read` | 查看镜像及其认证结果 |
| `images:write` | 登记或上传容器、虚拟机镜像并发起认证 |
| `images:delete` | 删除不再使用的镜像 |
| `operations:read` | 查询长时间任务的阶段、进度和结果 |
| `teamlab.topologies:read` | 查看平台能力、场景、正式版本、检查结果和部署预览 |
| `teamlab.topologies:write` | 创建、更新、删除和发布场景 |
| `teamlab.runtimes:read` | 查看运行环境、事件和下载选手配置 |
| `teamlab.runtimes:write` | 创建、重置、销毁环境以及创建、撤销选手配置 |
| `teamlab.traffic:read` | 查询流量和通信路径 |
| `teamlab.capture:read` | 查看和下载抓包结果 |
| `teamlab.capture:write` | 启动和停止抓包任务 |

平台除了检查接口权限，还会继续检查场景所有者、比赛权限组和运行环境归属。

### 3. 防止重复提交

所有创建、修改和删除接口必须携带请求唯一标识：

```http
Idempotency-Key: match-2026-team-17-create
```

- 同一个标识和同一个请求会返回原任务，不会重复创建资源。
- 同一个标识配合不同内容会返回 `409 idempotency_conflict`。
- 标识长度为 1 至 128，只允许英文字母、数字、`-`、`_` 和 `.`。
- 请求结果未知时应查询原任务，不应不断更换标识重新提交。

### 4. 查询长时间任务

发布、创建、重置、销毁和抓包会先返回 `202 Accepted` 和任务编号。调用方使用任务编号查询当前阶段：

```bash
curl "$BASE/api/open/v1/operations/$OPERATION_ID" \
  -H "Authorization: Bearer $GZCTF_TOKEN"
```

调用方应显示接口返回的阶段、进度和失败原因，直到任务成功、失败或取消。不得用固定等待时间猜测操作是否完成。

### 5. 版本冲突、分页和错误

- 更新草稿时必须提交读取到的版本号 `revision`，防止多人编辑互相覆盖。
- 草稿已被其他人修改时返回 `409 topology_revision_conflict`，调用方应重新读取后处理冲突。
- 列表查询使用 `?limit=50&after={cursor}`，单次最多返回 100 条。
- 调用方应根据稳定的错误代码处理，不要依赖可能调整的中文说明文字。
- `401` 表示身份无效，`403` 表示权限不足，`404` 表示资源不存在，`409` 表示状态冲突，`422` 表示提交内容不符合要求。
- 只有明确表示服务繁忙或暂时不可用的 `429`、`503` 才适合延迟后重试。
- 题目密钥、选手接入私钥、镜像仓库凭据和节点令牌不会进入普通日志或普通接口响应。

当前组网接入共包含 34 个开放接口操作：7 个镜像操作、11 个场景操作、8 个运行环境和选手接入操作、7 个流量与抓包操作，以及 1 个任务查询操作。

### 6. 不对外开放的内部接口

以下接口类别属于平台内部实现，不向客户系统开放：

- 管理界面接口：用于试运行、查看节点分配、日志、镜像准备情况和继续清理。
- 比赛管理接口：用于赛前准备、批量创建队伍环境、开放访问、关闭访问和赛后回收。
- 计算节点接口：用于实际创建网络、容器、虚拟机、选手接入通道和抓包任务。
- 节点回传接口：用于上传抓包分段、状态事件和节点能力。

这些内部接口由平台权限和节点身份保护，调用方应使用本章列出的开放接口，不应直接调用内部地址。

## 九、标准接入顺序

1. 查询平台能力，确认当前接口和场景数据版本。
2. 登记或上传场景需要的镜像，并查询导入任务结果。
3. 对需要平台管理能力的镜像发起认证，并确认认证结果。
4. 创建场景草稿，提交网段、设备、连接和启动依赖。
5. 检查场景并修正所有阻断问题。
6. 将通过检查的草稿发布为正式版本。
7. 按需预览节点安排和资源需求。
8. 根据正式版本创建运行环境并查询任务进度。
9. 环境就绪后创建选手接入配置。
10. 运行期间查询状态、事件和流量，必要时启动抓包。
11. 需要恢复初始状态时重置环境。
12. 比赛或培训结束后销毁环境，并确认清理完成。

完整请求字段、返回内容和在线调试以部署后的中文接口页面 `/api-docs/` 为准。
